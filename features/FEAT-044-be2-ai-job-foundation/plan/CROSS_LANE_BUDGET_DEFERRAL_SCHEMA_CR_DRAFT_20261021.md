## 2. Candidate logical record, not final DDL

The minimum logical model is a durable hold generation bound to one persisted active foundation attempt, plus recovery-window identity and durable idempotent operation outcomes. The implementation may normalize these into tables or embed reviewed fields; the exact physical layout is an open schema-review decision. No field named here authorizes an unreviewed column.

## 3. Keys, consistency and compatibility requirements

- At most one ACTIVE hold for a job/current attempt; exact org/job/attempt association and attempt-number checks must be enforced at the owning boundary and by reviewed SQL constraints where representable.
- Hold generation and operation identities are unique in their exact tenant scope. Keep immutable historical outcomes so a prior resume/open lost acknowledgement can be recovered after a later generation exists.
- One future due-retry commit atomically saves the new foundation attempt, job QUEUED, paired run QUEUED/id null and ACTIVE hold. If participant insert/CAS fails, all changes roll back; repeated retry sees no partial attempt allocation.
- Resume/cancel atomically close current hold and update the reviewed delivery/recovery metadata. No job-only or run-only winner is claimed.
- Claim/recovery selection queries and their locked rechecks use current hold status/generation. SQL indexes must support that targeted filtering without claiming an unapproved scheduler.
- Existing physical publication history remains appendable/traceable. Effective recovery counters are distinct from history; immutable historical attempts and their original retry-policy snapshots are not rewritten.
- Outbox lease generation and recovery epoch are different identities. Acknowledgement needs both relevant current identities and a job-locked deferral check; reusing one field for both requires explicit proof/compatibility review.
- No new envelope field, capability claim or authenticated epoch is inferred. Strict generation-bound S admission requires a separate contract binding; otherwise S authenticates existing identity and rechecks CURRENT persisted grant before its unique start CAS.
- No production budget grant may arise merely because an old row has no deferral record. Legacy/backfill behavior for unavailable adoption/configuration fails closed. Preserve unrelated non-video job behavior under its own contract.

## 4. Persistence API and transaction boundary

BE2-01's public transaction-scoped port needs typed lookup/open/CAS/close/replay capabilities plus targeted current-deferral and recovery-window reads. BE2-08 receives only its row participant capability; no application port exposes SQLAlchemy connection or transaction begin/commit/rollback.

Order existing job then run before reviewed deferral/dispatch metadata and the single complete canonical source-fence hold. Accounting is a separate UoW and is not called under lifecycle locks. Exact reservation proof/handoff validity through S, including invalidation/recovery, is a joint BE2-01/14 adoption gate; no ledger table is enlisted by accident.

Unknown reservation/actual execution outcome stays pending. Cleanup settlement/refund requires authoritative no-execution or terminal proof through BE2-14's own contract; a deferral status or elapsed time is not sufficient evidence. Retry's old reservation is never attached to its new attempt.
