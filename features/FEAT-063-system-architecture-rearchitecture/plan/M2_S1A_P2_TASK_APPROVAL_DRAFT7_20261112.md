## 2. Scope

### 2.1 Included behavior

1. **Authentication, target-scope and Parent-role gates.** All five Parent operations require an active `parent` role from `be1_adult_identities.account_role`. Collection `POST /v1/parent/profiles` and `GET /v1/parent/profiles` have no profile target: after authentication, a missing identity row, inactive role or any non-Parent role returns generic 403 `ACTION_NOT_ALLOWED` before request-field validation. For profile-targeted GET/PATCH/DELETE, after authentication, parse `profile_id` as a UUID (invalid UUID: 400 `INVALID_REQUEST`, field `profile_id`, code `INVALID_FORMAT`), then perform a Parent-owned lookup constrained by both verified issuer and subject. A missing or non-owned profile, including same subject with a different issuer, always returns the same generic 404 `PROFILE_NOT_FOUND` before role denial. Only after the profile is known to belong to the principal does a missing identity row, inactive role or non-Parent role return generic 403 `ACTION_NOT_ALLOWED`. This implements the owner’s post-round-3 clarification and matches SRS §9.8/AC-27 and D-174; it is not a phase-specific 403-over-404 exception. Profile-targeted routes must defer parsing the request body and `Idempotency-Key` until after the scope and role gates so malformed input cannot change the selected 404/403 precedence; use a raw `Request` boundary and the single Parent parser rather than a FastAPI typed body that parses JSON before dependencies. Collection POST similarly defers body parsing until after the role gate. The dependency sequence is authentication, owner-scope preflight where there is a profile target, Parent-role check, then request parsing/validation. This remains a documented implementation deviation from SRS §9.9 rule 2 (authorization in the use case); the use case and transaction still enforce ownership. The role port is an application port; the BE1 identity adapter owns the read of `be1_adult_identities`, opens and closes its own short read session (the repository uses `session.begin()` and cannot share it), and checks authenticated issuer and subject against the active Parent identity. The Parent repository never reads BE1 tables. A missing identity row is an authorization result (403), not a store outage. Missing columns, a database/query error or an unavailable adapter fails closed with 503 `PARENT_STORE_UNAVAILABLE`. The role read and command are not one atomic unit: a role revoked between them is accepted and recorded as a known limit. This S1a-P2 direction supersedes D-156 R4 only for these Parent routes; D-156 itself is not edited here. D-171 item 4 continues to govern BE1 organization-role resolution; this Parent-specific source is `account_role`. For this phase, P2-AT-01 proves the route and role contract offline with a fake adapter. Gate P2 PostgreSQL tests use an application-layer role stub and exercise Parent-owned list, deletion-request and receipt behavior only; they do not invoke or validate the production BE1 adapter against PostgreSQL. That adapter path is NOT COVERED until the BE1 state of the task database is aligned by a separate owner decision.
2. **List.** `GET /v1/parent/profiles` with query `limit` (default 25, maximum 100; a value above 100 or a non-integer returns 400 with a `field_errors` entry, per the owner's direction) and `cursor`. Response `{ "items": [<ParentProfileView>], "next_cursor": <string or null>, "request_id": ... }` where items are the caller's profiles in state `ACTIVE`, ordered by `created_at` then `profile_id`. The cursor is an opaque base64url encoding of the last (`created_at`, `profile_id`) with a version tag; a malformed cursor returns 400. A tampered but well-formed cursor cannot expose another owner's rows because the owner and state filters always apply; no signing secret is introduced. Known limit: `created_at` is the transaction start time, so a long transaction can leave a row behind a page already served.
3. **Deletion request.** `DELETE /v1/parent/profiles/{profile_id}` is a command with `Idempotency-Key`. It has no body, so its fingerprint is the operation plus the profile id. It sets `state` to `DELETE_PENDING` (14 characters; `DELETION_REQUESTED` would be 18 and not fit `String(16)`) and returns **202** with the minimal schema `ParentProfileDeletePendingView` = `{ "profile_id", "state": "DELETE_PENDING", "request_id" }` and no profile content. Behavior after the request:
   - GET by the owner returns 200 with the same minimal view (content withheld, FR-C-10). The profile read now includes `DELETE_PENDING` for the owner; `GET` is declared with `response_model=ParentProfileView | ParentProfileDeletePendingView` and the OpenAPI catalog and SRS projection record both shapes under 200 (SRS 21.2's "200 profile projection" becomes polymorphic; owner direction OQ-5).
   - PATCH returns 409 `INVALID_STATE_TRANSITION` (the SRS-registered code; owner direction OQ-5).
   - A replay of an earlier content-bearing PATCH receipt on a `DELETE_PENDING` profile returns the same 409 (the stored body holds profile content). POST replay stays as stored (ids and hash only).
   - A second DELETE with a **new** key on a pending profile returns 409 `INVALID_STATE_TRANSITION` (the UC-09 precondition "no deletion request already active"); a replay of the **same** key returns the stored 202. These deletion outcomes are the owner's selected S1a-P2 direction.
   - The list omits the profile; a StoryRun may not start on it (enforced in S2).
   - The purge of linked content, including content already stored in earlier receipts, and the `be1.data_lifecycle_requests` record are **not** implemented: no cleanup authority exists (D-188). Recorded as known limits.
4. **Idempotency order (transaction receipt-first behavior kept).** For PATCH and DELETE, authenticate, validate path UUID, perform the owner-scoped preflight (404 for missing/non-owned), and check the Parent role (403 only for an in-scope profile) before parsing request fields or `Idempotency-Key`. After request validation, the mutation transaction looks up the receipt first: same scope/key and equal fingerprint replays the stored status/body (except the content-bearing PATCH replay rule above); a different fingerprint returns 400 `INVALID_IDEMPOTENCY_KEY`. With no receipt, the transaction rechecks ownership and state under its lock (404 if scope changed; 409 for a disallowed `DELETE_PENDING` transition), then mutates and stores the receipt atomically. `INVALID_IDEMPOTENCY_KEY` is registered at 400 and is the one 400 without `INVALID_REQUEST`. For DELETE the fingerprint carries only the profile id, so a different-payload case does not exist; the same key on another profile is an independent command. POST create has no profile target: its role gate precedes request parsing, then the transaction keeps the existing receipt-first rule.
5. **Field errors.** The 400 body keeps `code: INVALID_REQUEST` and status 400 and adds the SRS section 9.8 `field_errors`, a list of { "field", "code" }. `field` is the name from the published contract, including body keys, query parameters, headers and path parameters; an invalid UUID in the known `profile_id` path parameter is reported as `profile_id` with `INVALID_FORMAT`. A field name the client invented is reported as the literal `"<unknown>"` with code `UNKNOWN_FIELD` so no client-supplied text is echoed. The owner selected the vocabulary `REQUIRED`, `INVALID_TYPE`, `OUT_OF_RANGE`, `TOO_LONG`, `EMPTY`, `UNKNOWN_FIELD`, `INVALID_FORMAT`; the Pydantic type mapping is fixed in the schema and tests. Entries are sorted by field name. One Parent error builder serves the raw-request parser, `handle_http_exception` and `ParentProfileError`, so bad cursor, bad `limit`, malformed `Idempotency-Key`, bad UUID, bad `expected_revision` and domain validation all carry `field_errors`. Malformed JSON is parsed only after the applicable auth/scope/role gates and returns 400 `INVALID_REQUEST` with an `INVALID_FORMAT` entry on the body root. The other exception to `INVALID_REQUEST` is `INVALID_IDEMPOTENCY_KEY` (400).
6. **Error ordering.** For collection POST/list: authentication 401, Parent role denial 403, then request validation 400. For profile-targeted GET/PATCH/DELETE: authentication 401, invalid path UUID 400, missing/non-owned profile 404, role denial 403 for an owned profile, request validation 400, receipt checks as in item 4, then state conflict 409. A malformed JSON body does not bypass these orders because raw-body parsing is deferred until after the applicable gates. Route tests combine failures to prove each precedence; these are requirements, not observations.
7. **Error mapping and OpenAPI surfaces.** `app.py` adds to `safe_messages` and `default_codes`: 403 `ACTION_NOT_ALLOWED` with a generic message, `INVALID_STATE_TRANSITION`, and the 202 path; its Parent validation handler derives `field_errors` from `exc.errors()` without echoing input. `PARENT_ERROR_RESPONSES` gains 403. Route composition, the OpenAPI catalog and the SRS projection get exactly two new operations (list, delete) and the new response codes and schemas.
8. **Domain state.** A small `ProfileState` enum (`ACTIVE`, `DELETE_PENDING`) in the domain module replaces string literals (SRS section 9.9 asks for an explicit state enum).

## 5. Design (draft proposal with owner directions incorporated)

- **Parent database:** no Parent migration. `state` accepts any string up to 16 characters and has no CHECK; `deleted_at` is reserved for the later purge and not written; the request time is recorded by `updated_at` and the receipt. A dedicated column, a state CHECK or an owner index would require a new separately approved Parent revision and Gate A; none is proposed here. No list performance claim is made without an index.
- **BE1 role columns (owner-reported state; no S1a-P2 migration):** the owner-run read-only preflight reported that the target identity matched and the table exists, but all three columns `account_id`, `account_role`, and `role_revision` are absent; only the Parent revision is stamped. This was not independently queried by Codex. D-190 selects continued S1a-P2 work without a BE1 schema change, identity seed, or Alembic action. The production BE1 adapter path on PostgreSQL is NOT COVERED; close that gap only after a separate owner decision aligns the task database BE1 state.
- **Role port and adapter:** retain the intended application port and BE1 identity adapter, with fail-closed handling for absent identity/columns or a store error. Offline route tests inject a fake adapter to prove role behavior. The Gate P2 PostgreSQL harness injects an application-layer role stub and does not query the BE1 adapter; no PostgreSQL adapter PASS is claimed.
- **List query:** keyset on (`created_at`, `profile_id`) filtered by owner issuer, owner subject and `state = 'ACTIVE'`; no client-supplied SQL names.
- **DELETE:** same receipt table and scoping as PATCH; the transaction locks the profile row; the receipt body holds only the minimal view.
- **Revision hash:** preserve the S1a-P canonical payload and ordering, including the `age_band_ref` and `age_band_version` keys with JSON null; no Rev62 age-band value is populated.
- **Tests:** the existing PostgreSQL acceptance test remains frozen and is not re-run (it assumes the earlier inventory and has no Parent role stub). Gate P2 uses a role stub at the application layer; it must not seed BE1 identity rows or call the BE1 adapter. Inventory-only row counts remain part of the global read-only guard. Its PostgreSQL evidence is limited to Parent-owned list, deletion-request and receipt behavior.
