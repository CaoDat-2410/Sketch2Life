## 2. Amended rules

**Criterion 7 (replaces "It rejects response-status additions and replacements").** Replacements stay rejected. A status may be added only when the pinned catalog projection `published_responses(key, contract["responses"])` declares it for that exact method/path and the pre-state lacks it. The added response object must equal exactly: `description` = the catalog description (restore-checkpoint override where it applies); `content` = `{media_type: {"schema": <catalog schema>}}` when the catalog declares a media type, otherwise no `content`, where the catalog schema is resolved exactly as the mapper resolves it (a component reference, the binary string form, `{"type": "object"}`, or an array of a component reference; an unresolvable name fails); and, only for paths under `/api/be1/v1/` or `/v1/parent/profiles`, `headers` = `{"X-Request-ID": {"description": "Correlation ID for this response.", "schema": {"type": "string", "maxLength": 120}}}`. Any other field, or an added status the catalog does not declare, fails. The post-state status set must still equal the catalog projection exactly. Two further clauses of criterion 7 are replaced: "Preserve ... all response headers" now applies to retained responses only, and the final sentence ("While the request-ID inventory is OPEN, every X-Request-ID request-parameter and response-header object must remain exactly equal ... including presence/absence") is replaced by amended criterion 9 below together with the exact added-response object defined here. Everything else in criterion 7 is unchanged, including the whole-document equality between the constructed expected runtime schema and the post-export schema. Criteria 5, 8 and 12 are not amended.

**Criterion 9 (narrows the scope of the fail-closed rule; this is the owner decision that criterion 9 requires).** Every `X-Request-ID` request parameter, and every `X-Request-ID` response header on a status present in both pre and post, must remain exactly equal in the runtime and the published schema. A status present on one side only is not compared as inventory; it is listed in the report (`requestIdStatusLevelDeltas`), and a header on an added status, if present, must be exactly the pinned object above. This check does not itself flag a missing header on an added status; in the runtime schema that is caught by the whole-document equality of criterion 7, and in the published schema by the exact projection equality. Removed and added statuses themselves stay governed by criterion 7 (runtime) and by the exact published-projection equality. The request-ID inventory otherwise remains OPEN.

**Criterion 11 (one named exception).** `features/FEAT-063-system-architecture-rearchitecture/approvals/TASK_APPROVAL.md` may differ between the pre and post source-state manifests only when both rows are PRESENT with the same Git status, the post size is larger, and the comparator itself proves that both recorded snapshots are byte prefixes of the record as it exists at comparison time (SHA-256 of the first *n* bytes equals the recorded hash, for both sizes). The proof values are written to the report (`sourceState.approvalRecordAppendOnly`). Any other out-of-allowlist difference still fails.
