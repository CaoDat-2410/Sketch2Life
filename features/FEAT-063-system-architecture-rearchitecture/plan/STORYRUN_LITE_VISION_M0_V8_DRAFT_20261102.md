## 3. Luồng command, invocation và phục hồi bắt buộc

1. `POST /story-runs` resolve actor scope server-side và dùng collection scope cố định `COLLECTION:/v1/story-runs`, đã biết trước resource ID. Sau khi parse key và tạo fingerprint, tra collection receipt **trước** active-owner check: same key/scope/fingerprint replay snapshot; same key khác fingerprint trả 400. Chỉ key chưa có receipt mới xét constraint/queue. Trong một Story transaction, unique receipt identity (actor + operation + collection scope + key hash) được dành trước, sau đó tạo UUID run/input và chốt FINAL 201 snapshot. Run UUID đồng thời là `story_run_id`, opaque `story_run_ref` và ledger `run_id`. Fingerprint gồm method/path/API version, RFC 8785 JCS của validated/default-applied request DTO và profile_ref; actor scope đã resolve thuộc unique identity, không lấy từ body. Concurrent same-key/same-fingerprint chỉ tạo một run; loser đọc FINAL receipt và replay nguyên status/body/ref. Key khác nhưng vướng unique active-owner constraint trả 409 `ACTIVE_RUN_EXISTS`, không tạo run.
2. `POST /upload-sessions` bắt buộc `target_kind=STORY_RUN`, `target_ref=<run_ref>`, `purpose=RUN_ARTWORK|RUN_ARTWORK_ORIGINAL`, `media_type`, expected size/hash và Idempotency-Key. Server xác minh run cùng Parent synthetic scope. Create dùng collection scope cố định `COLLECTION:/v1/upload-sessions`; tra receipt trước active-session cap/state checks. Existing same key/fingerprint replays initial snapshot; same key with different fingerprint returns 400. Chỉ key mới mới áp active-session cap và tạo resource. Preallocate upload UUID rồi cùng transaction tạo session + FINAL 201 receipt canonical trong Core. Concurrent same key/full fingerprint replay cùng upload_ref và snapshot, không sinh session hai. Fingerprint là RFC 8785 JCS từ validated/default-applied DTO cộng method/path/API version và gồm mọi trường trên; đổi media_type, target, purpose, size hoặc hash với cùng key trả 400. Original có purpose riêng và typed lineage/association với model-input asset cùng run.
3. Core `PUT part` dùng Parent owner scope đã bind và khóa row session. `(session, part_no)` cùng digest replay 200; digest khác trả 409 `UPLOAD_PART_CONFLICT`. Chỉ part mới nhận khi OPEN/NONE; metadata phải commit trước nhả row lock. Staging key deterministic theo session/part/hash. `PUT part`, complete, abort và expiry serialize bằng row lock/CAS `state_version`.
4. Complete xác minh part 1..N liên tục, byte sum và aggregate SHA trước acceptance, queue permit hay receipt; thiếu part trả SRS 422 `UPLOAD_INCOMPLETE`, giữ RECEIVING/resumable và không tiêu key. Từ OPEN/NONE chỉ một command thắng sang OPEN/PENDING; competing key khác trả 409. Từ OPEN/QUARANTINED, chỉ complete với If-Match hiện tại, cùng exact aggregate bytes/hash và key mới được CAS sang OPEN/PENDING; REJECTED/FAILED không retry. Mỗi accepted retry có receipt riêng; exact duplicate chờ cùng dispatcher hoặc replay snapshot, không dispatch lần hai.
5. Khi capacity còn, Core transaction ghi validation_state=PENDING + receipt PENDING, commit, enqueue gated command, ack rồi chốt FINAL 202; chỉ sau commit mới mở gate. Queue full trả 503 trước mutation/receipt/key use. Worker kiểm media/dimensions/hash; mọi exact source/normalized digest phải CLEAN mới chuyển COMPLETED/CLEAN và tạo Core Asset ref. Scanner ERROR/timeout hoặc recovery PENDING chuyển session sang OPEN/QUARANTINED, tăng version, giữ parts, không tạo asset/provider call; GET trả trạng thái/error retryable và client phải chủ động gửi complete mới với key khác.
6. Mapping API: Core OPEN/NONE→RECEIVING; OPEN/PENDING→VALIDATION_PENDING; OPEN/QUARANTINED→QUARANTINED; COMPLETED/CLEAN→READY + asset ref; FAILED/REJECTED→REJECTED; ABORTED/EXPIRED giữ nguyên. GET EXPIRED trả 410 SRS envelope kèm `upload_status` pilot-v1 snapshot gồm state/version/purge_state/purge_completed_at/updated_at; cùng-scope client poll đến PURGED. Trước migration, DATA_TABLE_REGISTER phải khai báo target/purpose, receipt ownership, typed owner constraints/FK/backfill, validation/state/cleanup fields. Core `organization_id` không giả Parent tenant.
7. Abort và expiry cạnh tranh cùng row lock với part/complete. Abort chỉ RECEIVING/QUARANTINED; expiry chỉ session hết hạn ở trạng thái resumable. Transition ghi ABORTED/EXPIRED, purge_state=PENDING, tăng version và FINAL 202 receipt trong cùng transaction. Durable tombstone là lệnh cleanup; startup/periodic sweeper xóa tất cả part/staging objects idempotently, rồi đánh dấu PURGED. Crash sau 202 không làm mất cleanup. Command receipt/tombstone không xóa theo session TTL trong pilot.
8. Story attach/dispatch chỉ nhận asset READY/CLEAN đã thuộc actor/run và đúng digest; request có expected run revision + Idempotency-Key. Reserve một permit tổng active+queued trước transaction. Full → 503 không mutate/key. Story transaction lock/CAS run revision, ghi binding + `INPUT_PROCESSING` + PENDING receipt; enqueue gated command; queue ack → FINAL 202 commit → mở gate. Duplicate cùng key PENDING chờ dispatcher; nếu dispatcher không còn, recovery chốt FINAL 409 `VISION_ATTEMPT_HOLD`, không enqueue mới.
9. Startup chỉ sau khi lấy advisory lock và cấp epoch mới mới reconcile PENDING receipts: không redispatch; Core validation PENDING chuyển QUARANTINED/hold retryable, giữ receipt lịch sử và yêu cầu key mới cho retry rõ ràng (zero provider); Story attach PENDING thành `AWAITING_RECONCILIATION`/`VISION_ATTEMPT_HOLD`. Queue RAM không là nguồn dispatch bền.
10. Worker A1 chạy đồng bộ trong thread executor riêng; mọi transition `claim` và `mark_sent` transactionally kiểm worker_epoch + expected run revision qua D17. Lock/fence refusal trước SENT là zero send. Sau durable SENT chỉ attempt đó được phép đi qua HTTP, kể cả lock loss ngay sau SENT; process mới không bao giờ mở attempt khác. Deadline/decode/scanner không block event loop.
11. Story result hook nằm trong `InvocationGuardedVisionObservationPort` trước `finalize()`: khi response V2 hợp lệ, UoW ghi immutable result/revision receipt keyed by run/job/attempt/hash. Cập nhật run head chỉ bằng CAS expected revision+worker_epoch. Hook/write failure sau SENT tạo UNKNOWN/hold, không success/resend. `transport_response_body_sha256` là raw HTTP body; `canonical_result_sha256` là canonical validated JSON; không gộp hai hash.
12. Nếu ledger finalize thành UNKNOWN nhưng durable result receipt tồn tại và tuple đúng, reconciler giữ ledger UNKNOWN, đọc receipt và cập nhật Story projection dưới epoch hiện hành; API có thể trả SUBJECT_REVIEW. Nếu không có receipt/result mà ledger CLAIMED/SENT/UNKNOWN, state là SRS `AWAITING_RECONCILIATION`, error code versioned, retry_allowed=false, action_required=OPERATOR_REVIEW. Không cooldown retry hoặc reanalyze.
13. `GET`/health/status chạy trên event loop riêng, phải trả trong lúc blocking worker chờ loopback. Pending state chỉ báo `INPUT_PROCESSING` khi receipt/worker còn active; hold/UNKNOWN không bao giờ trả 202 như gợi ý gửi lại.

### Crash/race matrix cho upload/attach/dispatch

| Sự kiện | Kết quả bền và API | Bảo đảm không lặp |
|---|---|---|
| Queue full trước Core/Story receipt | 503 `QUEUE_UNAVAILABLE`; không mutation/key use | Không có command để worker chạy |
| Part bị thiếu khi complete | 422 `UPLOAD_INCOMPLETE`; Core vẫn OPEN/RECEIVING, state_version không đổi, key không tiêu thụ | Client bổ sung part và complete lại cùng session |
| PUT part đua complete/abort | Row lock/CAS có một winner; loser reread state và nhận conflict, metadata không chèn sau transition | Staging object không tham chiếu bị sweeper xóa |
| Hai complete khác key | Chỉ một chuyển OPEN→VALIDATION_PENDING; request thứ hai 409 | Chỉ một validation dispatch |
| Cùng complete key còn PENDING | Chờ cùng dispatcher; nếu dispatcher mất, recovery chốt hold | Không enqueue bản thứ hai |
| Crash sau Core abort/expiry 202 | Tombstone + purge_state=PENDING; GET thể hiện abort/expired và cleanup pending | Startup/periodic sweeper tiếp tục purge idempotent |
| Crash sau PENDING trước queue ack | Recovery hold/quarantine; không tạo asset/provider | Key cũ replay hold; validation retry phải dùng key mới sau GET |
| Scanner ERROR/timeout hoặc Core validation recovery | Session thành OPEN/QUARANTINED, state_version tăng, parts giữ nguyên, GET có safe error/retryable | Không tạo asset hoặc gọi Vision; client gửi complete với key mới + If-Match hiện tại; một CAS mới enqueue tối đa một scanner attempt |
| Hai client retry validation từ cùng QUARANTINED version | Row lock/CAS cho đúng một complete mới chuyển OPEN/PENDING; request còn lại nhận 409 STALE_REVISION, key không tiêu | Chỉ một validation dispatch; same-key duplicate replays/chờ receipt của dispatcher thắng |

| Lock lost sau SENT | Run hold/reconcile; attempt đó có thể kết thúc tối đa một lần, receipt immutable theo epoch | New process thấy SENT; không có attempt/send mới |
| Result receipt commit trước ledger finalize | Story result bền; finalize có thể UNKNOWN | Reconcile cùng tuple; ledger UNKNOWN không mutate |
| Stale epoch ghi run head | CAS không khớp, projection không đổi; immutable receipt vẫn audit được | Worker cũ không overwrite recovery |

### Hai hash kết quả không được gộp

- `transport_response_body_sha256`: SHA-256 của đúng raw HTTP response body; A1 transport đưa hash này vào InvocationGuard/Ledger field hiện có `result_sha256`.
- `canonical_result_sha256`: SHA-256 canonical JSON sau khi bridge/model validation hoàn tất; đây là hash result document/evidence và Story revision.
- `original_image_sha256` và `model_input_sha256` là hai hash khác của ảnh gốc và ảnh dẫn xuất thực gửi VLM.

Story receipt phải ghi tên/ý nghĩa/version của từng hash. Không so sánh raw HTTP body hash với canonical JSON hash như thể chúng cùng bytes. Nếu mapping/version không khớp, receipt không đủ điều kiện reconcile.

### Request/response contract tối thiểu

- Create run nhận đúng một `profile_ref` là server-seeded synthetic profile; cấm list children/profiles.
- Create upload nhận `target_kind=STORY_RUN`, `target_ref`, `purpose=RUN_ARTWORK|RUN_ARTWORK_ORIGINAL`, `media_type`, `expected_size_bytes`, `expected_sha256` và Idempotency-Key; Parent synthetic scope được resolve từ server. Fingerprint có toàn bộ trường này; original liên kết typed với model input cùng run. Trả opaque upload ref, part size và expiry.
- Upload part dùng request body bytes, path part number từ 1, Content-SHA256 và Content-Length; client không gửi storage key.
- Complete nhận aggregate byte count/hash + Idempotency-Key; response snapshot không đổi. GET upload resource là nguồn chuẩn cho tiến độ validation.
- Story attach nhận model-input asset ref, optional original ref và expected run revision; backend kiểm owner, CLEAN và hash chính xác bytes gửi VLM.
- Subject confirmation chỉ nhận CONFIRM, expected understanding revision và Idempotency-Key.
- Error envelope theo SRS: `{code, message, correlation_id, retryable, retry_after_seconds?, field_errors?}`; không echo bytes/key/token/signed URL/provider detail. OpenAPI `StoryRunLite-v1` định nghĩa extension `upload_status` chỉ cho 410 GET upload để client poll tombstone/purge; các lỗi khác giữ envelope chuẩn.
- Story poll DTO trả `run_state`, `revision`, `state_version`, luôn có `target_revision` (current job expected revision; nếu chưa có job thì current run revision), run `started_at`, `updated_at`, optional `job_state/job_stage/job_started_at` chỉ khi current job tồn tại, `retryable`, `action_required`, safe `error`; `progress` chỉ khi đo được. ETag/If-None-Match; backoff theo SRS §9.5. Không trả target ref cross-scope, payload/prompt hoặc phần trăm bịa.
- Pilot extensions được version trong OpenAPI `StoryRunLite-v1`: `VISION_ATTEMPT_HOLD` là 409 response code; `IMAGE_SAFETY_REJECTED` là 422 response code; `PROVIDER_OUTCOME_UNKNOWN` là safe code trên Story status dùng SRS `AWAITING_RECONCILIATION`; `SAFETY_SCANNER_UNAVAILABLE` là safe error của upload state QUARANTINED. `IMAGE_DIMENSIONS_EXCEEDED`, `UPLOAD_INCOMPLETE`, `UPLOAD_CHECKSUM_MISMATCH`, `UPLOAD_CONTENT_MISMATCH`, `STALE_REVISION` và `QUEUE_UNAVAILABLE` đã có mapping trong SRS §9.8 và phải giữ nguyên. Không thêm SRS run state.

### Status, errors và limits

- 400 `INVALID_REQUEST`, SRS `INVALID_FILE_CONTENT`, `INVALID_IDEMPOTENCY_KEY`; 404 `RESOURCE_NOT_FOUND` cùng shape cho absent/out-of-scope.
- 409 `STALE_REVISION`, `ACTIVE_RUN_EXISTS`, `INVALID_STATE_TRANSITION`, `UPLOAD_PART_CONFLICT`, `UPLOAD_SESSION_STATE_CONFLICT`; pilot `VISION_ATTEMPT_HOLD` có versioned extension.
- 410 `UPLOAD_SESSION_EXPIRED` follows SRS §9.8 and carries the versioned `upload_status` tombstone extension on upload GET. Core receipt still replays the original command snapshot independently.
- 413 `MEDIA_TOO_LARGE`; 415 `UNSUPPORTED_MEDIA_TYPE`; SRS codes giữ đúng mapping §9.8: `INVALID_FILE_CONTENT`=400; `STALE_REVISION`=409; `IMAGE_DIMENSIONS_EXCEEDED`, `UPLOAD_INCOMPLETE`, `UPLOAD_CHECKSUM_MISMATCH`, `UPLOAD_CONTENT_MISMATCH`=422; `QUEUE_UNAVAILABLE`=503. Pilot extension `IMAGE_SAFETY_REJECTED`=422, versioned. Scanner unavailable/error/timeout is a retryable upload state `QUARANTINED` with versioned `SAFETY_SCANNER_UNAVAILABLE`, never an attached asset or provider call. No pilot code silently reuses an SRS code with a different HTTP status.
- 429 `RATE_LIMITED` + Retry-After theo SRS §10.4: generic API 60/min/account; local unauthenticated IP 20/min; create run 2/min/account; upload create/complete/abort 10/min/account; chunk PUT 60/min/account và tối đa 40 MiB byte mới/min/account; tối đa 3 active upload sessions/account; status/list parts 30/min/session. Exact-digest chunk retry tính request nhưng không tính byte mới. Demo dùng một synthetic principal, không nới ngưỡng.
- 503 `QUEUE_UNAVAILABLE` + Retry-After khi bounded outstanding capacity=1 đang dùng; từ chối trước DB mutation/receipt/key use. Đây là command admission, khác rate limit.
- `GET /v1/story-runs/{id}` vẫn HTTP 200 cho run đã tạo. Result có sẵn trả SUBJECT_REVIEW; chưa có response V2 hợp lệ trả SRS `AWAITING_RECONCILIATION` + versioned code, `retryable=false`, action operator. Không dùng 202/503 để gợi ý resend.
