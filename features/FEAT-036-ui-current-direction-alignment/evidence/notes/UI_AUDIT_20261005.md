# UI audit — 2026-10-05

## Method and limits

- Read `docs/context/PROJECT_CONTEXT.md`, `docs/context/SOURCE_REGISTER.md`, the governance workflow,
  the current-system/SRS baseline, ADR-0012 and ADR-0013, and the FEAT-033/034/035 status evidence.
- Reviewed the active `apps/ui-mobile` entry and screen source, the `apps/mobile` fixture-flow shell,
  the renderer screen integration, and the Parent Web / child-app boundary notes.
- Visually inspected preserved FEAT-035 screenshots and current `Pixel 10` Android runtime captures
  for onboarding, Home, child profile, Story Preview, Activity Recommendation, Parent Review, Pixi
  Intro, the native developer menu, and the initial missing-bundle launch error. A follow-up flow
  used the bundled synthetic drawing through the app's configured local demo workflow; no real child
  content or production account/data was used.
- Source review covers screens for which no current screenshot is available. No claim is made that
  all 15 screens passed device visual QA. Source defines a web developer switcher (`?dev=true`) and
  direct screen selection (`?screen=<id>`), but an Expo Web preview remained blank with an empty
  root on both `127.0.0.1` and `localhost`. The current `index.ts` registers the component with
  `AppRegistry` without Expo's web root bootstrap, which appears to block this capture route. This
  is a preview capture blocker, not native-device evidence. The quick switcher is Web-only: the
  triple-tap status-clock handler returns on native platforms. Android Studio's Device Manager
  opened the `Pixel 10` AVD. The app first showed a missing-bundle error with Metro unavailable;
  after Metro/ADB reverse was available, relaunch loaded the native UI. Android's React Native Dev
  Menu is available, but it does not provide app-route selection. The fresh album has 13 PNGs with
  unique SHA-256 hashes: 11 of 15 active route components, plus an inline voice-recording mode and
  an activity-prerequisite state. The separate Voice route and final three routes are not pictured;
  Pixi preparation failed after retry and blocked its downstream handoff.

## Findings

### UI-01 — Home safe-area overlap from the preserved screenshot is not reproduced (unconfirmed)

The preserved FEAT-035 `home-emulator-20261005.png` suggested that the header and bottom tabs crossed
system insets. The current `dashboard-runtime-emulator-20261005.png` on Pixel 10 does not reproduce
that: the greeting is below the Android status bar and the tab labels are above the gesture area.
Treat the earlier observation as stale-build evidence, not a confirmed current defect. Verify other
routes and navigation modes during a later device matrix run.

**Follow-up:** keep safe-area behavior in the cross-screen/device matrix. Do not schedule an inset fix
from the stale screenshot alone.

### UI-02 — Activity list is collapsed to three cards by default (P1)

`ActivityRecommendScreen` assigns `visibleActivityCards` to
`activityRecommendationCards.slice(0, 3)` while `showAllActivities` is false. A separate expand action
exists, but the normal first view is still a three-card shortlist. ADR-0012 and SRS B33 require the
complete topic + exact-age match set to be available in the normal chooser; preferences rank/explain
but never remove matching activities.

**Fix:** render the complete result set by default. If measured constraints require paging, retrieve
every page and make it clear that more results remain.

### UI-03 — Video screen is a handoff placeholder (P1; separate contract dependency)

The active screen is named `Video Placeholder`, tells the user that the “main video” will be added in
a future version, and continues to outdoor activity. The master SRS B30–B32 targets a 40–60 second
illustrated story video after exact adult script approval. Parent continuation requires a playable,
validated `READY` artifact. Pixi exploration is a separate implementation; the current placeholder
does not provide video approval, job/recovery, or playback states. `ScreenId` also includes
`video_player`, but `BaoApp` does not render a corresponding case.

**Fix/task:** scope video UI and runtime separately against an approved versioned contract. Add script
review/approval, truthful job status, retry/recovery, playable validated video, and the required
continuation gate. Do not infer success from a Pixi completion or still-image fallback.

### UI-04 — Required Parent Web and Guide Console surfaces are absent (P1; separate task)

The current source tree has no Parent Web or Guide Console screens. `apps/parent-web/README.md`
describes the web split as inactive, while the newer owner-approved master SRS B21/B20 makes Parent
Web (mobile and desktop responsive) and the desktop Guide Console target product surfaces. The root
project context also has a stale “mobile-only” statement alongside the later multi-surface scope.

**Fix/task:** reconcile project context and create separately approved feature plans for Parent Web
and Guide Console. Their authorization, ownership, assignment, feedback, observation and responsive
flows must use backend contracts/policy; Parent Web must not silently become a session runner.

### UI-05 — Demo identity is presented like an operational account (P1)

The active context initializes `MOCK_CHILDREN` and selects the first child by default; Home hard-codes
“Chào chị Lan!”. There is no adult sign-in/owner or Guide assignment screen in the active screen map.
That is acceptable only as a clearly identified fixture/demo experience. SRS actor and ownership
rules require authenticated adults and backend-authorized caregiver links/Guide assignments for
operational use.

**Fix:** visibly label fixture/sample identities and content. Scope adult sign-in, linked-child
selection and Guide-assignment entry in the owning operational surface. Never treat a UI role label
as authorization.

### UI-06 — Home story-card images render correctly in current runtime (stale finding; not reproduced)

The preserved FEAT-035 Home screenshot showed cyan and mint rectangles in the two “Câu chuyện mẫu”
cards. The current `dashboard-runtime-emulator-20261005.png` shows the fish and robot artwork loaded
in those cards, so this issue is not reproduced in the current Pixel 10 runtime.

**Disposition:** no image fix is proposed from current evidence. Keep an image-loading fallback in
the follow-up review if the issue reappears on another device.

### UI-07 — Story Preview artwork and thumbnails look washed out in the default demo state (P2; verify)

`story-preview-runtime-emulator-20261005.png` shows the meadow illustration and three scene cards at
very low contrast, even though the heading says the topic is ready and the primary action is active.
The screenshot is from the default synthetic state without a selected drawing, so the visual may be
intentional for a placeholder. Compare with a fully selected-drawing flow before filing a definite
visual defect.

**Follow-up:** the selected synthetic drawing renders clearly in the current Story Preview. The
real-flow screen does not show the default demo scene thumbnails, so their contrast is still
unverified; keep the issue limited to that state until those cards are inspected in a working flow.

### UI-08 — Native debug menu does not select app screens (capture tooling gap)

The Android emulator opens `React Native Dev Menu (Bridge)` with Reload, Open DevTools, Change Bundle
Location, Inspector, and related runtime tools. It has no 15-screen route selector. The app's own
`?dev=true` quick switch and `?screen=<id>` selection are Web-only, while Expo Web currently leaves
`#root` empty. This explains why a native emulator session cannot currently jump through every app
route for this review.

**Follow-up:** scope an approved capture path: make the Web root mount, or add a dev-build-only native
route selector. Keep it out of production routes and do not count the standard React Native Dev Menu
as app-screen coverage.

### UI-09 — Native app launch needs a reachable Metro bundle in this debug build (environment blocker)

On first launch the emulator showed the standard “Unable to load script” red screen. The native log
attempted `127.0.0.1:8081`. After project Metro/ADB reverse was available and the app was relaunched,
onboarding rendered. This is a development-runtime setup blocker, not a product screen-layout defect;
the initial error screenshot is preserved separately.

**Follow-up:** document the supported emulator startup command and port mapping so review builds reach
Metro consistently. Do not change app UI as part of this audit.

### UI-10 — Pixi renderer preparation failure blocks the final handoff (P1 runtime blocker)

After synthetic Gate A and Gate B confirmation, Pixi Intro opened in landscape as designed but showed
the app error dialog that renderer preparation could not complete. Retrying returned the same error.
The `Tiếp tục` handoff remained unavailable, so Video Placeholder, Outdoor Activity, and Feedback
could not be reached through the current native flow. The landscape capture is
`screenshots/ui-full-20261005/12-pixi-intro-error.png`.

**Follow-up:** investigate the local renderer preparation response and retry/recovery state before
using this path for end-to-end visual review. This is a runtime prerequisite finding; no UI code was
changed in this review.

### UI-11 — Standalone Voice screen is not connected to the current Capture flow (P2 route gap)

The native user flow exposes voice recording inline from Capture. The separate `VoiceScreen` route
was not reachable through a visible control; source search found no `nav('voice')` call from active
screens. The inline recording controls are captured at
`screenshots/ui-full-20261005/06-voice-recording-inline.png`; this does not verify the standalone
screen component's layout.

**Follow-up:** decide whether the inline mode replaces the separate route or the route should be
connected in a separately approved UI task.

## Existing behavior to preserve

- Profile screen uses completed age in years/months and session-scoped preferences rather than DOB.
- Normal discovery must retain exact age, confirmed Gate-A topic, adult/caregiver and safety rules; it
  must not restore readiness/history/material availability as discovery filters.
- Gate A, Gate B, Pixi, physical handoff, and feedback remain explicit flow concepts; original drawing
  preservation and typed renderer failure/recovery remain visible.
- The old `DemoWorkflowScreen` contains a readiness questionnaire but is not rendered by the active
  `BaoApp` route. Do not treat it as the active normal flow or reintroduce its questionnaire.
