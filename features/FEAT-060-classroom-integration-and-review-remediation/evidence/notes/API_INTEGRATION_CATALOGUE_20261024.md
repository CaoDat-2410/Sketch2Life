## 1. Runtime and trust boundaries

- Child UI uses `EXPO_PUBLIC_BE1_BASE_URL`, calls `/api/be1/v1`, sends a request ID, and stores its device grant/key only in Expo SecureStore. It does not receive an adult token or call Modal.
- Teacher and Admin authenticate through Firebase Auth. Their BE1 clients attach the Firebase ID token as `Authorization: Bearer`, `X-Request-ID`, and JSON content type. Organization and BE1 base URL come from app environment configuration. Adult role/class scope is checked by BE1.
- `classroom_main.py` selects the classroom-only composition; `demo_main.py` selects the local/demo routers; the compatibility `create_app()` keeps both route groups. Composition tests pass, but deployment/process wiring and a live environment were not exercised here.
- Teacher routes without an adopted contract are blocked from fixture behavior by default; their prototype screens require an explicit `?demo=1` URL. Teacher setup/lobby/orchestration and the BE1 observation page remain available in runtime mode. Admin unsupported routes already show the same unavailable state.
- Current backend flows rely on the configured BE1 persistence adapter. This workspace did not have a usable disposable PostgreSQL profile for the integrated UI flow. A mocked UI test plus isolated backend contract tests is not a single FE-to-DB receipt.
- Modal remains an AI-provider boundary for future, approved BE2 work. No Modal URL/model/GPU/region/timeout/spend profile was supplied, and this classroom path makes no Modal request. Moving the whole BE1 container to Modal is not required for the proposed inference boundary.
