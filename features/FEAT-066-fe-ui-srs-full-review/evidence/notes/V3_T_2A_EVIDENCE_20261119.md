## 2. Decisions (T-2a-DEC-n, SRS-cited)

- T-2a-DEC-1 (mount, Q1; l.1654-1658): the generic routes and the StoryRun-lite demo own the same literal paths, so they are mutually exclusive in one process: mounted only when `STORYRUN_LITE_MAIN_DEMO_ENABLED` is 0 (`include_upload_sessions` defaults to True; both flag values tested). With the demo on, the CONV-1 envelope rule for `/v1/upload-sessions` is off, so demo bodies stay unchanged (tested: 422 lite validation body, 404 `{"detail": "Not Found"}`, sibling path untouched). The router is registered in `story_demo_replaced_routers()`, so the T0.5 startup guard (collision count 4 to 9, unmounted 9 to 14) requires the existing acknowledgement variable. Android note for the FE: demo mode takes the part hash in `Content-SHA256`, real mode in `X-Part-SHA256`.
- T-2a-DEC-2 (asset reference, F-01; FR-C-08): a Parent asset has `asset_ref` = object key = `parent/{run_id}/{token}/original`, `asset_version` 1, `source_refs == [run_id]`, `owner_scope_kind PARENT_ACCOUNT`, `owner_scope_ref` = hash of `{issuer, subject}` (same formula as the Story repository, pinned by a test), NULL organization. `token` is the UUIDv5 of the session id, so a retried complete overwrites instead of leaving an orphan. Chunks are `parent/{run_id}/upload/{session}/parts/{n}` (under the run prefix, no metadata row, so the run-prefix sweep removes a leftover). The physical key stays in `core_upload_sessions.final_asset_ref` and `core_asset_metadata.asset_ref` (the purge keys on it) and never leaves the API: the `asset_ref` in a 202 or GET body is the opaque handle `upl_{upload_id}` (SRS l.1692, implementation review T2A-IR-02, coordinator ruling). A server-side consumer resolves it with `resolve_asset_key(db, handle, scope...)`, which returns the key only for a COMPLETED session in the caller's scope (T-2b and T-3b must use it and re-verify the hash). Tested: the handle holds no key text, the helper returns the key in scope, `None` for another scope and for a physical key. Teacher assets use the resolver's organization prefix and organization scope. A PostgreSQL test completes an upload and proves the purge plan is removable (no `KEY_UNKNOWN`, no `SHARED_REFERENCE`) and the prefix is clean after the sweep.
- T-2a-DEC-3 (complete failures, F-03; l.504, l.1657, l.940, l.1934): retryable, session stays `OPEN`, nothing written: `UPLOAD_INCOMPLETE` (422), body size or hash differs from create (422 `UPLOAD_CHECKSUM_MISMATCH`), scanner unavailable (503 `PROVIDER_UNAVAILABLE`), object store unavailable (503 `STORAGE_UNAVAILABLE`), target no longer accepting (409 `INVALID_STATE_TRANSITION`). Terminal, `FAILED` plus `error_code` and `validated_at` committed before the error is raised, chunk objects purged, part rows kept: stored bytes failing the part or aggregate size/hash (422 `UPLOAD_CHECKSUM_MISMATCH`), declared type not accepted by the purpose (415), signature not matching (422 `UPLOAD_CONTENT_MISMATCH`), infected or not CLEAN (422 `MALWARE_DETECTED`, `scan_verdict` set). Receipts hold successes only (C-D6), so a repeat of a terminal failure answers 409 `UPLOAD_SESSION_STATE_CONFLICT`. An asset exists exactly when its metadata row exists and the session is `COMPLETED`; a failed check leaves no asset row. The signature check uses the T-2z port `upload_media_validator` (and its shared table through `header_matches_media_type` when the port is `None`); no signature table is duplicated.
- T-2a-DEC-4 (RUN_ARTWORK, F-02 and Q4; l.983, l.1942, NFR l.657): JPEG, PNG and WebP, at most 20 MiB (five 4 MiB parts, inside the 25,000,000 CHECK). The 40 megapixel decode check stays with T-2b. Documents (`OCCURRENCE_DOCUMENT`): PDF, DOCX, PPTX, at most 25,000,000 bytes (FR-T-06 l.545), the extension must match the declared type; page count and encryption stay with T-3b. Over the cap is 413 (`MEDIA_TOO_LARGE`, `LESSON_FILE_TOO_LARGE`), a type outside the purpose 415 (`UNSUPPORTED_MEDIA_TYPE`, `UNSUPPORTED_LESSON_TYPE`). The SRS itself says 422 `UNSUPPORTED_MEDIA_TYPE` at l.983 but lists it under 415 in section 9.8 (l.870); §9.8 and the source plan table are followed.
- T-2a-DEC-5 (RUN_AUDIO, Q2; l.982, l.1942): declared in the policy table and disabled: create answers 400 `INVALID_REQUEST` with field `purpose`. The SRS lists no audio type and the 2 minute rule needs a decoder (T-2c). `AUDIO_TOO_LARGE` is omitted from the messages until then: a recorded deviation from the WP-2 route table.
- T-2a-DEC-6 (codes, Q3 and F-04; §9.8 l.859-873): `MALWARE_DETECTED` (422) is kept as a technical decision outside §9.8, as on the lesson and Parent flows (the SRS settles the behaviour only, l.940, l.1934); the owner may switch it to `INVALID_FILE_CONTENT`. A scanner outage is 503 `PROVIDER_UNAVAILABLE` (retryable); 503 `STORAGE_UNAVAILABLE` is only for object-store faults. A test proves a scanner outage never creates an asset.
- T-2a-DEC-7 (scanner provenance, T-2z OP-2 and F-06): the session columns `scan_verdict`, `scanner_name`, `scanner_version` are the operational copy. `core_asset_lineage.scanner_sha256` means the scanner identity digest `scanner_identity_sha256(name, version)` (the Parent writer's formula). T-2a writes no lineage row (nothing is derived at upload); T-2b and later writers must use that helper. The StoryRun-lite writer's content digest in the same column is demo-only (a different stack, mutually exclusive with the real routes) and is not read as identity.
- T-2a-DEC-8 (run deletion, D10 and F-05; FR-C-08): `SqlCoreRunUploadClose.plan_close_run_uploads` returns the union of the lite and the generic open session ids; `close_run_uploads` returns the sum. A generic session of the run (scope kind and ref, `target_ref`, purposes `RUN_ARTWORK` and `RUN_AUDIO`, state `OPEN`) goes to `ABORTED` with `error_code = 'RUN_DELETED'` and `aborted_at`. Chunk objects are removed by the run-prefix sweep (the close class has no storage port); completed-but-unattached assets are already purge seeds through `source_refs`. A close that races a running complete waits for the session row lock and then closes nothing (tested); after a close, complete answers 409 and writes nothing (tested).
- T-2a-DEC-9 (DDL scope, F-06): the asset version convention is "version 1" (no `final_asset_version` column); no extra CHECK on `scan_verdict` or on `OCCURRENCE_DOCUMENT` implying `ORGANIZATION` scope (not needed for approval, can be added later); `OCCURRENCE_DOCUMENT` is a register amendment inside DDL-F: reusing `LESSON_SOURCE` would make occurrence sessions visible to the lesson routes (`service.py` loads by purpose).
- T-2a-DEC-10 (contract details, F-07): create fields `purpose`, `target_ref`, `media_type`, `expected_size_bytes`, `expected_sha256`, optional `file_name`; unknown fields are 400 with `UNKNOWN_FIELD` (client cannot send role, owner or organization, l.1637). `safe_file_name` is server-generated for images (`artwork.<ext>`), the sanitized last path segment for documents. `owner_principal_ref` = the verified subject; `owner_scope_ref` the Parent hash; the access predicate checks both and re-resolves the scope on every call. A wrong part length is 400 `INVALID_REQUEST` with field `body`, a part number outside 1..expected is 400 with field `part_no`, a missing or malformed `X-Part-SHA256` is 400, a wrong content type is 415, a part over 4 MiB is 413 with the purpose's too-large code, a body not matching its hash is 422 `UPLOAD_CHECKSUM_MISMATCH`. DELETE: missing or weak `If-Match` is 400 `INVALID_REQUEST` with a field error (same behaviour as the lesson helper). The raw body is documented with `openapi_extra`; `openapi_contract_amendments.py` is unchanged (the `/v1` operations are outside its catalogued prefixes). The part header is the same hash header as the lesson route; generic parts do not take `Content-Range`. `_require_parent` is not reused (wrong role is the uniform 404, CV-5).
- T-2a-DEC-11 (not enforced, F-08): rate limits and concurrency caps of l.975-978 (X-18 `RATE_LIMITED` is planned in no goal) and the three-active-sessions cap are not enforced and no hook is added; Teacher `RUN_ARTWORK` (FR-T-11) is deferred to the Teacher run task (DDL-F already allows an organization scope for it).
- T-2a-DEC-12 (state and races, F-09): a run outside `INPUT_PROCESSING` answers 409 `INVALID_STATE_TRANSITION` (§9.8), mapped from the repository's `PARENT_STORY_RUN_NOT_ACCEPTING_ARTWORK`; the state is re-checked under the session lock before every chunk write and again right before the final PutObject. Part rows stay after abort, expiry and completion, only objects are deleted, so the derived revision (1 + parts while open, 2 + parts otherwise) does not change.
- T-2a-DEC-13 (route behaviour): create is keyed, 201, `ETag` = revision, a replay returns the first response with 201; the key is the single authoritative value from `parse_idempotency_key`. Receipts are in `be1_command_receipts` (principal, operation and target in the scope string, SHA-256 of the canonical payload as fingerprint; a Parent needs no organization); a concurrent same-key create loses the PK race, rolls back its session row and replays. GET answers 410 for an expired session (it is expired and its objects purged on touch). Complete is synchronous and answers 202 with state `COMPLETED`, `asset_ref`, `asset_state READY` and scanner name and version. DELETE order: replay, expiry (410), state conflict (409), stale revision (409 `STALE_REVISION` with the current ETag). OCCURRENCE_DOCUMENT has no default resolver (no occurrence table at this commit): until T-3a/T-3b register a factory in `app.state.upload_target_resolver_factories` it answers 404.
