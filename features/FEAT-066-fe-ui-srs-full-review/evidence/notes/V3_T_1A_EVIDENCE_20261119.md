## 2. Decisions (T-1a-DEC-n; the plan's D1..D11 apply as written, these are the implementation facts)

- T-1a-DEC-1 (route, D1; l.1670, l.1697-1699): `POST /v1/story-runs/{run_id}/video-generations`, body `expected_revision` (run revision), `story_sha256`, optional `quality_reason_code` (`QUALITY_LOW`, `NOT_MATCHING_STORY`, `CONTENT_CONCERN`, `OTHER`, candidate set; Q5), `extra=forbid`; `Idempotency-Key` required (missing or malformed: plain 400 `INVALID_REQUEST`, no `field_errors`; same key with another payload: 400 `INVALID_IDEMPOTENCY_KEY`). 202 `ParentVideoGenerationAcceptedV1 {request_id, video_generation{generation_id, state, generation_no, kind, job_id, run_state, run_revision}}`; `job_id` null until accepted. Check order, as implemented in `begin_intent`: role, key syntax, owner-scoped locked lookup 404, purged run replay or 409, replay by key (fingerprint equal or 400), run state, revision then hash (409 `STALE_REVISION` with `current_version`), unconfirmed or consumed script (409 `INVALID_STATE_TRANSITION`), defensive 422 `PROFILE_CONTEXT_NOT_CONFIRMED` / `SUBJECT_NOT_CONFIRMED`, cap (409 `VIDEO_REGENERATION_LIMIT_REACHED`), reason rule, adapter availability (503 `PROVIDER_UNAVAILABLE`), then the intent. A foreign actor, a wrong role and a wrong state never see 503 (tested with the adapters absent). A replay precedes every state check and answers the stored result (the generation row's current state). The reason is required once an accepted row exists and refused on the first request (400 `INVALID_REQUEST` with `field_errors [{quality_reason_code, REQUIRED|NOT_ALLOWED}]`; strictness is our reading of l.1670 "khi tạo lại").
- T-1a-DEC-2 (saga, D2/D3; l.395, l.597, BR-38): Tx1 commits the intent row, the `PENDING` receipt and the run in `VIDEO_ADMISSION_PENDING` (revision and version +1; the active lock is kept, wait start cleared). With no transaction open the service calls reserve then admit (worker thread, per-call timeout; an exception or a timeout is read as `UNAVAILABLE`), both keyed by the stored key hash with `request_ref` = generation id. Tx2 locks run then generation and compares-and-sets on `ADMISSION_PENDING`: `ACCEPTED` (generation number, both refs, `job_ref`, scenes copied from the pinned revision, run `VIDEO_QUEUED`, `job_state QUEUED`) or `ADMISSION_REJECTED` (run back to `SCRIPT_REVIEW` with a new adult-wait start, pointer back to the last accepted row), then `release` outside any transaction and `compute_released_at` recorded; a release that answers `UNAVAILABLE` keeps the reservation ref for the reconciler (`pending_compute_closures`). `UNAVAILABLE` leaves the intent pending and answers 202 `ADMISSION_PENDING`; no timer rejects an intent. `IDEMPOTENCY_MISMATCH` maps to 400 `INVALID_IDEMPOTENCY_KEY` and leaves the intent pending. `reconcile_pending_admissions(limit, run_id=None)` re-calls both ports with the same key; no scheduler exists in v3b (periodic runner slice, D-066-73 PD-9a): nothing calls it in production yet.
- T-1a-DEC-3 (D9, Q2): the generation row is the durable job record; no `ai_jobs` row. - T-1a-DEC-4 (jobs projection, D10): `GET /v1/jobs/{job_id}` reads a generation through `SqlParentVideoJobs` (one query by `job_ref` joined to the run's owner scope `actor_scope_ref`; works for `COMPLETED`, `FAILED`, `ABANDONED` runs whose lock column is NULL; a run in `DELETE_PENDING` or purged answers not found; an intent or a refused request has no job).
