- T-2b-DEC-3 (request, keys, replay, purged runs, T2B-D3; l.1664, l.1697, l.1699, DTR 6.5, l.1472): `Idempotency-Key` is required and parsed by `parse_idempotency_key` after the role check and before the run lookup. Receipt operation `ATTACH_ASSET`, scope `STORY_RUN/{id}`, fingerprint over `{asset_ref, expected_run_revision}`, stored body = the four outcome fields (the 202 body without `request_id`, which is new on a replay). Another body with the same key is 400 `INVALID_IDEMPOTENCY_KEY`. A replay re-authorizes (owner-scoped lookup first) and returns the stored 202 without a second write; a replay on a purged run returns the content-free lifecycle projection under the same 202 (union response model), even when the replay body differs; a fresh command on `DELETE_PENDING` or `DELETED` is 409 `INVALID_STATE_TRANSITION`. `expected_run_revision` is optional (l.1664 lists none); a sent value that differs is 409 `STALE_REVISION` with `current_version` = the run revision.
- T-2b-DEC-4 (state rule and retake, T2B-D4; FR-P-02 l.511, FR-P-12 l.521, l.394): first drawing = `INPUT_PROCESSING` with no drawing attached. One retake: exactly one drawing attached and either the run is in `SUBJECT_REVIEW`, or it is in `INPUT_PROCESSING` with `job_state = 'FAILED'` and `retryable` true (the recoverable failure of DEC-7). `ensure_accepting_artwork` uses the same predicate, so the upload for a retake can be created (a run with a drawing in `QUEUED` or `RUNNING` accepts no second drawing, not even an upload). Any other state, a second retake or the same asset again (another key) is 409 `INVALID_STATE_TRANSITION`. A retake writes input revision N+1 with every column copied forward except the drawing columns (`_next_input_values`; typed idea, context snapshot and its confirmation, lesson pin, and any column added later such as T-2c's voice fields), returns the run to `INPUT_PROCESSING` with `job_state QUEUED`, and clears the replaced understanding from the run row (subject, confidence, revision, hashes); older inputs and understandings stay as history, and `get_run` reports a candidate only when the latest understanding belongs to the current input (small change outside the plan allowlist wording, recorded). Assumption recorded (Q-2b-1, FR-P-12): the retake is capped at one but not limited to a topic mismatch, because the mismatch warning has no client field yet. T-2c moves the failure and retake state from `INPUT_PROCESSING/FAILED` to `INPUT_REVIEW` (l.394) and updates the predicate.
- T-2b-DEC-5 (normalization, T2B-D5; l.983, l.1942, l.1943): the stored original is read through `ObjectStoragePort`; its size and SHA-256 are recomputed against the upload record (mismatch 422 `UPLOAD_CHECKSUM_MISMATCH`, missing object 422 `UPLOAD_INCOMPLETE`, storage fault 503 `STORAGE_UNAVAILABLE`). Pillow reads the dimensions lazily first; more than 40,000,000 pixels is 422 `IMAGE_DIMENSIONS_EXCEEDED` before any decode; Pillow's bomb error and its bomb warning (turned into an error for the call only) map to the same code; `Image.MAX_IMAGE_PIXELS` is never written (a test pins it). An undecodable, truncated or type-mismatched stream is 422 `UPLOAD_CONTENT_MISMATCH`. Derived asset: EXIF orientation applied, transparency composited on white, RGB PNG, scaled down (never up) to at most 2,000,000 pixels; if the PNG exceeds 5,000,000 bytes three further reductions are tried (1,200,000, 700,000, 400,000 pixels), then 422 `IMAGE_DIMENSIONS_EXCEEDED` (documented: the decoded image cannot be encoded within the normalized limit). The original is never resized or rewritten. WebP, JPEG and PNG are accepted. Lineage `transform_version` is `PILLOW_RGB_PNG_V2` (white compositing differs from the legacy V1 path).
- T-2b-DEC-6 (persistence and concurrency, T2B-D6; FR-C-08, l.1692): `attach_uploaded_drawing` takes the run row `FOR UPDATE` and the idempotency advisory lock, then checks replay, purged state, revision, slot and "same asset already attached" before any `put_object`; only then it puts the derived object and writes the derived asset row (`parent/{run}/{token}/normalized.png`, same token as the original, Parent scope, `source_refs [run]`, `derived_from_ref` = original key), one `core_asset_lineage` row (scanner identity digest through `scanner_identity_sha256`, T-2a-DEC-7), the new input revision, the run update (`job_state QUEUED`, version and revision +1) and the receipt in one commit. The original asset row is untouched. After a failed commit the derived object is deleted only when no `core_asset_metadata` row references its key after the rollback (R1 B2). A request that loses a race returns 409 before touching storage (tested: three rounds, one 202 and one 409, one put of the derived key, the winner's object readable and never deleted). Purge: both assets carry `source_refs [run]`; a test proves the plan removes both assets, the lineage row and the objects.
- T-2b-DEC-7 (VLM step behind a port, T2B-D7; OD-13, l.394, l.871, FR-P-04): `DrawingAnalyzerPort.analyze(request) -> result` (subject, up to four features, confidence, `child_count`, `topic_compatible`). `app.state.drawing_analyzer` defaults to `None`: the run then waits in `INPUT_PROCESSING`/`QUEUED` with no timeout or reaper (the user can cancel; OD-13 owns the real worker). An unknown outcome goes to `AWAITING_RECONCILIATION`, never to a retake. The 422 for multi-child is the job's outcome, not this route's synchronous answer (l.1664 returns only asset ref and validation state). No Modal call is added.
