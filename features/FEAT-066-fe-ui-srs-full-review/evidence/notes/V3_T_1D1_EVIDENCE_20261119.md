- T-1d1-DEC-4 (concurrency): `FOR UPDATE SKIP LOCKED` on the run, re-check under the lock, compare-and-set on the locked revision and state; idempotent; two concurrent workers close each run exactly once; a live command (cancel) holding the row makes the sweep skip without waiting, and a later real `cancel_run` wins.

- T-1d1-DEC-6 (entry point; BR-34): `run_once(now=None, batch_size=50)` with `now` as the test hook, returns counts only; a failing row or listing is counted and does not stop the batch; only `PARENT_ACCOUNT` rows are read; logs carry counts only (a unit test pins that no run id or state appears). **Nothing schedules the sweep yet**: the periodic runner slice (D-066-73 PD-9a) must call `run_once` (or `build_story_run_closeout(session, adapters).run_once()`); recorded, not built. - Debt for T-2d-fix (not built): a lost ASR or VLM job (a `PENDING` transcript, or an `INPUT_PROCESSING` run with a stuck job state) is never closed by this sweep; it stays open until the reaper exists.

Timestamps written by `advance` (`completed_at`, `finished_at`) use the real clock, so only the selection is on the injected instant.
- First sweep after deployment may close many old synthetic runs at once (backfill of wait columns used `updated_at`; OD-06 synthetic-only); recorded.
- Hot files: none touched. Possible overlap with T-1c: none in code; T-1c must not write `story.runs` (any write bumps `updated_at` and resets the idle clock) when it issues a playback token, which its plan already says it does not.
- FE impact: a run can become `COMPLETED` or `ABANDONED` without a command; a `FAILED` run may carry `error_code` `VIDEO_DEADLINE_EXCEEDED`; a stale write on a closed run is 409 `INVALID_STATE_TRANSITION`.
