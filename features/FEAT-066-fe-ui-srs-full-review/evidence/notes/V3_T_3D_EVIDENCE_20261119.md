## 2. Decisions (T-3d-DEC-n, SRS-cited)

- T-3d-DEC-1 (create route and request; l.1659, l.775, l.547, FR-T-08, REG l.355): `POST /v1/lesson-occurrences/{occurrence_id}/plan-revisions`, keyed. Body (`extra=forbid`, strict, no whitespace stripping): `expected_head_revision_no` (0 when no plan revision exists), optional `document_revision_ref {document_id, revision_no}`, `objectives`, `teacher_direction`, optional `safety_notes`, `activities`. **There is no lesson pin field**: the plan copies the occurrence's exact pin (`source_lesson_*`), so it can never differ or retarget, and no `latest` alias exists anywhere (a contract test scans the paths). The revision is always a `DRAFT`, `revision_no = head + 1`, immutable (DDL-A triggers). Identical content to the head is allowed and is a new revision with the same hash (the SRS sets no uniqueness; the fence `expected_head_revision_no` orders them).
- T-3d-DEC-2 (limits, plan review F-03; technical, not SRS numbers): objectives 1-12 strings of 1-1000 characters, `teacher_direction` 1-2000, `safety_notes` up to 2000 (blank is stored as NULL), activities 0-24 (equal to the Lesson Library, so a whole library lesson can be copied), `CUSTOM` title 1-160 (an API-only limit equal to the library activity title: the DDL-A column `custom_title` is 200 characters, so the limit can be raised without a migration) and description 1-4000 (the DDL-A check). Published as `maxItems`, `maxLength` and `minimum` in the OpenAPI schema (a contract test asserts them). Zero activities is allowed (FR-T-10 pins an activity only "nếu có preset"). Texts are stored exactly as sent (no strip, no normalisation); a NUL or a lone surrogate is `INVALID_FORMAT`, a blank required text is `EMPTY` (400 `INVALID_REQUEST` with `field_errors`, never 422, never echoed). The schema layer already refuses a lone surrogate sent as JSON; the service guard is a second layer and a unit test covers it.
- T-3d-DEC-3 (safety checklist, **BLOCKED_OPEN** content; l.548 FR-T-09, l.1660, l.1708, l.2189; plan review F-02 and the coordinator ruling): the SRS requires a checklist for every Teacher-written activity and gives no item, wording or version, so none is invented. `PRODUCTION_REGISTRY` is a frozen empty constant (`ChecklistRegistry()`); no module defines an item (a unit test reads the module source). Consequences: (1) a `CUSTOM` activity is refused **at plan create** with 400 `INVALID_REQUEST` and the field error `{"field": "activities[i].kind", "code": "NOT_SUPPORTED"}`, so the Teacher never owns an immutable draft that can never be approved; (2) the same refusal at confirm for any plan that nevertheless holds one (defence in depth; the confirm request has no `activities` array, so there the path is `checklist[<activity order>]`); (3) `CATALOG` is refused the same way (TD-16); (4) every plan with `LESSON` activities or none is created and confirmed normally. The new code `NOT_SUPPORTED` was added to the closed `FIELD_ERROR_CODES` (unit test: it survives `safe_field_errors`, an unknown code is still dropped). The gate itself (`evaluate_checklist`) is complete and tested with a definition that exists only in test code and is injected through a dependency override (`get_checklist_registry`) or the service constructor; production wiring returns `PRODUCTION_REGISTRY` and the module cannot be populated by an import. Assumption until the owner answers: every item of a definition is required (the SRS names no optional item). The DB trigger `LESSON_PLAN_CHECKLIST_REQUIRED` stays the backstop and is mapped to 409 `INVALID_STATE_TRANSITION`, never a 500.
- T-3d-DEC-4 (plan hash; l.1660 "expected plan hash", l.1699): `content_hash = sha256(canonical_json({occurrence_id, document: {document_revision_id, text_hash} | null, objectives, teacher_direction, safety_notes, lesson_ref: {lesson_id, version_id, version_no, content_hash} | null, activities: [{order, kind, catalog_activity_ref, activity_version, title, description, snapshot_hash}]}))` with the Lesson Library algorithm (`json.dumps(ensure_ascii=False, sort_keys=True, separators=(",", ":"))`, UTF-8, SHA-256; a unit test pins equality with `canonical_content_hash`). Excluded: revision id and number, timestamps, state, checklist results (a unit test pins the input names). Every approved field changes the hash (a parametrised test); NFC and NFD forms differ (no normalisation).
- T-3d-DEC-5 (head fence and serialisation; l.1659, l.1699): authorise with no lock (scope first, 404 or 403), then re-select the occurrence row `FOR UPDATE` and decide again (an unauthorised caller never takes a lock; T-3c review P3-2), replay a stored receipt, refuse `ARCHIVED` (409 `INVALID_STATE_TRANSITION`), compare `expected_head_revision_no` with `max(revision_no)`: a difference is 409 `STALE_REVISION` with `current_version` (an integer, 0 when no plan exists) and the head's `ETag`, nothing written. The occurrence lock serialises create and confirm, so two creates from one head make one 201 and one 409, and lock order is occurrence then the rows of this task (T-3b locks occurrence then session; T-3c occurrence share then document), no cycle.
- T-3d-DEC-6 (activities; FR-T-08, FR-T-09 l.548, REG l.356, plan review F-04): `LESSON` `{lesson_activity_id}` copies an activity of the occurrence's **pinned** version into `activity_snapshot` with its `canonical_hash` as `activity_snapshot_hash`, `catalog_activity_ref` = the library activity id, `activity_version` = the pinned version number. An id of another version is `activities[i].lesson_activity_id` `INVALID_FORMAT`; an occurrence with no pin refuses `LESSON` (`activities[i].kind` `NOT_SUPPORTED`). Integrity (library rows have no immutability trigger): before copying, the pinned version must still be eligible (same organization, `ACTIVE` and `VISIBLE` lesson the caller may see by the T-3a rule, `APPROVED` version: else 409 `INVALID_STATE_TRANSITION`) and the full-content hash is recomputed (`canonical_content_hash` over `content_json` plus the ordered `activity_json` rows); a difference from the occurrence pin or from the stored version hash is 409 `STALE_REVISION` (no `current_version`: reloading the plan does not help). The check runs only when a `LESSON` activity is requested, so a plan that copies nothing does not depend on the library. `CUSTOM` is Teacher-written (title and description) and exists only in this plan.
- T-3d-DEC-7 (confirm; l.1660, l.775, l.1699, plan review F-01 and ruling, F-08): `POST .../plan-revisions/{revision_no}/confirm`, keyed, body `{expected_plan_hash, checklist: [{activity_order, checklist_version, items: [{item_id, checked}]}]}`. **Only the head revision can be confirmed**: any other revision is 409 `STALE_REVISION` with `current_version` = the head number and the head's `ETag`; a confirm of an older draft can therefore never overwrite a newer approval (SRS l.1699). To reuse old content the Teacher writes a new revision. Precedence under the occurrence lock: 404 (scope), 403 (role), receipt replay, `ARCHIVED` 409, plan row 404, state (`APPROVED` with the same hash is 200 and writes only a receipt; `APPROVED` with another hash 409 `STALE_REVISION`; `SUPERSEDED` 409 `INVALID_STATE_TRANSITION` whatever the body says), head 409, hash 409, then the 400 checklist gate. Nothing is written unless every check passes.
- T-3d-DEC-8 (what confirm writes, one transaction; l.775, l.1442, l.2688-2700 §31.8.2, T-3c hand-over): (1) the checklist columns of every `CUSTOM` activity (`safety_checklist_version`, `checklist_result` `{"items": [...]}`, `confirmed_by`, `confirmed_at`); (2) the previous `APPROVED` plan becomes `SUPERSEDED` with `superseded_at` **before** (3) this plan becomes `APPROVED` with `approved_by` and `approved_at` (the partial unique index forbids the reverse order); (4) the referenced document revision gets the one-way `CONFIRMED` stamp (`reviewed_by`, `reviewed_at`) if it is still `NEEDS_REVIEW` (UC-04: the Teacher approved the text this plan pins; an already confirmed revision keeps its first stamp); (5) the occurrence gets `approved_plan_revision_id`, state `APPROVED` (only from `DRAFT`, `DOCUMENT_REVIEW` or `PLAN_REVIEW`; a later state keeps its state and changes only the pointer) and `revision + 1` (its strong ETag changes); (6) audit entry `lesson.plan.confirm` and the receipt. Supersession only marks the old plan: no run, job or deck exists in v3, so the §31.8.2 cancellation and fencing rows are vacuous and WP-4 must read `approved_plan_revision_id` and the pins from this schema. `LESSON_PLAN_NOT_APPROVED` is returned by no T-3 route (a contract test scans the sources).
- T-3d-DEC-9 (keys, receipts, replay; l.1696-1699, plan review F-05): both commands need `Idempotency-Key`. Receipts in `be1_command_receipts` (scope `POST /v1/lesson-occurrences/{id}/plan-revisions` and `.../{n}/confirm`, so another occurrence or revision is another command), fingerprints over the canonical request (confirm: order-free over entries and items). A receipt keeps the **first response body** (small: a plan holds no document text) and a replay returns it verbatim with its original status after re-authorisation, so a replay after the plan was confirmed or superseded still shows the first answer (tests). Another payload with the key is 400 `INVALID_IDEMPOTENCY_KEY`; refusals write no receipt; a revoked Teacher cannot replay (404). The no-op confirm of an approved plan keeps a receipt and writes no audit entry.
- T-3d-DEC-10 (scope; l.864-865, T-3a-DEC-2/3): the responsible Teacher only writes (`authorize_occurrence(write=True)`); out of scope or unknown, School Manager (also one who teaches another class), Parent, Platform Admin, revoked or disabled: one identical 404 (the same body as an unknown occurrence); a second Teacher row of the class, guide, observer and a mixed account: 403 `ACTION_NOT_ALLOWED`; `TEACHER_ASSIGNMENT_REQUIRED` stays a create-only answer of T-3a. Reads need any covering teacher-family row (T-3a read guard, still the open owner question of T-3a F-03). The request rules (400) run before authorisation, as in T-3c, so a stranger with a bad body learns the rule and nothing about the occurrence.
- T-3d-DEC-11 (request size guard; T-3c review P3-4/P3-5, plan review): the T-3c guard was generalised, not copied: one table of `(method, anchored path, limit, message)` in the existing middleware; the plan create is capped at 1 MiB (worst case about 120,000 characters at 6 bytes once JSON-escaped is 0.7 MiB) and the confirm at 256 KiB (24 entries of 64 items is about 150 KB). Over the cap by `Content-Length` or by streamed bytes is 413 `MEDIA_TOO_LARGE` in the CONV-1 envelope before FastAPI reads, parses, validates or authorises anything. The caps are published in the OpenAPI descriptions. The two older JSON routes under `/v1/lesson-occurrences` (create, attach) still have no cap (debt, section 5).
- T-3d-DEC-12 (reads and ETags; TD-05, l.798 gives no shape): `GET .../plan-revisions?limit=&cursor=` (25 default, 100 maximum, `revision_no` descending, cursor on the number, no ETag), `GET .../plan-revisions/{revision_no}` with the strong `ETag "<content_hash>.<state>"` (content is immutable but the state changes at confirm; 304 only after authorisation). The head is the first list item; there is no `latest`. `supersedes_revision_no` is set only in the confirm response (it is null in reads).
- T-3d-DEC-13 (document reference; UC-04 l.1442, REG l.355, plan review F-06): `document_revision_ref` is optional (REG: the foreign key is optional), so an occurrence with uploaded documents can be approved with no reference (owner decision OPEN). A given reference must be a revision of a non-`DELETED` document of this occurrence: otherwise 404 `RESOURCE_NOT_FOUND` with the same body as an unknown occurrence. The `CONFIRMED` stamp applies to the referenced revision only; revisions added later by T-3c stay `NEEDS_REVIEW`, and a later edit never moves an approved plan (a plan pins `document_revision_id`).
- T-3d-DEC-14 (errors; DDL-A R3): a database fault is never a 500: a unique violation (23505) means "someone else won" (stored replay, else stale 409), any other integrity or database failure is 503 `PROVIDER_UNAVAILABLE`, and the checklist trigger is 409 `INVALID_STATE_TRANSITION` (a unit test pins the mapping). No capacity or billing code exists (`CLASS_CAPACITY_REACHED` is absent, tested).
- T-3d-DEC-15 (OpenAPI; ruling as T-3b/T-3c): the four operations are in the contract catalogue and served, and are not added to `SRS_V22_INCLUDED_OPERATIONS` (the FE-projected spec); a contract test pins that.
