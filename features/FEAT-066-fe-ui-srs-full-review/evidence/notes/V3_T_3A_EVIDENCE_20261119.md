Amendments A1-A3 of the plan review (all additive, no new table or column beyond Draft 1 section 4):

- A2: `protect_plan_revision` INSERT: draft only with empty approval columns, pin equal to the occurrence's, document revision of the same occurrence and not `DELETED`, number = head + 1, objectives typed and bounded. UPDATE: content immutable, `DRAFT -> APPROVED` (fails `LESSON_PLAN_CHECKLIST_REQUIRED` while a `CUSTOM` activity is unconfirmed), `APPROVED -> SUPERSEDED`, nothing else. `uq_plan_one_approved` (SRS l.775).
- A3 (F-06): lengths (`VARCHAR(36)` for account refs), `server_default now()` for the timestamps, value CHECKs written in `CASE` form so a jsonb function never raises, SHA-256 hex CHECKs, per-kind activity rules, born-state triggers on `source_documents` (`EXTRACTED`) and `document_revisions` (`NEEDS_REVIEW`), `ARCHIVED`/`DELETED` documented as reserved (tests set them by SQL), `catalog_activity_ref` documented as the library `activity_id` for `LESSON` activities. Open design points kept for the implementer of T-3d (service rules, not DDL): the pointer and the single `APPROVED` plan can only diverge through a service bug (the confirm order is supersede, approve, set pointer in one transaction); a divergence check is not in DDL-A.

## 3. Decisions (T-3a-DEC-n, SRS-cited)

- T-3a-DEC-1 (path and family; l.1652, l.798, TD-01, C-D9): literal `/v1/lesson-occurrences`, mounted unconditionally (the StoryRun-lite demo has no occurrence path; a contract test proves demo bodies stay unchanged with the demo on). The CONV-1 envelope applies by whole path segment (`/v1/lesson-occurrencesfoo` is outside the family).
- T-3a-DEC-2 (Teacher assignment table; l.1652 "Teacher được phân công", l.775 "Class, Teacher phụ trách hiện tại", l.864-866; review F-01): (1) class unknown, or the caller has no valid Teacher identity (active, `account_role teacher`, issuer equals the token's) or no active teacher-family row in the class's organization: uniform 404 `RESOURCE_NOT_FOUND`, the same body for every such case; (2) among the caller's rows with `class_id` equal to this class: a `teacher` row proceeds, only `guide`/`observer`: 403 `ACTION_NOT_ALLOWED`, none: **409 `TEACHER_ASSIGNMENT_REQUIRED`** (reachable for a Teacher of the organization who covers another class or holds only an organization-wide row); (3) after the receipt replay, a class whose `state` is not `active`: 409 `INVALID_STATE_TRANSITION`. A row with `class_id` NULL (organization-wide) counts for reads (the BE1 convention of `require_assignment`) and does not count for create: l.775 is a per-class assignment and M9-B writes class-scoped teacher rows. Recorded: a Teacher of the organization can tell an existing class from an unknown id (accepted by the source plan, in scope).
- T-3a-DEC-3 (existing occurrences; l.864-865, C-D4, CV-5): read needs any active teacher-family row covering the class (organization-wide rows included); stranger, other organization, revoked or inactive assignment, School Manager, Parent, unknown id and an id over 36 characters all answer one identical 404. A write (T-3b..T-3d, `authorize_occurrence(..., write=True)`, also the upload resolver) needs the `teacher` role and `responsible_teacher_ref` equal to the caller's account (403 otherwise). The Teacher replaced on a class loses access; the new Teacher of the class reads it (a deviation from Draft 1 OQ-2's "nobody until transfer" default, recorded: UC-12/T-6b owns the transfer; the new Teacher cannot write).
- T-3a-DEC-4 (refs and consistency; REG l.352): `responsible_teacher_ref` and `created_by` are `be1_adult_identities.account_id`; `organization_ref` and `class_ref` are opaque strings with no cross-owner foreign key; the class row is read `FOR SHARE` in the create transaction so a concurrent class change waits.
- T-3a-DEC-5 (capacity deviation; l.1652 "xác minh sức chứa/phân công"): the phrase asks for a capacity check. Capacity belongs to X-13 (Billing, deferred, R3), so `CLASS_CAPACITY_REACHED` is never returned in v3 (a unit test asserts the code is absent). No capacity or billing code was written.
- T-3a-DEC-6 (lesson pin; l.547, l.2563; review F-04, F-05): the request field is `lesson_version_ref` of the typed `LessonVersionRefV1 {lesson_id, version_id, content_sha256}`, field for field and strictness for strictness the Parent flow's `ParentLessonVersionRefV1` (a unit test compares the JSON schema, the config and a serialisation). `version_no` is stored (`source_lesson_version_no`) for lineage and returned as the display field `lesson_version_no`; it is not part of the ref. Eligibility is fail-closed: same organization as the class, library item `ACTIVE` and `VISIBLE`, visible to the caller by the `get_lesson` rule (creator or not `PRIVATE`), version `review_state APPROVED`. Not visible (unknown, other organization, hidden, archived, private of another author, a version of another lesson): 404; visible but a different hash: 409 `STALE_REVISION`; visible with the right hash but not approved: 409 `INVALID_STATE_TRANSITION`. Never `latest`; stored exact; a replay never re-runs the check. OQ-3 stays open for the owner (draft pins, library grants, other organizations); a looser rule later never invalidates stored pins.
- T-3a-DEC-7 (keys, receipts, audit; l.1696-1697, C-D5, C-D6; review F-08): `Idempotency-Key` 1-128 visible ASCII, one header (`parse_idempotency_key`); receipts in `be1_command_receipts` (scope `POST /v1/lesson-occurrences`, principal, key; organization set; SHA-256 of the canonical request: class, trimmed title, date text, the three pin fields). The success body (small, no child or storage data, no organization) is stored in `response_json` and replayed verbatim with status 201, `Location` and `ETag "1"`; another payload with the key is 400 `INVALID_IDEMPOTENCY_KEY`; refusals write no receipt; a concurrent same-key create loses the primary-key race, rolls back and replays. A different key with an identical body creates a second occurrence (no SRS uniqueness). Audit entry `lesson.occurrence.create` (actor = account ref, organization, no title or child data).
- T-3a-DEC-8 (revisions and ETags; l.1699, C-D7): `revision` starts at 1 and the service bumps it on every state or approved-plan change (T-3b..T-3d). The single read carries the strong `ETag "<revision>"` and `Cache-Control: private, no-cache`; a matching `If-None-Match` gives 304 only after authorisation (a stranger gets 404, never 304). The list carries no ETag. There is no PATCH in v3 (the SRS has none).
- T-3a-DEC-9 (upload carrier; l.1654, T-2a-DEC-13): the resolver for `OCCURRENCE_DOCUMENT` is registered here, not left to T-3b: only the responsible Teacher (write rule) resolves; the scope is the organization with prefix `occurrences/{organization}/{occurrence}/`; an `ARCHIVED` occurrence answers 409 `INVALID_STATE_TRANSITION` at session create. Guide, observer, a second Teacher of the class, other organizations and unknown ids get the uniform 404 (proved through the real `POST /v1/upload-sessions`).
- T-3a-DEC-10 (list boundary; l.798, Draft 1 T3A-D9): `GET /v1/lesson-occurrences?class_id=` is an occurrence-state list of one class (newest first on `(created_at, occurrence_id)`, the tuple compared in the cursor, so equal timestamps page without gap or repeat), not the X-17 run history; `limit` default 25, maximum 100 (101 is 400), `state` filter, opaque cursor (malformed: 400 on `cursor`). A class the caller does not cover answers the unknown-class 404. OQ-1 stays open: if the owner rules any occurrence list is X-17, drop this route; the single GET stays.
- T-3a-DEC-11 (read shapes; TD-05, l.798 gives no shape): `LessonOccurrenceV1 {contract, occurrence_id, class_id, title, scheduled_date, state, revision, responsible_teacher_ref, lesson_version_ref, lesson_version_no, approved_plan {revision_no, plan_hash, approved_at}, sample_video {slot_state, claimed_at, run_ref}, created_at}`; no organization id, storage word or child field (tests scan bodies, receipts and the OpenAPI schemas). `approved_plan` is read through the pointer, so T-3d only has to set it. The sample fields stay `AVAILABLE`/null until WP-4b (l.1708).
- T-3a-DEC-12 (validation; C-D3): every refusal of the body or the query is 400 `INVALID_REQUEST` with `field_errors` (never 422); unknown fields (`organization_id`, owner, Teacher, state, revision) are `UNKNOWN_FIELD` (l.1637); the title is trimmed, 1-200 characters, no control character or lone surrogate; `scheduled_date` is an ISO calendar date only.
