## 2. Decisions (T-3b-DEC-n, SRS-cited)

- T-3b-DEC-1 (route, request and handle; l.1653, l.1637, l.1692; plan review F-01, coordinator ruling 1): `POST /v1/lesson-occurrences/{id}/documents` takes one field, `asset_ref`, and `Idempotency-Key`. T-2a returns the opaque handle `upl_{upload_id}`; the object key stays in `core_upload_sessions.final_asset_ref` and `core_asset_metadata`. Only the `upl_` form passes validation (anything else, including an object key, is 400 `INVALID_FORMAT` and is not echoed). The server finds the session by id, then calls `resolve_asset_key` (T-2a) for the key and requires the same key as the session. Organization, owner, file name, hash and type are server-derived; extra body fields are `UNKNOWN_FIELD`.
- T-3b-DEC-2 (TD-15 and the parse deviation; l.779, l.806, l.1653, l.1940-1941, l.1936-1938; plan review F-03): the job row is written already terminal, in the attach transaction, with no outbox row, no queue message, no semantic request and no command receipt in `ai_jobs`. **Deviation from SRS l.1941** ("parser in a resource-limited worker, no arbitrary outbound network") and from the processing-time limit of l.1936-1938: the parse runs in a bounded thread of the API process, like the library's `complete_upload` at HEAD. Mitigations: the 25,000,000 byte cap and the ZIP guards of the parser (2,048 entries, 100 MiB expanded, ratio 100, encrypted flag, path traversal), a parse deadline (30 s, `ParseGate`), a process-wide concurrency cap (2 parses, 5 s wait, then 503 `PROVIDER_UNAVAILABLE` with `Retry-After: 5`), and no row lock or database connection held during storage or parser work. `pypdf`, `python-docx` and `python-pptx` do not fetch anything, but outbound network is not blocked at operating-system level. Known limits: a Python thread cannot be killed, so a runaway parse keeps its slot until it returns (the cap bounds the number of runaways; the service closes the file on a timeout, which ends a parser that is still reading it); the cap is per process, not per fleet. Moving the parse to a worker with CPU, memory and network limits is the way to close the deviation.
- T-3b-DEC-3 (which asset, verification, no second scan; l.1653 "upload session đã hoàn tất", "source hash do server xác minh", l.1934, l.940): the session must be `OCCURRENCE_DOCUMENT`, target equal to this occurrence, owner equal to the caller, scope `ORGANIZATION` of the occurrence's organization, state `COMPLETED` and scan verdict `CLEAN`. Anything else (another actor's, another occurrence's, another organization's, unscanned, `ERROR`/`INFECTED`, failed, still open, unknown handle) is one identical 404. The object is read through the storage port, size and SHA-256 are recomputed and compared with the session size and `core_asset_metadata.content_sha256`: over 25,000,000 bytes 413 `LESSON_FILE_TOO_LARGE`; any difference 422 `UPLOAD_CHECKSUM_MISMATCH`; missing object 422 `UPLOAD_INCOMPLETE`; storage fault 503 `STORAGE_UNAVAILABLE`. There is no second AV scan: T-2a scanned the same bytes and recorded the verdict, and the hash re-check proves the bytes are the scanned ones (a test counts scanner calls). T-3b never writes a verdict. The file extension (from the stored safe name) must map to the asset's media type and the parser's detected type must equal it, else 415 `UNSUPPORTED_LESSON_TYPE`.
- T-3b-DEC-4 (parser reuse and text; l.545, FR-T-06, UC-04; plan review F-02, F-06): the same `DeterministicLessonDocumentParser` instance (`app.state.lesson_document_parser`). The extraction now carries the full text. The parser normalises it before its size check and hash: NUL and the other control characters (except tab, line feed, carriage return) are removed, lone surrogates become U+FFFD, so neither can reach `str.encode` or PostgreSQL `TEXT` as a 500. The stored text and its hash are the normalised string (the database CHECK computes the same SHA-256 of the UTF-8 bytes). The service refuses text that is still not storable (NUL, surrogate, empty, over 2 MiB of UTF-8) as 400 `INVALID_FILE_CONTENT`, with no row. The library service ignores the new field; its `extracted_fields` come from the normalised text, so a stray control character no longer reaches them either.
- T-3b-DEC-5 (refusals are synchronous and write nothing; §9.8 l.862-873, UC-04 l.1437): every parser or check rejection is answered on the request before any row exists, so the Teacher replaces the file with a new upload (the refused asset stays a `COMPLETED` session and an asset row until the upload and asset lifecycle purges them). Mapping: `UNSUPPORTED_MEDIA_TYPE` 415 `UNSUPPORTED_LESSON_TYPE`; `OCR_NOT_SUPPORTED` 422 `OCR_NOT_SUPPORTED` (the library maps it to 415; new routes follow §9.8); `INVALID_SOURCE_DOCUMENT` and `DOCUMENT_EXPANSION_LIMIT_EXCEEDED` 400 `INVALID_FILE_CONTENT`; a parse over the deadline 400 `INVALID_FILE_CONTENT`; an unexpected parser fault 400 `INVALID_FILE_CONTENT` (never a 500, never echoed); `ENCRYPTED_DOCUMENT_UNSUPPORTED`, `DOCUMENT_PAGE_LIMIT_EXCEEDED`, `DOCUMENT_TEXT_LIMIT_EXCEEDED` 422 with their own codes. **These three codes are outside §9.8** (the SRS asks for "safe stable codes", l.1437, and names none for encryption or limits); they are kept as technical decisions, the owner may rename them. Anything else the parser might one day raise fails closed as 400 `INVALID_FILE_CONTENT`. The library route answers `ENCRYPTED_DOCUMENT_UNSUPPORTED` and `OCR_NOT_SUPPORTED` with 415 while this route answers 422 for both; clients key on `code`, not on the status.
- T-3b-DEC-6 (parser limits as they are; l.545, l.1437; plan review F-06): a document with some text and some scan or blank pages is accepted with the warning `OCR_NOT_SUPPORTED_PAGES` plus `page_coverage` (the pages that have text); the warning is derived by the service from the page count and the coverage, because the parser only reports pages with text. Only a document with no text at all is refused (`OCR_NOT_SUPPORTED`). A DOCX has no page count at HEAD (`page_or_slide_count` NULL, coverage `[1]` or `[]`), so the 100 page or slide limit is enforced for PDF and PPTX only; recorded as a known limitation (SRS l.545 and l.1437 cannot be enforced for DOCX with this parser).
- T-3b-DEC-7 (the job; l.779, l.806, l.1653): one `ai_jobs.job` row (type `lesson_source_document_extraction`, target `LESSON_SOURCE_DOCUMENT`, target id the document, organization of the occurrence, `session_id` NULL, purpose `LESSON_SOURCE_EXTRACTION`, request ref `request_id` document id, `request_revision` 1, `input_hash` the asset SHA-256) with history `created, started, succeeded:accepted`, `job_revision` 3, one attempt started and finished at one instant, one result ref (`lesson-document-revision:<revision id>`, the text hash, provenance `parser:<name>@<version>`). `succeeded` and `accepted` mean "text extracted", never "plan approved" (UC-04: the review of the text is a separate resource; the revision starts `NEEDS_REVIEW`). The row id is `source_documents.extraction_job_ref`. Policy `lesson.inline.v1` has `max_attempts` 1 and status `INLINE_NO_RETRY` (not the fixture status `PROPOSED`), so no retry exists. The reconciler queries (`queued_dispatched_not_started`, `overdue_running`, `due_retries`, `has_pending_dispatch`) return nothing for it (a PostgreSQL test).
- T-3b-DEC-8 (job read rule; l.865, l.1675, T0.4-DEBT-1 and DEBT-2): `GET /v1/jobs/{job_id}` reads this kind for an actor who holds the `teacher` role for exactly the class of the document's occurrence (`ActorMembership.class_roles`, from the T0.2 loader rows; the class must be active). The rule is on the spec as `rule_grants_teacher_role`: an actor the rule accepts is read as Teacher whatever the union of organization roles says, and a School Manager who teaches another class, a guide or observer of this class, an observer of this class who teaches another, a Platform Admin, a Parent, another organization and a revoked or disabled account all get the uniform 404. A revoked assignment turns a 200 into a 404 even with an `If-None-Match`. The other teacher of the class reads the job too (T-3a-DEC-3: the Teacher who replaces the class Teacher reads). Result refs (revision id and text hash, no text, no child data) are eligible for a `succeeded` and `accepted` job of this type. DEBT-2 (latency): no constant-cost dummy membership read was added; the existing T0.4 tests pin "never for a missing job", ids are opaque and the oracle is weak, so the residual risk of T0.4 stays accepted. The registry is built per application with the SQL lookup (`routers/jobs.py`); the module default stays empty and every other job type still answers 404. Review R1 F-02 ruling: the reader also requires `account_role == teacher` for this kind, so a School Manager account that teaches the class gets the same 404 on the job as on the document routes. Any current `teacher` row of the class reads the job (not only the responsible Teacher): the document routes let the other Teacher of the class read too (T-3a-DEC-3) and BR-05 gives one Teacher per class, so the sets coincide outside a transfer.
- T-3b-DEC-9 (order, locks, keys, replay; l.1696-1699; plan review F-03, F-07): authorise (T-3a write rule: the responsible Teacher; guide, observer, a second Teacher of the class 403; outside the class 404) and read a snapshot with no lock, then replay check (receipt scope `POST /v1/lesson-occurrences/{id}/documents`, fingerprint over the occurrence id and the asset ref; another payload with the key is 400 `INVALID_IDEMPOTENCY_KEY`; a replay is re-authorised and returns the stored 202 body without reading storage or parsing), then the occurrence state (only `ARCHIVED` refuses, 409 `INVALID_STATE_TRANSITION`; a replay still answers after archive), then the session snapshot, then release the connection, read, verify, parse. The write transaction locks the occurrence row `FOR UPDATE`, then the upload session row, re-checks the receipt, the state, the session predicates and "already attached", inserts the document, revision 1, the job, the audit entry `lesson.source_document.create` (account ref, organization, no file name) and the receipt, and commits. The same asset with another key is 409 `RESOURCE_CONFLICT`; two concurrent attaches of one asset make one 202 and one 409 with no orphan row; two concurrent attaches with one key return the same 202. The occurrence row is not changed (no state change, no revision bump): `DOCUMENT_REVIEW` and `PLAN_REVIEW` are never set by a v3 route (T-3a).
- T-3b-DEC-10 (reads; TD-05, l.798 gives no shape, l.1708): `GET .../documents` (25 default, 100 maximum, `(uploaded_at desc, source_document_id desc)`, cursor with both columns, no `ETag`), `GET .../documents/{id}` (strong `ETag "<head_revision_no>"`, 304 after authorisation), `GET .../documents/{id}/revisions` (no text, `revision_no desc`, no `ETag`), `GET .../documents/{id}/revisions/{n}` (text, hash, parser, warnings, coverage; `ETag "<text_hash>.<review_state>"` because the text is immutable but the review stamp changes; 304). A document is reachable only through its own occurrence. No bucket, key, URL, scanner name, organization id or asset ref appears in a read body or a read schema (tests scan bodies, the OpenAPI and the published schemas). The read guard is the T-3a one (any teacher-family row covering the class, organization-wide rows included), so a guide or observer of the class can read the extracted text: this widens the open owner question of T-3a F-03 to the document text and is recorded in section 5.
- T-3b-DEC-11 (OpenAPI; ruling): the five operations are in the contract catalogue (`MOUNTED_OPERATIONS`) and served; they are NOT added to `SRS_V22_INCLUDED_OPERATIONS` (the FE-projected spec), and neither is the jobs route. A contract test pins that the projected spec has no `/documents` path until the FE sync task adds them.
- T-3b-DEC-12 (envelope): the new top-level codes have Vietnamese messages (section 1); `RESOURCE_CONFLICT` keeps the status message; the 503 busy answer carries `Retry-After` and `retry_after_seconds`. The "stale hash 409" of the source plan P-18a is the T-3d confirm, not this route: a changed object here is 422 `UPLOAD_CHECKSUM_MISMATCH` (§9.8 l.871).
