## 1. What changed

Backend (under `backend/src/sketch2life/interfaces/http/`):
- `routers/parent_story_runs.py`: the four keyed story commands (create run, context, subject and script confirmation) declare `Idempotency-Key` as required with `min_length=1, max_length=128` (was 256). After `_require_parent`, `parse_idempotency_key(request)` (C-D5: exactly one header, 1-128 visible ASCII) is the authority and its value goes to the service. Same order as cancel and delete.
- `app.py` (validation handler only): on `/v1/story-runs` paths a header issue on `Idempotency-Key` no longer sets `INVALID_IDEMPOTENCY_KEY` and no longer adds a `field_errors` item. It is a plain 400 `INVALID_REQUEST`, `field_errors` null when nothing else is wrong; other issues keep their `INVALID_FIELD` items. The `/api/parent/v1/ai/...` paths keep the old behaviour (T-2d owns them).
- `routers/be1_registry.py`: create class (`POST /api/be1/v1/organizations/{organization_id}/classes`) requires `Idempotency-Key` (declared 1-128, then `parse_idempotency_key`), writes a durable `be1_command_receipts` row (scope `POST /organizations/{organization_id}/classes`, fingerprint = SHA-256 of canonical `{"display_name"}`), and replays. Body gains `state` and `assignment_revision` (additive, SRS l.1635). The receipt stores `class_id`, `state`, `assignment_revision` only (no display name). Replay uses the request's `display_name` (equal to the original by fingerprint) and the stored `assignment_revision`, status 201. Re-authorisation runs before the receipt lookup. Commit uses local `IntegrityError` handling: the concurrent loser rolls back (class, audit and event rows included), re-reads the receipt and replays; no receipt found gives 409 `RESOURCE_CONFLICT`. Same key with another `display_name`: 400 `INVALID_IDEMPOTENCY_KEY`. No migration, no model change, no `Response`/ETag.
- `routers/be1_registry.py` (OQ-4 folded in): `assign_class_teacher` (C6) now also calls `parse_idempotency_key(request)` after the scope check, so a key with a space or over 128 characters, or two headers, is 400 `INVALID_REQUEST`.
- `openapi_contract.py`: create-class `request_inputs` lists the required `Idempotency-Key`; the create-class operation is added to `IDEMPOTENCY_MISMATCH_OPERATION_KEYS` (now 18). `openapi_contract_amendments.py`: example gains `state`, `assignment_revision`. Operation counts unchanged (154/135).

## 2. SRS and owner decisions

| Decision | Basis |
|---|---|
| Key semantics: scope per principal, operation and target resource; same key and payload returns the original result; other payload gives `INVALID_IDEMPOTENCY_KEY` | SRS l.1697; l.1636 (client keeps the key on retry) |
| Rule "1-128 visible ASCII; missing, empty, over-long, spaced, control, non-ASCII or repeated key is 400 `INVALID_REQUEST`" | Owner decision C-D5 (DECISIONS.md:481), not an SRS number. SRS has no length. C-D5 calls it "the existing M2 Parent rule"; in fact the four story routes were at 256 and the AI route at 200 until this task. |
| `INVALID_IDEMPOTENCY_KEY` only for payload reuse, listed under 400 | SRS §9.8 (l.862) |
| Only successful commands store a receipt | C-D6 |
| Uniform 404 outside scope, 403 only for an assigned non-admin role inside the organization | SRS l.864-865, C-D4 |
| Create class: 201 with a class reference; no `If-Match` (expected revision is for profile, lesson plan, story, script only) | SRS l.1649, l.1699 |
| Additive response fields `state`, `assignment_revision` | SRS l.1635 |
| OD-18a: key change applies to the four M2 routes because no Android dependence exists | Source plan OD-18a; Android check in plan §2 and plan review R1 (re-run, same result). Source at `.worktrees/mobile` `80fdc1a5` only; an already shipped build is not inspected. |

Rulings applied (from plan review R1 and the coordinator):
- OQ-1: `assignment_revision` is the assignment counter the next assignment call must send (`class_assignment_revision(0)` = 1). It is NOT the "expected class revision" of SRS l.1651 (TD-28 open). T-7c must not take this field as the l.1651 class revision. The word "class revision" is not used for it.
- OQ-2: the five key failures on the four story routes carry `field_errors: null`. The plan row P-04 wording "with `field_errors`" is deliberately not followed (Contract Draft 11/12 §3.6 N-1: errors from `parse_idempotency_key` carry null; cancel and delete already answer null). Create class stays in the CONV-1 family: its key errors carry the list `[{field: Idempotency-Key, code: ...}]`. Messages differ: a missing key (validation handler) says "Yêu cầu không khớp với hợp đồng API.", a spaced key (HTTP-exception handler) says "Yêu cầu không hợp lệ."; tests assert `code` only.
- OQ-3 (parked, numbered debt DEBT-T01-1): the 400 for key reuse with another payload is covered by the existing sequential repository tests only. `parent_story_repository.py:784` still answers 409 `INVALID_IDEMPOTENCY_KEY` for the concurrent loser in `confirm_context` (and other concurrent-loser paths use non-§9.8 409 codes, e.g. `:918`, `:1124`, `:1704`). SRS §9.8 lists the code under 400. Do not read "all payload reuse is 400". Proper fix (replay when the fingerprint matches, else 400) belongs to the task that owns the Parent story concurrency paths.
- OQ-4: folded in (see section 1).
- Check order, so nobody "fixes" one side: the four story routes keep a required header declaration, so a keyless request answers 400 before authentication; cancel and delete (optional header) check the role first. Both are safe because the 400 does not depend on the resource (SRS l.865). The published OpenAPI keeps `Idempotency-Key` required (maxLength 128) on the four routes.
