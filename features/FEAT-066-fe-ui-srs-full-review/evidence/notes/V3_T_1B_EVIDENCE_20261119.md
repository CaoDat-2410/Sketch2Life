State before revision follows T-1a (same family and file); Draft 1 had the revision first.
- T-1b-DEC-3 (effect of unsuitable; l.395, l.1580, l.503): generation `READY` to `REJECTED_BY_ADULT` by compare-and-set (`rejection_reason_code`, `generation_revision` +1); run to `SCRIPT_REVIEW` with `adult_wait_started_at` and `last_meaningful_activity_at` = now, `revision` and `version` +1, the owner lock kept, `current_video_generation_id` kept (T-1c must test the generation state, not the pointer); output asset kept internally until the run is deleted (purge tested); receipt FINAL 200 with ids and states only. No outbox event and no audit row (the sibling confirm routes have none).
- T-1b-DEC-4 (cap; l.518, l.573, l.1671): at three accepted rows (`generation_no IS NOT NULL`) the answer is 409 `VIDEO_REGENERATION_LIMIT_REACHED` and nothing changes: the video stays `READY` and the adult may still complete or cancel. A rejected row keeps its number, so it counts toward the three.
- T-1b-DEC-5 (hide timing, recorded SRS inconsistency for the owner check): FR-P-09 (l.518) hides the rejected video "when the regeneration is accepted"; l.395 and l.1580-1581 hide it at the mark, even if no regeneration follows. The stored state is `REJECTED_BY_ADULT` at the mark. A client sees no difference: the only way to see a video is the playback token (l.1676), which needs a run in `VIDEO_READY`, which the run leaves at the mark; no storage URL is ever exposed. FR-P-09's "hidden once the regeneration is accepted" therefore holds at the latest.
- T-1b-DEC-6 (`complete`; l.1672, l.503, l.517): body `expected_revision`, key required, only `VIDEO_READY`. Run `COMPLETED`, `active_owner_parent_account_id` NULL (the one-run lock is released in the same transaction), `finished_at` and `last_meaningful_activity_at` = now, `adult_wait_started_at` NULL, `revision` and `version` +1; the generation stays `READY` (not a video approval); content stays until the user deletes the run (the existing `DELETE` accepts `COMPLETED`; the purge of the `READY` row and its asset is tested). No playback token after completion (it needs `VIDEO_READY`); the SRS names no replay after completion.
- T-1b-DEC-7 (replay): the same key and payload returns the current run (the family's convention, as `script-confirmation`), not a stored body; the receipt body keeps ids and states only. A replay after a purge is the projection.
- T-1b-DEC-8 (concurrency): every command locks the run row first, so cancel, complete and unsuitable serialise; the loser sees the new state (409). Two same-key requests: one change and one replay.
- T-1b-DEC-9 (catalog): both operations are catalogued and added to the FE projection (as T-2b, T-2c and T-1a did). The two error tables declare 422 like the siblings (the validation envelope), which the catalog test compares.

## 3. Open questions and findings

- **Q4 (main path DECIDED by the SRS and implemented; one corner OPEN for the owner).** Combined review R1 found that the first version (option B1: nothing changes) left the run, after `video-unsuitable`, with no way forward but cancel and idle closeout. SRS l.416 says each AI rewrite "including after a video is marked unsuitable" creates a new revision that needs confirmation again; l.393 gives SCRIPT_REVIEW two exits (a rewrite, a confirmed revision); BR-14 (l.258) and BR-16 (l.260) require the confirmation before the next creation; FR-P-09 (l.518) grants two regenerations; AC-06 (l.1129) counts 1 + 3 rewrites and 1 + 2 regenerations as independent limits. So the SRS settles the main path and B1 was wrong. **Implemented option B2 (code only, no migration):** `story-rewrites` accepts a `CONFIRMED` latest revision only when a `REJECTED_BY_ADULT` generation sits on it, and supersedes it (BR-14: kept internally); the way back is `video-unsuitable` (200), `story-rewrites` (202, new `DRAFT` revision), `script-confirmation` (200), `video-generations` (202, `QUALITY_REGEN` number 2). It costs one of the three rewrites. A `CONFIRMED` revision without a rejected generation (no video, an older failed generation, a ready video) is still refused with 409 `INVALID_STATE_TRANSITION`. The earlier statements in this note, in Draft 1 and in the T-1a notes ("a rewrite works", "A or B, T-1a works with both") are superseded by this paragraph.
  **Corner OPEN, owner question (BLOCKED_GATE for option A):** an adult who already used all three rewrites (story revision 4) before the marked video cannot rewrite again (`STORY_REWRITE_LIMIT_REACHED`, pinned by test `test_the_revision_four_corner_stays_refused_with_the_rewrite_limit`) and cannot confirm the same revision again, so cannot regenerate. The SRS is silent on this corner (FR-P-07 and FR-P-09 are independent limits). Option A (confirm the same revision again through a review epoch on `uq_story_revision_review_once`) needs a migration and a change to an approved M2 route. Question: accept the limit as the SRS reading of FR-P-07, or open the migration of option A?

- T-1b-DEC-5 is a reading of an inconsistent SRS and needs the owner check (accepted by review R1: storing `REJECTED_BY_ADULT` at the mark is compatible with every clause because no client can see a video after the mark).
- T-1b-DEC-10 (R1 fix, Q4 above): B2 as described. Hot file touched: `parent_story_repository.py` (one block in `reserve_story_rewrite` and one private helper): conflict check against `.worktrees/v3-next` and the other T-2d work is the coordinator's.
