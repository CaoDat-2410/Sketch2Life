## 2. Decisions (T-7b-DEC-n, SRS-cited; the coordinator assigns D-066 numbers)

- T-7b-DEC-1 (commands; l.1709, l.1697, l.1651, l.1699, TD-08): `POST /api/be1/v1/classes/{class_id}/suspend` and `.../archive`, School Manager only, keyed (`Idempotency-Key` 1-128), strong `If-Match: "<class_revision>"`, no body. 200 `{"contract":"Be1ClassStateV1","class_id","state","class_revision"}` with `ETag`. The body has no name, age, child reference or count. The verbs are a candidate, not SRS text (TD-08 is OPEN-TECHNICAL).
- T-7b-DEC-2 (states and machine; l.593, l.842, l.866, l.1461, l.1896, F-11): `active`, `suspended`, `archived`. **Amendment to TD-08's default text:** `suspended` is stored as `suspended`, not mapped to `locked` (`locked` is the session-group term; the SRS says "tạm ngưng"). Transitions `active -> suspended`, `active -> archived`, `suspended -> archived`; `archived` is terminal; every other pair, the same state again included, is 409 `INVALID_STATE_TRANSITION` and writes nothing. **No reactivate or unarchive route**: l.1896 ties reactivation to capacity (X-13, not built); a contract test pins the absence of such a path.
- T-7b-DEC-3 (list filter and Teacher rule; l.796, l.1640, l.1708, closes T-7a Q-1): `GET .../classes?state=active|suspended|archived|all`, default `active`; a bad value is 400 `INVALID_REQUEST`. The Manager may ask for any state. A Teacher sees only classes of a **class-scoped** row (teacher, guide, observer), and only states `active` and `suspended` (`archived` alone is an empty page, `all` means the two). **An organization-wide teacher-family row is a membership marker and no longer lists every class** (an organization-wide `school_admin` row still does). Items gain `class_revision`. The cursor scope is `be1.classes:{org}:{state}`, so a cursor cannot move to another filter and the T-7a shape (no state) is refused.
- T-7b-DEC-4 (TD-28, the class revision; l.1651, l.1699): `be1_classrooms.revision`, start 1, +1 on a state change and on a Teacher assignment (`assign_class_teacher`); T-7d adds the enrollment move; a profile create does not bump it (T-7c). `assignment_revision` (1 + teacher rows) is unchanged and stays the l.1650 token. A replay of the assignment returns before the bump, so it never double-bumps. Hand-off (F-10): `create_class` and the assignment response return only `assignment_revision`; a client learns `class_revision` from the list (A07) or from the state command answer. Reassignment and offboard (T-6a) must also bump `class_revision`.
- T-7b-DEC-5 (read/write class guard; l.593, l.1425, l.1461, F-07): `get_class(..., write=True)` is the default. Writes that now refuse a non-active class with **409 `INVALID_STATE_TRANSITION`**: `create_session`, `create_observation`, `record_consent`, `create_profile` (after the scope check, so a stranger never learns the state), the assignment. Reads pass `write=False` and see every state: A09 (roster), A10 (consents), the portfolio route. **`revoke_consent` stays allowed** on a read-only class (withdrawing a consent is not a class write; the SRS is silent). `/v1/me` (`account_scope.py`) is unchanged, so it still hides a suspended class (Q-4). A running session of a class suspended later is not touched (Q-3); the session lifecycle is ruled in T-7b-DEC-13 (stage 2). Class writes read the class row `FOR SHARE` (`get_class(write=True)`, `create_profile`), the same as the occurrence family (review F-02), so a suspension that races a write waits for it; `assign_class_teacher` and the state commands take `FOR UPDATE`. Lock order: session `FOR UPDATE`, then class `FOR SHARE`; the state commands lock the class only, so there is no cycle.
- T-7b-DEC-6 (archived is read-only for the Manager and gone for a Teacher; **an inference**: the SRS names only the suspended class as read-only): `hide_archived_from_teacher` answers the uniform 404 to a caller without a `school_admin` row on A09, A10 and the portfolio; writes on an archived class are 409 for any role, and the list hides it from a Teacher (the 409 on a write reveals only to a caller that already passed the scope check).
- T-7b-DEC-7 (assignment on a read-only class; plan review F-03): the assignment reads the class in any state, takes the any-state `FOR UPDATE` lock, replays a stored receipt, then refuses a non-active class with **409 `INVALID_STATE_TRANSITION`** (before the assignment-revision check, as the T-3d precedence puts the archived refusal before the stale check). The Draft 1 claim was wrong: with the old `state = 'active'` lock filter a suspension that committed while the assignment waited gave a uniform 404 after the wait. Now the loser of a suspend-versus-assign race is told 409. The reverse loser, the suspension that carries the old class revision after an assignment bumped it, is 409 `STALE_REVISION` with `current_version`.
- T-7b-DEC-8 (command order; plan section 3, mirrors `assign_class_teacher`): (1) class by id, any state, missing -> uniform 404; (2) School Manager of the class (`require_assignment`, roles `school_admin`): unassigned, other organization, Parent, Platform Admin, inactive and a Teacher of another class -> one 404 body, a Teacher assigned in the organization (class row, organization-wide row, guide) -> 403 `ACTION_NOT_ALLOWED` (F-14, both tested); (3) key and strong `If-Match`; (4) class row `FOR UPDATE`; (5) receipt `(subject, "POST /classes/{id}/{command}", key)`: same fingerprint (`sha256({"command","if_match"})`) -> the stored body and its `ETag`, another -> 400 `INVALID_IDEMPOTENCY_KEY`; (6) `If-Match != revision` -> 409 `STALE_REVISION` (+`current_version`, `ETag`); (7) transition check; (8) one transaction: `state`, `revision + 1`, audit `class.suspend|class.archive`, outbox `be1.class.suspended.v1|be1.class.archived.v1` (aggregate = class id, revision = the class revision, payload class id, `from_state`, `to_state`), receipt (class id, state, revision only). A unique violation on the receipt key rolls back and replays the winner. Stale is decided before the transition, so an archived class with an old `If-Match` is told to reload first.
- T-7b-DEC-9 (write matrix of the occurrence families; plan review F-04; l.593, l.1425): every class-scoped write of the occurrence routes refuses a read-only class with 409 `INVALID_STATE_TRANSITION` **after** the replay check (a replay of an earlier success still answers its first body) and takes the class row `FOR SHARE` where the work happens under the occurrence lock, so a concurrent suspension waits (the suspension takes `FOR UPDATE`; no lock cycle: occurrence, then class, and the suspension locks only the class). Covered: occurrence create (T-3a, existing), document attach (T-3b), text revision edit (T-3c), plan create and confirm (T-3d), and the upload session create and complete of purpose `OCCURRENCE_DOCUMENT` (`ensure_accepting`). Reads stay open. An occurrence whose class row is missing is not refused (the class ref is opaque, no foreign key).
- T-7b-DEC-10 (X-13 and ownership; F-06): no capacity, subscription, quota, billing or payment code and no `CLASS_CAPACITY_REACHED`. A downgrade-driven suspension (FR-B-07 l.593, l.1896) is not built and **no suspension reason or origin is stored**: SRS l.842 says the class state is the projection of Billing's capacity events, so a Billing teammate cannot tell a manual suspension from a capacity one and reactivation of a capacity-suspended class "needs capacity". Hand-off: one writer rule for `state`, the `revision` bump contract (+1 per state change), and an origin column (a new migration) when Billing projects into BE1.
- T-7b-DEC-11 (OpenAPI): both commands are catalogued under the tag "BE1 - Organizations & Classes", keyed, and join `SRS_V22_INCLUDED_OPERATIONS` (the FE-projected spec, like the assignment command).
- T-7b-DEC-12 (a downgrade needs the code revert; F-08, F-12): the downgrade refuses while any class has `revision > 1` and, once T-7c/T-7d ship, needs the matching code revert. The ORM column sits on a `be1_core` table but the migration is on the `lesson_library` chain, so `alembic upgrade heads` (not a per-branch upgrade) is required.
- T-7b-DEC-13 (session lifecycle on a read-only class; implementation review F-01, P2; SRS l.593 "Lớp tạm ngưng chỉ đọc", l.1417 UC-03 and l.1461 UC-06 "chỉ xem được"; archived is inferred as at DEC-6). Rule: **a read-only class starts or continues no run, and a run that already exists can always be closed.** The run-starting or continuing transitions `lobby`, `start` and `resume` are class writes: after the scope check `_do_transition` reads the class with `get_class(write=True)` and answers **409 `INVALID_STATE_TRANSITION`** (the same code as `create_session`), before the session revision or the learning-stage or consent checks, writing nothing. `pause`, `finish` and `completion` stay allowed (stopping or closing a run is not a class write; Q-3 default kept: a class change does not touch a session, it only stops new runs).
