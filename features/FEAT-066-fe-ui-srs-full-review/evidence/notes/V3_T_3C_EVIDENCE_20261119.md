## 2. Decisions (T-3c-DEC-n, SRS-cited)

- T-3c-DEC-1 (route; l.546, l.798, l.1437, TD-05): `POST /v1/lesson-occurrences/{occurrence_id}/documents/{document_id}/revisions`. The SRS names the group "revision chỉnh sửa" without a path; this resource-style path is the plan's choice (TD-05 flag). An edit never touches the source file, the extraction revision or any earlier revision (FR-T-07: the original file stays, a new immutable text revision is written). The library `POST .../lessons/{id}/versions` (a lesson version, not a text revision) is not touched.
- T-3c-DEC-2 (request and text rules; l.546, l.1437; plan review F-02): body `{extracted_text, expected_head_revision_no}`, unknown fields are `UNKNOWN_FIELD`, `Idempotency-Key` required. The text is stored exactly as sent (no stripping, no trimming, no line-ending change, no HTML handling) and hashed as UTF-8 bytes; it is never logged or echoed in an error. Rules, answered as 400 `INVALID_REQUEST` with `field_errors [{extracted_text, code}]` before authorisation and before any database access: encoding is strict, so a lone surrogate (JSON `\ud800`) is `INVALID_FORMAT` and never a `UnicodeEncodeError` 500; a NUL is `INVALID_FORMAT` (PostgreSQL text cannot hold it); more than 2,097,152 UTF-8 bytes is `TOO_LONG` (bytes, not characters: the Pydantic `max_length` of 2,097,152 characters is only a coarse bound that cannot refuse valid text); blank after `str.strip()` is `EMPTY`. A stranger with a bad text learns the text rule and never whether the document exists.
- T-3c-DEC-3 (request size guard; plan review F-01): a text of 2 MiB of control characters is 6 bytes per character once JSON-escaped (about 12 MiB), so the route body is capped at 13 MiB. The guard is a branch of the existing ASGI bounded-upload middleware (`BoundedImageUploadMiddleware`, already added to the app, so `app.py` is not edited): it refuses a `Content-Length` over the cap and counts streamed bytes, and answers 413 `MEDIA_TOO_LARGE` in the CONV-1 envelope with `X-Request-ID`. It runs before FastAPI reads, parses or validates the body and before authentication, authorisation or any database access. FastAPI turns an exception raised while it reads the body into its own 400, so the streamed case records the breach, drops whatever the application then answers and sends the 413 itself (a unit test uses an application that swallows the error). Only this route is bounded; the existing branches of the middleware behave as before. Deviation: the middleware file is outside the Draft 1 allowlist (section 5).
- T-3c-DEC-4 (scope; l.864-865, T-3a-DEC-3, T-3b review F-02 ruling): write path is the responsible Teacher only (`authorize_occurrence(write=True)`). Unknown occurrence or document, a document reached through another occurrence, another organization, another class, unassigned, School Manager (also one who teaches another class), Parent, Platform Admin, revoked or disabled: one identical 404. A second Teacher row of the class, a guide, an observer and a mixed account (observer of the class): 403 `ACTION_NOT_ALLOWED`. The authorisation runs again before a receipt is read, so a revoked Teacher cannot replay an old key.
- T-3c-DEC-5 (revision rule; l.546, l.1699, C-D7; plan review F-06): one transaction, no storage and no parser. Lock order: the occurrence `FOR SHARE`, then the source document `FOR UPDATE` (T-3d takes the occurrence then the document revision, so no cycle). Then the receipt, the state checks, the head: if `expected_head_revision_no` differs from the head, 409 `STALE_REVISION` with `current_version` (a plain integer) and `ETag "<head>"`, and nothing is written (the edit never overwrites or forks the head). Otherwise `revision_no` is head + 1, `origin` `TEACHER_EDIT`, `base_revision_no` the head, `review_state` `NEEDS_REVIEW`, parser columns NULL, empty warnings and page coverage, `created_by` the Teacher's account. A unique or primary-key violation (unreachable behind the lock; a test with the lock switched off fails) maps to the stored replay or to the stale 409. A trigger or other database fault is 503 `PROVIDER_UNAVAILABLE`, never a 500. The occurrence row is not changed (no state change, no revision bump). `ARCHIVED` occurrence and `DELETED` document are 409 `INVALID_STATE_TRANSITION` (no v3 route produces either; the tests set them by SQL).
- T-3c-DEC-6 (no-op; plan OQ-2, review F-04): an edit whose text hash equals the head's hash (exact bytes, so another line ending or one more space is a real edit) writes no revision and no audit entry and answers 200 with the head revision (`Content-Location` instead of `Location`). The stale fence comes first (a text equal to an old revision with an old fence is 409), and the revision cap comes after it (a no-op at 50 revisions still answers 200). Documented in the OpenAPI description.
- T-3c-DEC-7 (keys and receipts; l.1696-1699; plan review F-03, F-04): scope `POST /v1/lesson-occurrences/{occurrence_id}/documents/{document_id}/revisions` (so another document or another caller is another command), fingerprint over `{expected_head_revision_no, text_hash}`, another payload with the key is 400 `INVALID_IDEMPOTENCY_KEY`, refusals write no receipt. The receipt holds references only (`status_code`, `document_revision_id`, `revision_no` and the `review_state` the revision had when it was created), never the text (up to 2 MiB). A replay reads the immutable row and answers with that review state and ETag, so it equals the first response even after T-3d confirms the revision, and it returns the original revision after any later edit. The no-op writes a receipt too (status 200, the head of that moment); its replay returns that head, not the current one.
- T-3c-DEC-8 (review state and approval; l.546, l.1660, plan OQ-1, review F-07): an edit never confirms itself (`NEEDS_REVIEW`); FR-T-07's "Teacher reviews and approves before use" is met when a plan that pins the revision is confirmed (T-3d stamps `CONFIRMED`). No separate approve route is added (the SRS has none). Consequence: a DRAFT plan may pin a `NEEDS_REVIEW` revision and the Teacher may edit again after pinning. Open for the owner (section 5).
- T-3c-DEC-9 (revision cap; plan OQ-3, review F-05): at most 50 revisions per document, counted including the extraction revision, under the document lock; the 51st edit is 409 `RESOURCE_CONFLICT` (no `current_version`; the OpenAPI text says that reloading does not help). The SRS sets no number; the bound protects storage (about 100 MiB worst case) because no delete exists. A cap on total stored text instead of a count stays an option for the owner.
- T-3c-DEC-10 (pins are exact; l.546, l.1659): an edit never moves an existing plan, because a plan revision pins `document_revision_id`; a PostgreSQL test shows a plan pinned to revision 1 still points at it, with revision 1 byte-identical, after revision 2 exists.
- T-3c-DEC-11 (audit): one `core_audit_entries` row `lesson.document_revision.create` per new revision (actor = the account ref, organization, resource = the revision id, no text, no file name); none for a no-op.
- T-3c-DEC-12 (OpenAPI): the operation is in the contract catalogue (`MOUNTED_OPERATIONS`, tag `Lesson Occurrences`, keyed) and served; it is not added to `SRS_V22_INCLUDED_OPERATIONS` (the FE-projected spec), like the T-3b operations, and a contract test pins that.
