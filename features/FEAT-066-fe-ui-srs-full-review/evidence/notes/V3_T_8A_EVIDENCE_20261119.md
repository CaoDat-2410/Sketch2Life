| T-8a-DEC-1 | DDL-C is split: only `inbox_items` is created. IN_APP needs no delivery row; the inbox is the source of truth. Q-1 default (yes) applied. | FR-B-09, UC-15, l.1681, REG l.403-405 |

| T-8a-DEC-3 | Guard order: bearer (401) -> identity row by subject, `state = active`, issuer equal to the token, `account_role` in the four roles (else 404) -> every query filtered by the caller's account. Platform Admin reads and marks only its own inbox: this is a generic own-inbox read, it touches no teammate-owned admin scope (T8A-08). A valid bearer with no identity row is 404, not 401 (tested). | l.864-865, l.1681 |
| T-8a-DEC-4 | `NotificationV1` hides recipient, role, organization ref, trigger id, dedupe key and hash. `NotificationPageV1 {items, next_cursor, unread_count}`: order `created_at desc, inbox_item_id desc`, opaque keyset cursor (`encode_cursor`, scope `notifications`, UTC ISO time + id), `limit` 25 default, 100 max, 101 is 400, a bad, other-scope or zone-less cursor is 400 `INVALID_REQUEST` with field `cursor`. Expired items are hidden. `unread_count` counts at most 100 (one bounded count over the partial index); the schema description says "100 means 100 or more" (T8A-07). Headers `Cache-Control: private, no-cache` and `Vary: Authorization` on the page. | l.1640, l.1681 |
| T-8a-DEC-5 | Mark-read keeps a receipt in `be1_command_receipts` (T8A-01, no new DDL), written in the same transaction as the effect. `principal_ref` = the token subject; `operation_scope` the constants `POST /notifications/read` and `POST /notifications/read-all` (the item id is not in the scope); fingerprint = SHA-256 of canonical `{operation, inbox_item_id}`; `organization_id` NULL; `response_json` = the response body (no content). Same key and fingerprint replays the stored body (a read-all replay keeps the first `marked_count` and leaves later arrivals unread); another fingerprint is 400 `INVALID_IDEMPOTENCY_KEY`. The effect is monotone SQL: `read_at = GREATEST(now, created_at)` only `WHERE read_at IS NULL`, so the first `read_at` is never moved and an item created in the future still satisfies the CHECK. A concurrent first use of one key loses on the receipt PK (`IntegrityError` at commit), rolls back and replays. Receipts are success-only (a 404 writes none). A key is scoped to the principal and the operation: the same key on `read` and `read-all` is two independent commands (the receipt PK holds the scope). No ETag (monotone field, no revision). | l.812, l.1697, C-D6 |
| T-8a-DEC-6 | Producer port: `SqlNotificationProducer(session, clock)` validates, hashes and inserts with `ON CONFLICT (recipient_account_id, trigger_dedupe_key) DO NOTHING RETURNING`. On conflict the stored hash decides: equal returns the existing id (`created=False`), different raises `NotificationDedupeConflict`. `created_at` comes from the injected clock (not the database default), so `expires_at > created_at` is checked in the application before the write and the CHECK cannot be hit by clock skew (T8A-06). The command hash leaves out `expires_at` (a retry computes it from a new clock; the first stored expiry stays). | l.784, FR-B-09 |
| T-8a-DEC-7 | The "no child content" rule is an allowlist (T8A-02, T8A-05). `safe_parameters`: at most 8 keys, keys `^[a-z][a-z0-9_]{0,31}$`, values are bool, int (absolute value at most 2^53-1) or a string `^[A-Za-z0-9_.:-]{1,64}$`; no float, null, list or object; the key denylist (name, child, story, transcript, media, url, email, token, endpoint, address) stays as defence in depth. Size is measured in the PostgreSQL text form and capped at 1,536 bytes, below the CHECK (2,048), so a valid command cannot fail with a 500 on insert (T8A-04); in practice eight maximal entries are 8 * (32+64) bytes and stay far below. `trigger_id` and the dedupe key use `^[A-Za-z0-9._:-]{1,128}$` in the validator and the CHECK. Vietnamese names, spaced values, diacritics, sentences, URLs and e-mail addresses are refused (unit matrix). Known limit: a one-word token such as an opaque ref cannot be told from a one-word name by any rule; the port documents that parameters are codes, counts and opaque refs. | l.784, l.1681, FR-B-14 |
| T-8a-DEC-8 | No producer is wired (T-1d2, X-13 billing, group invitation stay unconnected); tests act as the producer through `SqlNotificationProducer`, the one adapter. Android stays unavailable (X-12, OD-08). | OD-08, OD-13 |
| T-8a-DEC-9 | `NOTIFICATIONS_BASE = "/v1/notifications"` joins the CONV-1 family on a whole segment (`/v1/notificationsfoo` is excluded). The T-8b push-endpoint paths are not registered: the framework answers 404 (tested on the app and in the route table). | R10 |
| T-8a-DEC-10 | The three operations are added to the FE-facing projection (`SRS_V22_INCLUDED_OPERATIONS`) with the tag `Notifications` (tag description of 7 words, the projection test limit is 9). The stale sentence in `SRS_V22_OPENAPI_DESCRIPTION` ("... and notifications are unavailable.") is reworded in the fix pass (T8A-I1, section 9): "notification push endpoints are unavailable" no extra sentence (the description test caps it at 55 words; it is 54 now). | T8A-03 |
