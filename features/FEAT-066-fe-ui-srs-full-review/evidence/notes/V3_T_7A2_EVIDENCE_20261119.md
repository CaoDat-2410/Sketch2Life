## 1. OWNER-VISIBLE SRS CONFLICT (read this first)

The owner's wording for this task was: a same-organization Teacher without the class assignment gets 403 `ACTION_NOT_ALLOWED`; unknown or out-of-scope gets the uniform 404. Applied literally to a Teacher whose active rows cover **only other classes** (or whose row is revoked), that conflicts with the SRS:

- l.864-865 (section 9.8): 403 only when the resource is known to be in the caller's scope; one 404 shape for an unknown id and an out-of-scope resource; it must not reveal membership, assignment or existence.
- l.1150 (AC-27): an unknown id and an out-of-scope id both 404.
- l.2575 (Teacher role row): the Teacher's scope is "the class/profile assigned in the school", so another class is out of scope.
- Owner-approved convention CONV-1 (D-066-68 C-D4, D-066-71 CV-5), and accepted tests that already encode the 404 (`test_be1_synthetic_pilot_postgres.py::test_t9_teacher_assigned_to_a_different_class_is_denied`, `test_t7a_roster_privacy_postgres.py` A09/A10 and roster, `test_m2_s1a_teacher_postgres.py` l.340-358, `test_be1_scope_guard_404_403.py`).

A 403 for that caller would let a Teacher with no part in a class tell a real session or class id from a random one (A07 does not list the class; every other route answers 404).

**Built (minimal SRS-compliant variant), decision T-7a2-DEC-4:** 403 `ACTION_NOT_ALLOWED` when the Teacher account's active rows **cover** the class (an org-wide `teacher` row, a `guide` or `observer` row of the class or org-wide) but none is an active `teacher` row of exactly that class, and for the School Manager; uniform 404 when no row covers the class (other class only, revoked, other organization, Parent, Platform Admin, no or inactive identity, issuer mismatch). For every caller SRS l.864 lets see a 403, the owner's wording holds.

Cost of the owner's literal alternative (for the owner to decide, not built): a new pre-coverage check in `require_assignment` or a wrapper, applied to R1-R3 and for consistency to A09, A10 (T-7a) and every route that calls `require_assignment`; it flips at least the accepted tests listed above and creates the existence oracle described. It is NOT a one-condition change in the helper (plan review P2-1: the 404 comes from the coverage check inside `require_assignment`, before the helper sees any row).
