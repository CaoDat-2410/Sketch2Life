## 2. Decisions (T-1c-DEC-n; Draft 2 D1..D8 apply as written, these are the implementation facts)

- T-1c-DEC-1 (token, TD-07 deviation; l.575-576, l.1676, l.1691, l.1693): the stateless signed token of Draft 2 D2, 300 s by default (30 to 900), because TD-07's "stored hashed" needs a table outside DDL-B1. It is never stored, logged, put in a URL or returned in an error body (tests assert it for logs, URLs, headers and bodies). Revocation is the per-request recheck.
- T-1c-DEC-2 (stream authorization; l.1691-1693, l.863-865): `GET /v1/story-runs/{id}/playback` requires the Firebase bearer AND the header `X-Playback-Token`; the token carries a domain-separated digest of the owner scope and the stream compares it to the caller's scope, so a valid token in another authenticated Parent's hands, or a teacher, manager or admin account, is the uniform 404 (one body shape). Order: token shape, signature and expiry (401 `INVALID_TOKEN` / `TOKEN_EXPIRED`, no store read), then in one short database scope the parent role, the path run against the token's run, the owner-scoped run and generation (404), then the object (404 when absent, 503 `STORAGE_UNAVAILABLE` on a store failure, a missing store or an object over the ceiling). A token in a query string is never read. `HEAD` is 405. `AUTHORIZATION_REVOKED` (l.875) is not produced for a Parent: a revoked grant is the uniform 404.
- T-1c-DEC-3 (run state AND generation state; T-1b hand-over, l.1676): playback needs the run at `VIDEO_READY` and the current generation `READY` with the technical, consistency and safety states `PASSED` and an output, read in one statement; the pointer alone never decides. A `REJECTED_BY_ADULT` generation (the pointer stays on it, T-1b D3), a run not at `VIDEO_READY`, an in-flight, blocked or failed generation and a run in a purge state get no token and the stream answers 404. The same predicate (`is_playable`) feeds the detail's `playback.state`.
- T-1c-DEC-4 (Q5 DECIDED conservatively, product question stays OPEN): after `complete` or the idle closeout no token is issued (409 `INVALID_STATE_TRANSITION`) and an old token answers 404. SRS l.1676 names the grant "active until complete, idle closeout or cancel" and requires the artifact at `VIDEO_READY`; §21.3 (l.1691) ties the token to "one ready video"; AC-41 (l.1164) is silent. BR-38 (l.282) and FR-B-11 (l.597) say stored data stays viewable after the quota runs out, which is a quota rule, not a completed-run rule. The SRS does not say whether a completed run replays its video, so the owner may still decide to allow it (a state check change in one predicate). The detail shows `playback.state` `UNAVAILABLE` for a completed run.
- T-1c-DEC-5 (fail closed at the route; l.1691): with no signing secret the token and stream routes answer 503 `PROVIDER_UNAVAILABLE` (the token route only after its 404 and 409 checks, so a foreign actor never sees 503 first) and the API still starts (production has no secret in any existing test or fixture). A startup warning names the setting without its value. local and test use a per-process random key; a token minted by another worker is then 401 `INVALID_TOKEN` (documented; local runs use one worker). The secret is a `SecretStr` of 32 or more visible ASCII characters and is never echoed in a validation error.
- T-1c-DEC-6 (streaming; l.1692): authorization runs in its own short session, closed before `StreamingResponse` is built; the generator reads 64 KiB chunks through `ObjectStoragePort.get_object` (it skips to the range start by reading and discarding: the port has no range read, see debt), closes the body in a `finally` also when the client leaves or the object ends early, and an object over the ceiling is refused before the first byte. Headers: `Accept-Ranges: bytes`, `Content-Type: video/mp4` (fixed, never from object metadata), `Content-Disposition: inline` without a file name, `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Content-Length`. One `Range` gives 206 with `Content-Range`; a malformed, multiple or unsatisfiable range gives 416 with `Content-Range: bytes */<size>`. No listing, download or export route exists.
- T-1c-DEC-7 (detail, `StoryRunDetailV1`; l.780, l.805, l.1811, AC-41, TD-22): additive optional fields on the existing response model: `video` (null until a request was accepted or is waiting; `current_generation_id`, `generation_no`, `kind`, `state`, `job{job_id, state, stage, retryable, error_code}`, `scenes[{scene_index, state}]`, `playback{state, asset_ref, token_route}`, `video_requests_used`, `video_requests_remaining`, `admission_pending`, `history`), `quota` (the constant `{state "UNAVAILABLE", granted, used, available, month: null}` of TD-22, never zero; no port, reader or setting; field names follow the Billing balance read) and `timeline` (derived from existing timestamps: `RUN_CREATED`, `VIDEO_REQUESTED`, `VIDEO_ACCEPTED`, `VIDEO_STARTED`, `VIDEO_READY`, `VIDEO_FAILED`, `VIDEO_SAFETY_BLOCKED`, `VIDEO_REJECTED_BY_ADULT`, `RUN_COMPLETED`). `video_requests_*` are the three-request run cap of l.573, not the monthly quota. The history holds the accepted rows (at most three); a pending intent is not history. The playback block is a readiness descriptor and the route name; a token exists only after the explicit POST. Never shown: prompts, raw transcript, hidden revisions, provider text, a foreign scope, the physical key (never selected: the read asks the database "has output" only).
- T-1c-DEC-8 (one builder; D5): `story_run_response` serves every route that returns the model, the legacy `/api/parent/v1/ai/...` routes included (`parent_ai._story_response` is the same function). The lifecycle envelope (DELETE_PENDING on) returns before any video read, as before.
- T-1c-DEC-9 (public failure codes, D8; l.875): `video.job.error_code`, the run-level `error_code` while the current video failed or was blocked, and the `failure.code` of `GET /v1/jobs/{id}` use the closed set `VIDEO_SAFETY_BLOCKED`, `VIDEO_DEADLINE_EXCEEDED`, `VIDEO_TECHNICAL_FAILURE`, `PROVIDER_UNAVAILABLE`; the stored `SAFETY_BLOCKED` maps to `VIDEO_SAFETY_BLOCKED` and every other stored code to `VIDEO_TECHNICAL_FAILURE`. This changes the job route's code for T-1a rows (it had shown the stored text); three T-1a pins were updated (section 4). A renderer's code reached the run-level `error_code` unmapped before this task (a T-1a leak the detail work found); that is closed here.
- T-1c-DEC-10 (ETag; l.1811): strong, `"d1-<first 32 hex of sha256 of the canonical sorted-key JSON of story_run>"`, so `request_id` is outside the input and every body field (playback state, counts, scene states, timeline) is inside it; the content hash replaces the run revision because generation and scene states change without a run revision bump. `Cache-Control: private, no-cache`, `Vary: Authorization`. `If-None-Match` (a list, the weak form and `*` are accepted) is evaluated after authorization against a body recomputed from the database; a foreign caller with a matching tag gets 404, never 304. No tag on the lifecycle envelope. Commands keep the body `expected_revision`.
- T-1c-DEC-11 (opaque handle, F-06): `asset_ref` is `vid_` plus the generation id, in the grant and in the detail. The physical key stays in the Story-owned `output_asset_ref` column, is read only by `resolve_playback`, and is excluded from the record's `repr`.
- T-1c-DEC-12 (catalog and projection): the two new operations are catalogued and added to the FE projection (`openapi_srs_v22.py`), and the detail entry gains the 304 row. Draft 2 said "runtime-only"; T-1a's implementation review (F-08) ruled the projection edit acceptable because Android needs the contract, and T-1b did the same. Removing the two tuples reverts it. The stream is published as a binary `video/mp4` 200 and 206 and its header parameters `X-Playback-Token` and `Range`; no query parameter exists.
- T-1c-DEC-13 (no DDL): no table, no column, no constraint. The token needs no grant table; `video_generation_scenes` and `video_generations` (T-1a) were enough.

## 3. Open questions, risks and debt

- Q1 (OPEN-WITH-DEFAULT yes): is the stateless signed token acceptable instead of TD-07's stored hashed token? If the owner wants a stored grant, a `story.playback_grants` table needs its own DDL approval and this task moves later.
- Q2 (client, OPEN-WITH-DEFAULT): header transport (`X-Playback-Token` plus the bearer) cannot serve a plain web `<video src>`, and a browser fetch with custom headers needs CORS, which the backend does not have (T0.6). If the web player needs a URL-borne token a one-time exchange route is needed; not built. The owner may instead choose a pure capability token (no bearer on the stream) and accept the leak risk of review F-01.
- Q3 (OPEN-WITH-DEFAULT): the SRS asks for a "timeline" (l.805) but no history store exists and "no read-model table" is a rule (l.845); the timeline is derived from existing timestamps. A true history needs an owner decision.
- Q4 (OPEN-WITH-DEFAULT): the token lifetime; 300 s default (settings 30 to 900); the SRS says only "short-lived".
- Q5 (DECIDED conservatively, product question OPEN): T-1c-DEC-4.
- Quota summary content: OWNED_BY_OWNER (the quota reader); only the marker is delivered here.
- Debt: (1) the object-storage port has no range read, so a range skips by reading and discarding up to 100 MiB (the ceiling) per request; the real adapter needs a ranged `get_object`. (2) `Content-Length` is taken from the object's declared length; a store that returns fewer bytes ends the response early. (3) A stateless token cannot be revoked before its expiry; mitigated by the per-request recheck, the actor binding and 300 s. (4) With one per-process key in local/test a second worker rejects another worker's tokens. (5) Teacher assignment recheck is a seam only (T-4a1); `ScopeKind` ORGANIZATION is not read. (6) A deployment with no signing secret serves 503 on playback only (deployment owner). (7) The run-level error-code mapping applies to video failures only; other families keep their stored code. (8) `get_run` now runs one extra bounded read (two statements) whenever a run has a current generation; it also runs for `GET /active/current` and every command response.
- FE impact: Android adds the token call, the bearer-plus-header stream and the extra fields. The mobile client (`.worktrees/mobile`) and the web client (`.worktrees/ui`) were grepped: neither has an exact-key decoder (the types are plain TypeScript interfaces), and the frozen M2 projection test reads a frozen JSON file whose `required` list stays valid because every new field is optional. No FE test was run (NOT CHECKED). The web `<video>` case is Q2. Rollback: remove the two routes (the additive response fields may stay); the job and run-level code mapping is a one-function revert.

## 7. OWNER-VISIBLE decisions and open items (read these first)

1. Q1, stateless signed token instead of TD-07's stored hashed token: accepted by implementation review R1; no SRS conflict (SRS section 21.3, l.1691, asks for a short-lived token limited to one ready video and to actor and run, rechecked against current ownership; l.1693 and l.576 say nothing about storage). Lost against a stored token: single use, per-token revocation, an issuance audit trail; replaced by the per-request recheck (owner, run state, generation), the bearer-plus-actor binding and 300 s. TD-07 names a table, so the owner should confirm once.
2. Q2, header transport (`X-Playback-Token` plus the bearer): correct for l.1693 (no URL copy in logs, history or referrers; a query-string token is never read, test-pinned). A plain web `<video src>` cannot set that header and a browser `fetch` with custom headers needs CORS, which the backend does not have. Stays OPEN. Android (ExoPlayer or MediaPlayer headers) and a native iOS player work. Do not close it by moving the token into the URL.
3. Q5, a COMPLETED run gets no token (409 for a new token, 404 for an old one, `playback.state` `UNAVAILABLE`): the SRS is silent on replay after completion (l.1676 requires `VIDEO_READY`; l.282 and l.597 are about quota exhaustion). One predicate (`is_playable`) flips it. FE consequence: after `complete` or the idle closeout (T-1d1, 168 h) the adult cannot replay.
4. Range requests skip by reading and discarding up to the object ceiling (100 MiB) per request until the object-storage port gets a ranged `get_object` (and the S3 adapter a `Range` parameter); required before a real renderer ships.
5. Public names that the SRS does not name: `VIDEO_TECHNICAL_FAILURE`, `VIDEO_DEADLINE_EXCEEDED` (l.875 names only `VIDEO_SAFETY_BLOCKED`; `PROVIDER_UNAVAILABLE` is in the l.873 table) and the 416 code `RANGE_NOT_SATISFIABLE` (the SRS error table has no 416 row). FE will switch on these names.
6. `TOKEN_EXPIRED` and `INVALID_TOKEN` reuse the SRS bearer codes (l.863): a client that treats `TOKEN_EXPIRED` as "refresh the ID token and retry" must instead call `playback-token` again after a 401 from the stream (a token lives 300 s, so a player requests a new one to seek after expiry).
