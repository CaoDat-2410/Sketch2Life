## 1. HEAD facts

- Legacy route `POST /api/parent/v1/ai/drawing-understandings` (`parent_ai.py:232`): base64 image, `modal_dev` gate, synchronous Modal call, `attach_artwork` inserts the **original and derived** `core_asset_metadata` rows itself. After T-2a the original row already exists (written by upload `complete`: key `parent/{run}/{token}/original`, version 1, `source_refs=[run]`, Parent scope), so `attach_artwork` cannot be reused for the original (primary-key clash).
- T-2a gives a client only the opaque `asset_ref = upl_{upload_id}`; `resolve_asset_key(db, handle, scope...)` returns just the key (`infrastructure/uploads/service.py:156`). It does not check target, purpose, hash or scanner identity.
- Run store (`parent_story_repository.py`): `_owned_run` raises 404 `RESOURCE_NOT_FOUND` for unknown or foreign runs; `ensure_accepting_artwork` accepts only `INPUT_PROCESSING`; `record_understanding` and `fail_drawing_analysis` complete the VLM step; run `revision` and `version` bump on every change; receipt operation `ATTACH_ASSET` is already in `ck_story_receipt_operation`.
- `modal_function_client.MAX_IMAGE_PIXELS = 2_000_000` and `prepare_drawing_input` (JPEG/PNG, source at most 5,000,000 bytes) are the Modal worker contract; DB limits: original at most 20 MiB, derived at most 5,000,000 bytes (`ck_story_run_input_sizes`).
- The StoryRun-lite demo owns `POST /v1/story-runs/{run_ref}/assets` (`story_run_lite.py:108`). Real and demo routes are mutually exclusive in one process (T0.5 guard, `include_parent_story_runs`).
- The Android client still calls the legacy route (`apps/ui-mobile/.../ParentApi.ts:374`, base64) and has no code for this route, so nothing in the client depends on the new one yet.

## 2. Decisions (SRS-cited)

- **T2B-D1 Route and mount (l.1664).** New module `interfaces/http/routers/parent_story_inputs.py`, `APIRouter(prefix="/v1/story-runs", tags=["Parent StoryRuns"])`, mounted under the existing `include_parent_story_runs` flag (so the demo exclusion and `story_demo_replaced_routers()` cover it). T-2c and T-2d add their routes to the same module; `parent_story_runs.py` is not edited (T0.9 edits it first). The M2 story envelope already applies to every `/v1/story-runs*` path (`app.py` handlers), so no envelope change.
- **T2B-D2 Actor and 404 rule (l.1664, l.864-865, CV-5).** Parent account only; a wrong role or inactive account answers the T0.9 body (404 `RESOURCE_NOT_FOUND`). The run is loaded by `_owned_run` (owner scope hash of issuer+subject), so a foreign or unknown run is the same 404. The asset is resolved by a new helper `resolve_completed_upload(db, handle, owner_scope..., target_ref=run_id)` in `infrastructure/uploads/service.py` (additive, next to `resolve_asset_key`): purpose `RUN_ARTWORK`, state `COMPLETED`, `target_ref` equal to this run, scope equal to the caller, `scan_verdict CLEAN`. It returns key, size, SHA-256, media type and scanner name/version. Any miss (another actor's asset, another run's asset, a lesson asset, a physical key passed as ref, unknown id) is the same 404; no hint that the asset exists. No client-supplied owner, key or URL is read (l.1637, l.1692).
- **T2B-D3 Request and keys (l.1664, l.1697, l.1699).** Body `AttachRunAssetRequestV1`, `extra=forbid`: `asset_ref` (`^upl_[0-9a-f-]{36}$`), optional `expected_run_revision` (int, at least 1; sent and different from the run revision gives 409 `STALE_REVISION` with `current_version`; l.1664 lists no revision, so it is optional). `Idempotency-Key` required, `parse_idempotency_key` (1-128, 400 `INVALID_REQUEST`/`INVALID_IDEMPOTENCY_KEY`), after the role check and before the run lookup. Receipt operation `ATTACH_ASSET`, scope `STORY_RUN/{run_id}`, fingerprint over `{asset_ref, expected_run_revision}`; replay re-authorizes then returns the stored 202 body; same key with another body is 400 `INVALID_IDEMPOTENCY_KEY`. No DDL.
- **T2B-D4 State rule, retake (FR-P-02 l.511, FR-P-12 l.521, WP-2 rules).** First drawing: run in `INPUT_PROCESSING`, no drawing attached. One retake: run in `INPUT_REVIEW` or `SUBJECT_REVIEW` (before subject confirmation) and the run has exactly one drawing input; a second retake, or any other state, is 409 `INVALID_STATE_TRANSITION`. The same asset twice (another key) is 409 `INVALID_STATE_TRANSITION`. A retake writes input revision N+1 (previous understandings and inputs stay as history), clears nothing else, and returns the run to `INPUT_PROCESSING` (l.394 says a rerun goes back to `INPUT_PROCESSING`). `PARENT_STORY_ARTWORK_ALREADY_ATTACHED` and `PARENT_STORY_RUN_NOT_ACCEPTING_ARTWORK` are not in §9.8; the new route answers `INVALID_STATE_TRANSITION` (as T-2a-DEC-12). `ensure_accepting_artwork` (used by the T-2a upload resolver) is widened to the same state set plus the retake count so a retake upload can be created.
- **T2B-D5 Normalization (l.983, l.1942, l.1943, FR-P-02).** The source is read through `ObjectStoragePort`, size and SHA-256 recomputed against the session (mismatch 422 `UPLOAD_CHECKSUM_MISMATCH`, missing object 422 `UPLOAD_INCOMPLETE`, storage fault 503 `STORAGE_UNAVAILABLE`). Decode with Pillow under limits: dimensions read lazily first, more than 40,000,000 pixels is 422 `IMAGE_DIMENSIONS_EXCEEDED` before any decode; decompression-bomb errors map to the same code; a stream that does not decode is 422 `UPLOAD_CONTENT_MISMATCH`. Derived asset: EXIF-orientation applied, RGB PNG, scaled down (never up) to at most 2,000,000 pixels (the existing Modal worker contract) with a three-step ladder if the PNG exceeds 5,000,000 bytes, else 422 `IMAGE_DIMENSIONS_EXCEEDED`. The original is never resized or rewritten (l.1942: hash and provenance first). WebP is accepted (T-2a policy). New module `infrastructure/story_inputs/drawing.py`; it does not import the Modal client.
- **T2B-D6 Persistence (FR-C-08, l.1692).** New `SqlParentStoryRunRepository.attach_uploaded_drawing(...)` under the run row lock: refuse purged runs, verify state and retake count, insert the derived `CoreAssetMetadataModel` (key `parent/{run}/{token}/normalized.png`, token from the same UUIDv5 as the original, so a retried attach overwrites; `derived_from_ref` = original key; Parent scope; `source_refs=[run]`), one `core_asset_lineage` row (`NORMALIZE_DRAWING_IMAGE`, version `PILLOW_RGB_PNG_V2`, scanner identity from the upload session through `scanner_identity_sha256`, T-2a-DEC-7), the new `run_inputs` revision (copy-forward of typed idea and context snapshot, as `attach_artwork`), the run update (`current_input_revision`, `asset_ref`, `derived_asset_ref`, `job_state QUEUED`, version and revision +1), and the receipt, in one commit. The derived object is put before the commit and deleted on any DB failure. The original row is not touched. Purge: both assets carry `source_refs=[run]`, so the FR-C-08 plan already finds them; a test proves the plan stays removable.
- **T2B-D7 VLM step behind a port (OD-13, l.394, FR-P-04).** New port `application/ports/parent_story_inputs.py::DrawingAnalyzerPort.analyze(DrawingAnalysisRequest) -> DrawingAnalysisResult` (candidate subject, up to 4 visible features, confidence, `child_count`, `topic_compatible`). Local adapter `FixtureDrawingAnalyzer` (infrastructure) answers only for an explicit mapping of derived SHA-256 to a result (same discipline as the T-2z scanner: unknown input is a recoverable failure, never a made-up answer). `app.state.drawing_analyzer` is `None` by default: the run then stays `INPUT_PROCESSING` with `job_state QUEUED` (no worker exists; real workers are OD-13). When a port is composed (tests, local), a `ParentInputJobRunner` runs after the response through `BackgroundTasks`, calls the existing `record_understanding` (extended with `expected_input_revision` so a result for a replaced drawing is discarded) or `fail_drawing_analysis`. `child_count > 1` fails the step with code `MULTI_CHILD_NOT_SUPPORTED` (l.871; the run goes to `INPUT_REVIEW`, retake allowed once); a topic mismatch is stored as `warnings` beside `result` in the understanding snapshot (not in the `candidate` body, whose model forbids extra keys). No Modal call is added.
- **T2B-D8 Response and job ref (l.1664 "201/202 asset ref and validation state", l.1675).** 202 `ParentRunAssetAcceptedV1 {request_id, story_run_id, asset_ref, asset_kind "DRAWING", asset_state "READY", input_revision, run_revision, run_state, analysis_state QUEUED|RUNNING|SUCCEEDED|FAILED, job}`; `Content-Location: /v1/story-runs/{id}`. `job` is `null` until Q-J is answered (section 6); the client polls `GET /v1/story-runs/{id}` (`job_state` already exists, l.780). Adding the job ref later is additive.
- **T2B-D9 Legacy route stays.** P-06b says to remove `drawing-understandings` once Android has moved; Android has not (`ParentApi.ts:374`, `useParentController` uses `analyzeDrawing`). Nothing is removed in v3 (recorded for T-2d, which owns P-06b).

## 3. Route and contract

| Method and path | Actor | Request | Success | Errors |
|---|---|---|---|---|
| `POST /v1/story-runs/{run_id}/assets` | Parent, run owner | `Idempotency-Key`; `{asset_ref, expected_run_revision?}` | 202 `ParentRunAssetAcceptedV1` | 400 `INVALID_REQUEST`, `INVALID_IDEMPOTENCY_KEY`; 401; 404 (role, run, asset); 409 `INVALID_STATE_TRANSITION`, `STALE_REVISION`; 413 `MEDIA_TOO_LARGE`; 415 `UNSUPPORTED_MEDIA_TYPE` (an audio or non-image asset); 422 `IMAGE_DIMENSIONS_EXCEEDED`, `UPLOAD_INCOMPLETE`, `UPLOAD_CHECKSUM_MISMATCH`, `UPLOAD_CONTENT_MISMATCH`; 503 `STORAGE_UNAVAILABLE`, `PROVIDER_UNAVAILABLE` |

`MULTI_CHILD_NOT_SUPPORTED` is reported by the job step (state and `error_code` on the run), not by this synchronous answer, because the VLM runs after the response; the WP-2 table lists it under this route, so the review should confirm that reading. New messages for these codes go into the story-envelope table in `app.py` (hot file). Catalog: one new `MOUNTED_OPERATIONS` entry, `SRS_V22_INCLUDED_OPERATIONS` entry, operation counts re-read at implementation time (T-3a and T-2c also move them).
