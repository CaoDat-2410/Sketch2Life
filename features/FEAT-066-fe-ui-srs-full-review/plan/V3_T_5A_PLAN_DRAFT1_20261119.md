## 1. Verified facts

- F1 `lesson.occurrences` already has `sample_slot_state` (`AVAILABLE|CLAIMED`), `sample_claimed_at`, `successful_sample_run_ref` (varchar 128, no FK), `class_projection_confirmed_by_ref`, `class_projection_confirmed_at`, `revision`, `state` (`APPROVED`, `SAMPLE_AVAILABLE`, `SAMPLE_USED`, ...). CHECKs: `ck_occ_sample` (`CLAIMED` needs `sample_claimed_at`; `AVAILABLE` needs both empty), `ck_occ_projection` (by and at together), `ck_occ_plan_state` (`SAMPLE_USED` keeps the plan pointer). The trigger `protect_occurrence` freezes identity and pin columns only: **nothing in the database stops `CLAIMED -> AVAILABLE`**; the one-way rule is a service rule (Q4).
- F2 No table holds audience or use; `core_audit_entries` has no metadata column. The receipt of the confirmation therefore lives in `be1_command_receipts.response_json` (refs only) and two audit rows.
- F3 Existing helpers: `authorize_occurrence`, `require_class_writable`, `raise_stale_revision`, `etag_for_revision`, `parse_idempotency_key`, `PlanRevisionService` as the model of a keyed occurrence command (occurrence `FOR UPDATE`, receipt, audit, revision +1).
- F4 T-1c Draft 2: stateless token `ptk1.<header>.<payload>.<mac>` (HMAC, key id, 300 s, never in a URL), minted by `POST /v1/story-runs/{id}/playback-token`, redeemed at `GET /v1/story-runs/{id}/playback` with header `X-Playback-Token` plus the live bearer; every request re-reads ownership, run state and generation. T-1a: a generation is playable when the run is `VIDEO_READY` and the generation is `READY` with technical, consistency and safety `PASSED`.

## 4. Authorization (2 reviews)

Both occurrence routes use the T-4b1 `decide_child_data` decision (exact-class `teacher` row that is `responsible_teacher_ref`; strangers, org-wide-only rows, Manager, Parent, Platform Admin, revoked assignments: uniform 404; guide, observer or non-responsible Teacher: 403) on the **current** assignment rows at each call (FR-T-14, FR-T-16 "only the current responsible Teacher"). The stream adds the checks of D6. Lock order as T-4b1 and T-4b2: occurrence `FOR UPDATE`, class `FOR SHARE`, then the Story run row `FOR SHARE` (read the run and its generation under the lock, so a concurrent cancel, unsuitable mark or completion, which take the run `FOR UPDATE`, wait or lose; no Story write and no cross-owner transaction is made, only a read lock, l.351). The Story facts come through one read-only function in `infrastructure/story_video/repository.py` (`sample_facts(run_id)`: occurrence ref, plan pin, run state, generation id and states); Lesson code does not query Story tables directly.

## 5. State machine and concurrency

Occurrence: `APPROVED -> SAMPLE_USED` at the first confirmation; slot `AVAILABLE -> CLAIMED` once. Two concurrent first confirmations (same or different run, different keys): the occurrence lock serializes them; the first claims, the second sees `CLAIMED` and either refreshes (same run) or gets 409 `SAMPLE_VIDEO_ALREADY_EXISTS` (other run). The claim update carries `WHERE sample_slot_state='AVAILABLE'` and the expected revision as a backstop. Same key twice: one write, replay (receipt-key race handled as T-3a). A confirmation racing a plan confirm (T-3d): the occurrence lock orders them; the later one sees the new pointer and refuses the old-plan run (409 `STALE_REVISION`). A confirmation racing a regeneration or an unsuitable mark: the run lock orders them. Failures before the first confirmation never touch the slot (FR-T-13).

## 8. FE, rollback, risks

FE: web Teacher result screen: "Project to class" asks the audience and use acknowledgement, calls the confirmation, then the token, and plays through the header-borne stream (the `<video src>` question is T-1c Q2); Android is unaffected. Rollback: revert the commit; the claim already written by a test database is data, not schema. Risks: R1 the claim is service-enforced only (F1); R2 a confirmation for a run of a plan that was just superseded is refused although the video is playable (D2, Q3); R3 `successful_sample_run_ref` is not cleared when a run is deleted (REG l.284 wants "delete clears the pointer, keeps the claim"); readers treat a dangling pointer as "claimed, no run" and refuse another run, and T-13a's delete does not write Lesson rows: recorded as debt; R4 audience and use are kept only in the receipt (no audit metadata column); R5 the stream change touches the T-1c authorization path, so the review covers the Parent paths too (their tests must stay green).
