## 2. SRS and decision (TD-03, draft D-066-93)

- l.814 `/health/live`, `/health/ready`, `/metrics` "Probe/metric vận hành, được bảo vệ phù hợp"; l.1711 operator dashboard shows only redacted operational metadata, no drill-down; FR-O-07 l.612 (probe, queue visibility, redacted logs for the operator in Docker Compose); §9.6 l.790 exempts "auth bootstrap/health" from authorisation (this covers `live`, and the kept `/health`).
- **Decision: the operator-credential variant of TD-03, not an internal listener.** Reason: one process, one port in this codebase; a second listener means a process manager and compose change (deployment, T0.8). Recorded as the alternative for later.
- `live`: public, `{"status":"ok"}`, no detail, no dependency call.
- `ready` and `metrics`: allowed only when one of these holds, else denied.
  1. `Authorization: Bearer <probe credential>` equals the configured operator probe credential (new optional `Settings.ops_probe_token`, `SecretStr`, minimum 32 characters when set; compared in constant time on SHA-256 digests).
  2. Only when `env` is `local` or `test`: client and server addresses are loopback, Host is local, and none of `forwarded`, `x-forwarded-for`, `x-real-ip` is present (reuse the demo guard logic, moved to a shared helper; behaviour of the demo guard unchanged).
- In `staging`/`production` only (1) applies, so a same-host reverse proxy cannot unlock them. Denial: 401 `AUTH_REQUIRED` when a credential is configured; 404 `RESOURCE_NOT_FOUND` when none can ever match (no credential, non-local). Fail closed; no log of the presented value.
- Compose note: a host curl through the published port is not loopback inside the container, so the operator uses the credential from the shared `.env`, or `docker compose exec api` (loopback). `/health` stays the compose healthcheck (S-02).

## 3. Routes and shapes

| Route | Schema | Success | Failure |
|---|---|---|---|
| `GET /health/live` | in Swagger | 200 `{"status":"ok"}` | none |
| `GET /health/ready` | `include_in_schema=False` | 200 `{"status":"ready","checks":{"database":"up"}}` | 503 `{"status":"not_ready","checks":{"database":"down"}}` |
| `GET /metrics` | `include_in_schema=False` | 200 Prometheus text 0.0.4 | access errors above |

- Ready checks: `Be1Runtime` present with an engine and no `database_error`, then `SELECT 1` on a fresh connection inside a 2 second bound (`anyio` `to_thread` plus `fail_after`); any exception or timeout is `down`. Body never carries exception text, host, URL or credentials. Non-critical dependencies (storage, scanner, identity provider) are not probed in this task (open question 1). `Cache-Control: no-store`.
- Metrics, hand-written exposition (no new dependency): `sketch2life_build_info{service}`, `sketch2life_process_start_time_seconds`, `sketch2life_http_requests_total{method,status_class}` (method from a fixed set else `OTHER`; class `1xx..5xx`), `sketch2life_http_request_duration_seconds` histogram with fixed buckets and no labels, `sketch2life_http_requests_in_flight`. No route, path, user, organization, run or job label; no unmatched-path label; no business counts (aggregates are X-11). Per-process registry behind a lock (single worker per Dockerfile; state this in the HELP text).
- `/health` and `/api/be1/v1/health` untouched. No DDL.
