## 4. Authorization and concurrency

Lock order of the confirmation: occurrence `FOR UPDATE`, class `FOR SHARE`, the caller facts and the decision re-read under the locks (T-4b1 pattern), then the Story run row `FOR SHARE` through `sample_facts` (a concurrent cancel, unsuitable mark or complete takes the run `FOR UPDATE` and waits or loses; Lesson code writes no Story row). The Story side reads the occurrence with a plain read (no row lock); T-4b2 create takes occurrence `FOR SHARE`, class `FOR SHARE`, selection, then inserts a new run; the Story commands lock the run first and the assignment and class `FOR SHARE` after it. No cycle: the only waiter on a run lock from the Lesson side holds an occurrence lock that no Story code requests. Two concurrent first confirmations (different keys, same or different run): the occurrence lock serialises them, exactly one claims; the loser refreshes or no-ops (same run) or gets 409 `SAMPLE_VIDEO_ALREADY_EXISTS` (other run). Same key twice: one write, replay (a receipt-key `IntegrityError` rolls back and replays). A confirmation racing a plan confirm: the occurrence lock orders them (D2: an old-plan run is still accepted). Failures before the first confirmation never touch the slot (FR-T-13).
