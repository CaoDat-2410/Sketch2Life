## 3. Authorization and concurrency (2 reviews)

Both occurrence routes use the T-4b1 `decide_child_data` decision on the CURRENT assignment rows at each call (FR-T-14, FR-T-16 "only the current responsible Teacher"): uncovered, revoked, Manager, Parent, Platform Admin: uniform 404; rows that cover the class without an exact-class `teacher` row (org-wide, guide, observer) or a non-responsible Teacher: 403 (aligned with T-7a2). **Order:** occurrence `FOR UPDATE`, class `FOR SHARE`, **caller facts and the decision re-read under the locks**, then the Story run row `FOR SHARE` through `sample_facts` (a concurrent cancel, unsuitable mark or completion takes the run `FOR UPDATE` and waits or loses; no Story write, no cross-owner transaction, only a read lock, l.351). Deadlock check (R1 F-9): the Story commands (T-1b, T-1d1, T-13a and the T-4b2 retrofit) take the run lock and never lock the occurrence; the Story-side access rule reads the occurrence with a plain read (no row lock, so it never waits on the `FOR UPDATE` of this task); T-4b2 create takes occurrence `FOR SHARE`, class `FOR SHARE`, selection, and inserts a new run row. The confirmation is the only writer; the claim update carries `WHERE sample_slot_state='AVAILABLE'` and the expected revision as a backstop. Two concurrent first confirmations (same or different run, different keys): the occurrence lock serializes them; the first claims, the second sees `CLAIMED` and either refreshes (same run) or gets 409 `SAMPLE_VIDEO_ALREADY_EXISTS` (other run). Same key twice: one write, replay (a receipt-key race is handled as in T-3a, IntegrityError, rollback, replay). A confirmation racing a plan confirm (T-3d): the occurrence lock orders them; the later one sees the new pointer, and under D2 a run of the old plan is still accepted. A confirmation racing a regeneration or an unsuitable mark: the run lock orders them. Failures before the first confirmation never touch the slot (FR-T-13).

## 7. FE, rollback, risks

FE: web Teacher result screen: "Project to class" asks the audience and use acknowledgement, calls the confirmation, then the token, and plays through the header-borne stream (the `<video src>` question is T-1c Q2); **the web must project before pressing Complete** (a completed run can no longer be projected, OPEN-2 with T-4b2 D6); a repeat confirmation ends the tokens of the earlier one; Android is unaffected (Parent paths unchanged). ## 8. OPEN questions
