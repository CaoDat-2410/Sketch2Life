## 1. HEAD facts (verified in `infrastructure/lesson_library/service.py`)

- **Create side:** `create_access_grant` (:1167-1254): `PUBLIC` makes a `PENDING_REVIEW` grant and sets the version `PENDING_REVIEW`; **every other audience** (`ORGANIZATION`, `PRINCIPAL`, `PARENT_GROUP`) is refused at :1189-1190 with 409 `PUBLICATION_REQUIRED` unless `version.review_state == "APPROVED"`.
- A version becomes `APPROVED` only in `decide_access_grant` (:1282-1342, Manager approval of a PUBLIC grant; a refusal sets `CHANGES_REQUESTED`). Versions are inserted `DRAFT` (:159, :258, :373). States: `DRAFT, PENDING_REVIEW, CHANGES_REQUESTED, APPROVED` (`tables.py:186`). Hence a Teacher cannot share privately before a public approval: the defect.
- **Read side repeats the gate:** `_parent_access_rows` (:1857-1954) has `LIBRARY_VERSIONS.c.review_state == "APPROVED"` in the base statement (:1885, shared by the `PUBLIC` and `PRINCIPAL` branches) and in the `PARENT_GROUP` statement (:1932). Parent list, get, export, activity catalog and the Parent StoryRun lesson pin (`get_parent_lesson`) all go through it, so fixing only the create side would create shares nobody can read.
- Invitation list, accept, decline and group membership code do not look at `review_state`.
- **Other `APPROVED` consumers outside T-10d (T10D-01):** `lesson_occurrences/service.py:164-211` (`resolve_lesson_pin`: occurrence create with a lesson pin answers 409 `INVALID_STATE_TRANSITION` unless the version is `APPROVED`, T-3a-DEC-6) and `lesson_occurrences/plans.py:291-322` (plan activity copy repeats it). They are the Teacher-side use of a lesson as a preset (FR-T-08 l.547, l.2563). The SRS does not require Manager approval for a Teacher pin (BR-53 concerns AI outputs), so this is a product question, not an SRS violation.
- Existing tests approve the PUBLIC grant before sharing (`test_lesson_library_api.py:710`, `:801`, helper at :470; the share cases are around :813-935), so none pins the gate. `PUBLICATION_REQUIRED` is in `error_envelope.py:185`'s domain-code list only. `apps/web/src/shared/api/backendApi.tsx:193` has only the `review_state` type; web UI gating on it was not checked beyond that grep (NOT CHECKED). The pinned contract draft `LESSON_LIBRARY_API_CONTRACT_DRAFT_REV29_20261028.md` still lists the 409: left untouched, staleness recorded.

## 2. Decisions

| ID | Decision | SRS basis |
|---|---|---|
| D1 | **Only PUBLIC needs a Manager decision.** `create_access_grant` for `ORGANIZATION`, `PRINCIPAL`, `PARENT_GROUP` no longer reads `review_state`; a version in any state (including `DRAFT`) can be shared privately. The basis is the SRS, not TD-24's word "reviewed", which no version state expresses: a persisted version is written only by its author (`created_by == actor` already required) and a document-derived version comes from a source the Teacher confirmed (`create_lesson_version`, :386). No AI path writes versions (X-10). | FR-PL-05 l.2646, FR-PL-06 l.2647, BR-51 |
| D2 | Every other create gate stays: author only (404 `LESSON_NOT_FOUND`), lesson `ACTIVE`, version belongs to the lesson (404), expiry in the future (422), no share to self (422), `ORGANIZATION` audience equals the caller's organization (404), group `active` (409 `INVALID_TRANSITION`), `PUBLIC` takes no audience ref (422); key, `If-Match`, receipts unchanged. | l.2647 |
| D3 | A private grant does not read or write `review_state`. A version in `PENDING_REVIEW` (public request open) or `CHANGES_REQUESTED` (Manager declined PUBLIC) stays privately shareable and shared; a later PUBLIC decision never alters private grants. | FR-PL-05 |
| D4 | **Parent read side follows:** the `APPROVED` condition moves to the `PUBLIC` branch statement only; the `PRINCIPAL` and `PARENT_GROUP` statements drop it. Everything else unchanged: grant `ACTIVE` and unexpired, capability, lesson `ACTIVE`, `moderation_state == "VISIBLE"` (a Platform Admin hide ends access), membership and group `active`, newest granted version per lesson. | FR-PL-04 l.2645, FR-PL-06 |
| D5 | "Submit for review" stays the PUBLIC grant request (TD-12): the OpenAPI `purpose` text of the create-grant operation says so and that private audiences need no approval. | TD-12 |
| D6 | **OWNER-VISIBLE (TD-24):** the SRS settles the rule, so the task proceeds on it (ground rule 1) and the report lists the behaviour change: before, a Teacher needed a public approval to share with a Parent group, a named Parent or the school; after, only PUBLIC needs it. | l.2646-2647 |
| D7 | `PUBLICATION_REQUIRED` becomes unused; it stays in `error_envelope.py` (hot file untouched) as removable debt. | |
| D8 | **Occurrence pin and plan activity copy keep their `APPROVED` gate** (T-3a/T-3d behaviour): T-10d does not change them. A regression test shows that a privately shared `DRAFT` version is still refused for an occurrence pin with 409 `INVALID_STATE_TRANSITION`, so the gap is visible, not accidental. Q-3. | FR-T-08 l.547 |

## 4. State machine

Version `review_state`: `DRAFT -> PENDING_REVIEW` (PUBLIC grant created) `-> APPROVED | CHANGES_REQUESTED` (Manager decision). Private grants (`INVITED -> ACTIVE` for a person, `ACTIVE` for group or school) neither read nor write it. Grant states untouched.

## 7. FE impact, rollback, risks

R1 Parents may read a version the Manager asked to change (D3): intended. R2 No explicit "Teacher reviewed" flag exists: "reviewed" is authorship plus document confirmation; a future AI-drafted version (X-10, BR-53) needs its own confirm state before it can use this path (T-10b hand-off). R3 The `PRINCIPAL` audience is not validated as an active Parent account and has no organization check (:1193-1196), and a group share is `ACTIVE` at once for all active members: a latent gap behind the old gate, now live; recorded for the evidence note, T-10c area (deferred), no change here.
