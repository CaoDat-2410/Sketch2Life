## 4. Authorization (2 reviews)

New pure decision `decide_child_data(rows, class_id, caller_account_ref, responsible_teacher_ref)` in `domain/lesson_occurrences/child_selection.py`, aligned with the T-7a2 coordinator ruling (goal log: 404 when the caller's rows do not cover the class or were revoked; 403 when they cover it but the caller is not the class assignee):

| Caller | Outcome |
|---|---|
| no active Teacher identity (stranger, other organization, Manager, Parent, Platform Admin) or no active row in the organization or a revoked assignment | 404 `RESOURCE_NOT_FOUND` (uniform with an unknown id) |
| rows that do not cover the class (rows for other classes only) | 404 |
| rows cover the class but there is no exact-class `teacher` row (an org-wide `teacher` row, a `guide`, an `observer`) | 403 `ACTION_NOT_ALLOWED`, no child data in the body |
| an exact-class `teacher` row but `responsible_teacher_ref` is another account | 403 |
| an exact-class `teacher` row and the caller is `responsible_teacher_ref` | proceed |

This is stricter than `decide_write` for child data on purpose (an org-wide row does not give child access, FR-T-14) and answers the same status family as T-7a2 for a covered caller, so there is no divergence between `GET` of an occurrence (200) and child data (403). `TEACHER_ASSIGNMENT_REQUIRED` (409) is not used on existing-occurrence routes (the T-3 helpers use it only for create-by-class). The check runs on **every** command and read on the CURRENT assignment rows: facts are read, the occurrence is locked, the class is locked `FOR SHARE`, then the facts and the decision are **re-read and re-decided under the locks** (FR-T-14, l.553; R1 F-12a). A revoked assignment is 404 at the next call; a confirmed selection of a former Teacher cannot be used (T-4b2 re-checks). The Manager never receives names or ids (O-PRIV, T-7a).

## 5. Concurrency

All commands take the occurrence `FOR UPDATE`, then the class `FOR SHARE` (lock order shared with T-4b2 and T-5a: occurrence, class, selection, story run), so two selections of one occurrence serialize: the second sees the first's live row (case a). The confirm is `UPDATE ... WHERE state='OPEN' AND revision=:n AND expires_at>:now`; two confirms: one wins, the other replays by key or gets 409. Backstops in the database: `uq_sel_live` (one live row per occurrence) and `uq_sel_draw` (at most one `DRAW` and one `RESELECT` per occurrence). **An `IntegrityError` on either index (or on the receipt key) rolls back and re-runs the command ONCE; a second failure is 409 `INVALID_STATE_TRANSITION`; it is never a 500** (R1 F-2).
