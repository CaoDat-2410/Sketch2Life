## 2. Decisions

- D1 (recovery, owner decision; deviation T2DF-DEV-1 from l.1413 "out of technical retries marks the run failed", l.1413 is the story flow; BR-17 l.261 and FR-AI-06 l.572 are scene rules, no conflict): a rewrite generation that fails technically (`StoryGenerationFailure`, invalid draft, K4/K5) keeps the run: `SCRIPT_GENERATING -> SCRIPT_REVIEW` (l.394), `job_state FAILED`, safe `error_code`, `retryable`. Every failure writer is a compare-and-set under the run lock: run state `SCRIPT_GENERATING` (the unknown writer too) AND a row with exactly the reservation's `story_revision_id` still `GENERATING`; otherwise it changes nothing and raises 409 `INVALID_STATE_TRANSITION` (the runner already treats that as discarded); the purge guard stays first (existing tests expect it with no statement). The terminal fallback (revision `FAILED`, run `FAILED`, lock released, `finished_at` set, `adult_wait_started_at` NULL) applies only when the row IS still `GENERATING` and there is no previous story to return to (first story or legacy), never when the row is gone. `fail_drawing_analysis` gets `expected_input_revision` (runner passes it) and requires `INPUT_PROCESSING`, an in-flight `job_state` and the input unchanged; `fail_drawing_analysis_recoverable` also requires an in-flight `job_state`; `_finish_transcript` already requires `PENDING`. Late `complete_story_revision` is already refused (no `GENERATING` row of that id); add the run-state check.
- D2 (slot rule, OPEN Q1, SRS is ambiguous not silent): l.378 "at most three rewrite requests after the first" and l.2350 "three rewrites accepted, fourth denied" (accepted = the 202) read as requests; l.405, l.1025, FR-P-07 l.516 "three rewrites" and "a revision is immutable" (a failed attempt makes none) read as revisions; the video counters are explicitly accepted-request based because they cost quota (l.405, l.1024, l.1907). Conservative choice: a failed attempt does not consume a slot, at most 3 attempts per slot, so at most 9 rewrite generations per run (text, no GPU). Counted from existing receipts: a FINAL 202 receipt of this actor, operation `GENERATE_STORY_REVISION`, run scope, body `story_revision_no = k`; precondition: receipts are not pruned during a run. The 4th attempt (and a revision count of 4) is 409 `STORY_REWRITE_LIMIT_REACHED` (§9.8 l.866; l.1728: keep the story, confirm or cancel); the client sees "limit reached" although no rewrite was used, so the FE rule is `retryable false` + that code = confirm or cancel. This is an interim second retry ledger beside `ai_jobs.attempt` (l.1790) until OD-13.
- D3 (no DDL, supersede late): the new route no longer supersedes the previous revision at reserve; `complete_story_revision` supersedes `revision_no - 1` (`DRAFT`, or `CONFIRMED` after a rejected video) in the same transaction. A failed attempt therefore only deletes its own row (`GENERATING`/`AWAITING_RECONCILIATION`, no content, no children, no trigger) and the story tree is exactly as before; works after T-1b's rejected-video start too (the run stays at `SCRIPT_REVIEW` with the `CONFIRMED` story and its rejected video; the next rewrite is allowed by the same T-1b rule). The legacy route keeps its reserve-time supersede. Keeping the failed row is impossible without DDL (`uq_story_revision_run_no`, `ck_story_revision_no`); not planned, would be BLOCKED_GATE.
- D4 (durable trace, no DDL, BR-34 l.278): each recovery, terminal timeout and reaper action writes one `core_audit_entries` row: scope `PARENT_ACCOUNT` + the run's owner ref, `actor_ref` the owner scope (runner path) or `system:story-task-reaper`, `action` one of `STORY_REWRITE_ATTEMPT_FAILED`, `STORY_TASK_TIMED_OUT_DRAWING|TRANSCRIPT|STORY`, `resource_type` `story_run`, `resource_id` the run id, `decision` the safe code; deterministic `audit_id` (uuid5 of run id, action, new revision), `on_conflict_do_nothing`. No story, hint, transcript or error text.
- D5 first story and legacy (OPEN Q3): no previous story, so failure stays terminal `FAILED` (l.1413).
- D6 unknown outcome (OPEN Q4): the runner's `SCRIPT_GENERATION_UNKNOWN`/drawing `AWAITING_RECONCILIATION` (l.398, l.1748) is unchanged; the reaper resolves it at the 6 h AI job deadline (l.394, l.615, l.988). After K5 the adult may start a new attempt while the first outcome stays unknown; that is adult-initiated after the hard deadline, not a blind repeat; a late result is refused as stale.
- D7 reaper and limits: `StoryTaskReaperService.run_once(now, lease, unknown_deadline, batch_size)`. Only the 6 h deadline is licensed by the SRS (l.394, l.615 FR-O-10, l.988); a shorter lease for QUEUED/RUNNING has no SRS number (FR-O-06 l.611: per stage, needs benchmark), so `lease` is a required argument (no default, `0 < lease <= AI_JOB_DEADLINE`) and the future scheduler passes 6 h unless the owner sets less (OPEN Q2). `unknown_deadline` defaults to 6 h; `batch_size` 1..200.
- D8 vocabulary: timeouts use the existing `PROVIDER_TIMEOUT` (`ai_jobs`, `learning_media`); it is not in §9.8 (async codes are safe codes on the job, l.875), GET run returns only the code, the FE maps its text (the English `public_message` is not returned).
- D9 (stale fields): `confirm_story_revision` also sets `retryable false`, `error_code NULL`; `reserve_story_rewrite` already clears the code. The video paths already clear both.
- D10 pattern reuse: T-1a `reconcile_pending_admissions` (listing then compare-and-set, counters) and the T-1d1 sweep conventions (bounded ordered listings with no content columns, `FOR UPDATE SKIP LOCKED` on the run, re-check under the lock, compare-and-set on `revision` and state, one transaction per run, counts-only report, Parent scope only, injected `now`).
- DEV-2 (`T2DF-DEV-2`, owner-visible): the reaper edits business rows although the ops runbook l.2082 says a lost worker alert should check the worker "and not auto-fix business rows". The owner directive authorises it; it is a stopgap that OD-13 replaces with `ai_jobs` leases (l.1780), and every action leaves an audit row (D4).

## 3. Stuck states, detection, transition (compare-and-set per row)

Candidate listing: `PARENT_ACCOUNT`, run not purged, ordered by clock, bounded; each row re-read `FOR UPDATE SKIP LOCKED` (busy or changed = `skipped`), state, job state, clock and `revision` re-checked.

| Kind | Detected | Becomes |
|---|---|---|
| K1 drawing lost | `INPUT_PROCESSING`, job QUEUED/RUNNING, `updated_at <= now - lease` | `job_state FAILED`, `retryable true`, `PROVIDER_TIMEOUT`, `_apply_settle`: `INPUT_REVIEW` (retake) or `SUBJECT_REVIEW` for a lost rerun; `updated_at = now` starts the wait |
| K2 drawing unknown | same state, job `AWAITING_RECONCILIATION`, `updated_at <= now - unknown_deadline` | as K1 |
| K3 ASR lost | run `INPUT_PROCESSING` and transcript `PENDING`, `created_at <= now - lease` | transcript `FAILED` (`PROVIDER_TIMEOUT`), run bump, `_apply_settle` |
| K4 story lost | `SCRIPT_GENERATING`, QUEUED/RUNNING, `updated_at <= now - lease`, a `GENERATING` row | rewrite: D1 recovery; first story or legacy: terminal `FAILED` as in D1 and the PENDING legacy receipt (same actor, operation, run scope, at most one) finalised 502 |
| K5 story unknown | `SCRIPT_GENERATION_UNKNOWN`, `updated_at <= now - unknown_deadline`, an `AWAITING_RECONCILIATION` row | as K4 |

Rewrite discriminator: the runner path uses `reservation.receipt_id is None and revision_no >= 2`; the reaper path (no reservation) finds a FINAL 202 receipt whose body `story_revision_id` is the row's id. D1 recovery (one repository method for both): delete the row (rowcount 1), run `SCRIPT_REVIEW`, `job_state FAILED`, `error_code`, `retryable = failed attempts for the slot < 3`, lock kept, `version`/`revision` +1, `updated_at = now`, audit row. Transitions new to the model: `SCRIPT_GENERATING -> SCRIPT_REVIEW` with a failed job and `SCRIPT_GENERATION_UNKNOWN -> SCRIPT_REVIEW|FAILED`; `INPUT_PROCESSING -> INPUT_REVIEW` after a timeout exists today. Terminal rows also set `finished_at = now` and `adult_wait_started_at` NULL (as the T-1d1 close and the video failure path do).

Late worker versus reaper: both lock the run row. Worker first: the run left the state, the reaper skips. Reaper first: a late `complete`, a late known or unknown `fail_story_revision`, a late `fail_drawing_analysis` or `record_understanding` find another state or no `GENERATING` row of that id (also after a new attempt: new id) and change nothing. A second pass finds nothing (idempotent). Known limit: a late result of the first job of a same-drawing rerun is accepted for the second (no job identity until OD-13).

## 4. What the Parent sees (GET run, no schema change)

After a failed rewrite: `run_state SCRIPT_REVIEW`, the previous `story_revision_no`, `story_status`, story content, `job_state FAILED`, `retryable`, `error_code`; next `story-rewrites` with the same `expected_story_revision` and a new key is attempt 2 of the slot. The stored 202 of the failed key replays with the now-deleted `story_revision_id` (a dangling id: clients read GET run). FE rule for the Phase B FE fixes: banner from `job_state FAILED` in `SCRIPT_REVIEW`, retry only when `retryable`; the mobile flow does not treat `FAILED` as in flight.
