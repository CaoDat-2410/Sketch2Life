# V3 T-10d plan, Draft 1: private sharing must not depend on the PUBLIC approval (approved-version gate defect)

Date 2026-11-19. Goal v3 Phase C. Facts read at HEAD 6696e888 (the Lesson Library files have no uncommitted change). Source: Draft 5 WP-10 "T-10d basis", P-22a (AUD-T#33, SM-23), TD-24, TD-12; SRS FR-PL-04 l.2645, FR-PL-05 l.2646, FR-PL-06 l.2647, BR-51 l.2676, BR-53 l.2678, BR-58 l.2683, §31.2 l.2553-2557. Status: plan, not implemented, not reviewed.
**Owner scope rule:** no capacity, subscription, quota, billing or payment code. No route is added, removed or reshaped. **Review rule: 2 reviews** (it widens who can read a lesson version: a Parent-visible access gate, and a 409 that clients may see becomes a 201). No DDL.

## 1. HEAD facts (verified in `infrastructure/lesson_library/service.py`)

- `create_access_grant` (`:1167-1254`): for `PUBLIC` the grant is `PENDING_REVIEW` and the version moves to `PENDING_REVIEW`; **for every other audience** (`ORGANIZATION`, `PRINCIPAL`, `PARENT_GROUP`) line `:1189-1190` refuses with 409 `PUBLICATION_REQUIRED` unless `version.review_state == "APPROVED"`.
- A version becomes `APPROVED` only in `decide_access_grant` (`:1282-1342`): a Manager approval of a `PUBLIC` grant sets `review_state="APPROVED"` (a refusal sets `CHANGES_REQUESTED`). Versions are inserted as `DRAFT` (`:159`, `:258`, `:373`) and the review states are `DRAFT, PENDING_REVIEW, CHANGES_REQUESTED, APPROVED` (`tables.py:186`). So a Teacher cannot share privately before a Manager approves a public release, which is the defect.
- **The read side repeats the gate:** `_parent_access_rows` (`:1857-1954`) filters `LIBRARY_VERSIONS.c.review_state == "APPROVED"` in the base statement (`:1885`, used by the `PUBLIC` and `PRINCIPAL` branches) and in the `PARENT_GROUP` statement (`:1932`). Removing only the create-side gate would let a share be created that the Parent can never list, open or export (`list_parent_lessons`, `get_parent_lesson`, `get_parent_lesson_export`, the activity catalog and the Parent StoryRun lesson pin all go through it).
- Invitation list, accept and decline (`:1774-1855`) and group membership code do not look at `review_state`.
- Existing tests all approve the PUBLIC grant before sharing (`integration/lesson_library/test_lesson_library_api.py:790-850`, `_approve_public_grant`), so none pins the gate. `PUBLICATION_REQUIRED` is in the error envelope's domain-code list (`error_envelope.py:185`) and in no test, mobile or web source (`apps/web/src` has only the `review_state` type in `shared/api/backendApi.tsx:193`; the web UI gating on `review_state` was not checked beyond that grep: NOT CHECKED).

## 2. Decisions

| ID | Decision | SRS basis |
|---|---|---|
| D1 | **Only the PUBLIC audience needs a Manager decision.** `create_access_grant` for `ORGANIZATION`, `PRINCIPAL` and `PARENT_GROUP` no longer reads `review_state`. "Reviewed" (TD-24) is satisfied by authorship: a persisted version is written only by its author (`item.created_by == actor` is already required), and a document-derived version is created from a source document that the Teacher reviewed and confirmed (`create_lesson_version` marks the document revision `CONFIRMED`, `:386`). No AI path writes versions today (X-10). | FR-PL-05 l.2646 (Manager approval only for PUBLIC), FR-PL-06 l.2647, BR-51, BR-58 |
| D2 | **Every other gate stays:** author only (404 `LESSON_NOT_FOUND` for others), lesson `ACTIVE`, version belongs to the lesson (404), expiry in the future (422), no share to the author's own account (422), `ORGANIZATION` audience must be the caller's organization (404), group must be `active` (409 `INVALID_TRANSITION`), `PUBLIC` takes no audience ref (422). The creation key, `If-Match` and receipts are unchanged. | l.2647 |
| D3 | **Version state is left alone by a private grant.** A private grant does not change `review_state`; a version in `DRAFT`, `PENDING_REVIEW` (a public request is open) or `CHANGES_REQUESTED` (the Manager declined the public release) can be shared privately and stays shared. A later PUBLIC decision does not revoke or alter private grants. | FR-PL-05, BR-51 |
| D4 | **Read side follows (Parent):** `_parent_access_rows` keeps `review_state == "APPROVED"` **only for the `PUBLIC` branch** (an active PUBLIC grant exists only after approval, so this is defence in depth). The `PRINCIPAL` and `PARENT_GROUP` branches drop it. Everything else in those statements is unchanged: grant `ACTIVE` and not expired, capability, lesson `ACTIVE`, `moderation_state == "VISIBLE"` (a Platform Admin hide still ends access), membership and group `active` for groups, the "latest granted version per lesson" rule. The base statement is split so the APPROVED condition sits on the public statement only. | FR-PL-04 l.2645, FR-PL-06 l.2647 |
| D5 | **"Submit for review" stays the PUBLIC grant request** (TD-12): the OpenAPI `purpose` text of the create-grant operation says so and that private audiences need no approval. No new route. | TD-12 |
| D6 | **Owner confirmation:** TD-24 asks the owner to confirm. The SRS settles the rule (Manager approval for PUBLIC only), so the task proceeds on the SRS (ground rule 1) and the final report lists the change as OWNER-VISIBLE: before, a Teacher needed a public approval to share with a Parent group or person; after, no approval is needed for private audiences. | l.2646-2647 |
| D7 | The error code `PUBLICATION_REQUIRED` becomes unused by the service; it stays in `error_envelope.py` (no edit of that hot file) and is recorded as removable debt. | |

## 4. State machine

Version `review_state`: `DRAFT -> PENDING_REVIEW` (PUBLIC grant created) `-> APPROVED | CHANGES_REQUESTED` (Manager decision). **Private grants (`INVITED` -> `ACTIVE` for a person, `ACTIVE` for a group or school) do not read or write it.** Grant states are untouched.
