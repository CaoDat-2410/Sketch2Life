## 1. HEAD facts

- Legacy route `POST /api/parent/v1/ai/drawing-understandings` (`parent_ai.py:232`): base64, `modal_dev` gate, synchronous Modal call; `attach_artwork` inserts the original **and** derived asset rows. After T-2a the original row already exists (upload `complete`: key `parent/{run}/{token}/original`, version 1, `source_refs=[run]`, Parent scope), so `attach_artwork` cannot be reused for the original.
- `resolve_asset_key` (`uploads/service.py:156`) checks scope only, not target, purpose, hash or scanner identity.
- Run store: `_owned_run` raises 404 `RESOURCE_NOT_FOUND` for unknown or foreign runs; `ensure_accepting_artwork` accepts only `INPUT_PROCESSING`; `ck_story_run_state` has **no `INPUT_REVIEW`** (added by T-2c's DDL-B1); for a known VLM failure `fail_drawing_analysis` writes `FAILED` (terminal, frees the Parent's active slot, `parent_story_repository.py:1580-1586`); receipt operation `ATTACH_ASSET` exists.
- Modal worker contract: `MAX_IMAGE_PIXELS = 2_000_000`; DB limits original at most 20 MiB, derived at most 5,000,000 bytes.
- The StoryRun-lite demo owns `POST /v1/story-runs/{run_ref}/assets`; real and demo routes are mutually exclusive (`include_parent_story_runs`, T0.5 guard).
- Android still calls the legacy route (`ParentApi.ts:374`) and has no code for the new one.
- Story envelope (`app.py:485-548`): `current_version` only on the cancel path, `field_errors` hard-coded `None`, unknown codes get one generic message.

## 2. Decisions (SRS-cited)

- **T2B-D1 Route and mount (l.1664).** New module `routers/parent_story_inputs.py`, prefix `/v1/story-runs`, tag `Parent StoryRuns`, mounted under `include_parent_story_runs` and listed in `story_demo_replaced_routers()`. T-2c and T-2d add routes to it; `parent_story_runs.py` is not edited by T-2b.
- **T2B-D2 Actor, 404 rule, asset lookup (l.1664, l.864-865, l.1637, l.1692, CV-5).** Parent only. The guard is the T0.9 helper imported from the module that holds it (not copied), and a wrong role, inactive account or issuer mismatch answers 404 `RESOURCE_NOT_FOUND` even if T0.9's OD-18b branch were absent (a new route has no 403 to preserve). Run by `_owned_run`. Asset by a new additive helper `resolve_completed_upload(db, handle, owner scope, target_ref=run_id)` next to `resolve_asset_key`: purpose `RUN_ARTWORK`, state `COMPLETED`, target equal to this run, caller scope, `scan_verdict CLEAN`; it returns key, size, SHA-256, media type, scanner name and version. Every miss (other actor, other run, lesson asset, physical key, unknown id) is the same 404. One exception that leaks nothing: the caller's own, same-run, completed `RUN_AUDIO` session answers 415 `UNSUPPORTED_MEDIA_TYPE` (none can exist until T-2c enables audio; tested in T-2c). No client-supplied owner, key or URL is read.
- **T2B-D3 Request, keys, purged runs (l.1664, l.1697, l.1699, DTR 6.5, l.1472).** Body `AttachRunAssetRequestV1`, `extra=forbid`: `asset_ref` (`^upl_[0-9a-f-]{36}$`), optional `expected_run_revision` (l.1664 lists none; a sent value that differs gives 409 `STALE_REVISION` with `current_version`). `Idempotency-Key` required, `parse_idempotency_key` (1-128) after the role check and before the run lookup. Receipt `ATTACH_ASSET`, scope `STORY_RUN/{id}`, fingerprint over `{asset_ref, expected_run_revision}`; replay re-authorizes and returns the stored 202; another body with the key is 400 `INVALID_IDEMPOTENCY_KEY`. A fresh command on `DELETE_PENDING` or `DELETED` is 409 `INVALID_STATE_TRANSITION`; a replay of an earlier receipt on a purged run returns the content-free lifecycle projection under the route's normal status (model after `confirm_subject`, `parent_story_repository.py:1033-1040`); the response model is the union `ParentRunAssetAcceptedV1 | ParentStoryRunLifecycleEnvelopeV1`. No DDL.
- **T2B-D4 State rule and retake (FR-P-02 l.511, FR-P-12 l.521, l.394, WP-2 rules).** First drawing: `INPUT_PROCESSING`, no drawing attached. One retake, at most one earlier retake: eligible when the run is in `SUBJECT_REVIEW` (subject not yet confirmed), or in `INPUT_PROCESSING` with `job_state = 'FAILED'` and a drawing attached (the recoverable failure of D7). The same predicate is used by `ensure_accepting_artwork`, so the retake upload can be created. Any other state, a second retake, or the same asset again (another key) is 409 `INVALID_STATE_TRANSITION`. A retake writes input revision N+1 (older inputs and understandings stay as history; typed idea, context snapshot and its confirmation are copied forward) and returns the run to `INPUT_PROCESSING`, `job_state QUEUED`. T-2c moves the failure and retake state from `INPUT_PROCESSING/FAILED` to `INPUT_REVIEW` (l.394) and updates the predicate. **Assumption recorded (Q-2b-1, FR-P-12):** the retake is capped at one but not limited to a topic mismatch, because the mismatch warning has no client field yet.
- **T2B-D5 Normalization (l.983, l.1942, l.1943).** Source read through `ObjectStoragePort`; size and SHA-256 recomputed (mismatch 422 `UPLOAD_CHECKSUM_MISMATCH`, missing object 422 `UPLOAD_INCOMPLETE`, storage fault 503 `STORAGE_UNAVAILABLE`). Pillow: dimensions are read lazily first and more than 40,000,000 pixels is 422 `IMAGE_DIMENSIONS_EXCEEDED` before any decode; the limit is enforced by that check and a per-call guard, **never by mutating the process-global `Image.MAX_IMAGE_PIXELS`**; a bomb error maps to the same code; an undecodable stream is 422 `UPLOAD_CONTENT_MISMATCH`. Derived asset: EXIF orientation applied, RGB PNG, scaled down (never up) to at most 2,000,000 pixels with a three-step ladder if the PNG exceeds 5,000,000 bytes, else 422 `IMAGE_DIMENSIONS_EXCEEDED` (documented: the decoded image is too large for the normalized limit). The original is never resized. WebP accepted. Decode runs in the API process; l.1942 asks for an isolated worker (a proposal for the synthetic demo): parked as hardening, like T-2a-IR-07. Module `infrastructure/story_inputs/drawing.py`; no Modal import.
- **T2B-D6 Persistence and concurrency (FR-C-08, l.1692).** `SqlParentStoryRunRepository.attach_uploaded_drawing(...)`: take the run row `FOR UPDATE`, refuse purged runs, then re-check state, retake count and "same asset already attached" **before** any `put_object`; only then put the derived object, insert its `CoreAssetMetadataModel` (key `parent/{run}/{token}/normalized.png`, same UUIDv5 token as the original, `derived_from_ref` = original key, Parent scope, `source_refs=[run]`), one `core_asset_lineage` row (`NORMALIZE_DRAWING_IMAGE`, `PILLOW_RGB_PNG_V2`, scanner identity from the session through `scanner_identity_sha256`, T-2a-DEC-7), the new `run_inputs` revision (copy-forward of every column the table has; a unit test compares the column set of each `run_inputs` insert with the table so a later column cannot be forgotten), the run update (`job_state QUEUED`, version and revision +1) and the receipt, in one commit. Cleanup after a failed commit deletes the derived object **only when no `core_asset_metadata` row references that key after the rollback** (the deterministic key may belong to a committed winner). The original row is untouched. Purge: both assets carry `source_refs=[run]`; a test proves the plan stays removable.
- **T2B-D7 VLM step behind a port (OD-13, l.394, FR-P-04).** Port `DrawingAnalyzerPort.analyze(request) -> result` (subject, up to 4 features, confidence, `child_count`, `topic_compatible`) in `application/ports/parent_story_inputs.py`; `FixtureDrawingAnalyzer` answers only for an explicit mapping of derived SHA-256 to a result (unknown input is a recoverable failure, never an invented answer). `app.state.drawing_analyzer` defaults to `None`: the run then stays `INPUT_PROCESSING`/`QUEUED`, with no timeout or reaper (the user can cancel; OD-13 owns a real worker). When composed, `ParentInputJobRunner` runs after the response through `BackgroundTasks` **with its own session from the session factory** (request dependencies are closed by then), sets `RUNNING`, and calls the existing `record_understanding` (new optional `expected_input_revision`, so a result for a replaced drawing is discarded) or a new `fail_drawing_analysis_recoverable`. `child_count > 1`: code `MULTI_CHILD_NOT_SUPPORTED` (l.871) as the run's `error_code`, the run stays `INPUT_PROCESSING` with `job_state FAILED`, `retryable true`, **active slot kept** (not the terminal `FAILED` of `fail_drawing_analysis`), retake allowed once (D4). A topic mismatch is stored as `warnings` beside `result` in the understanding snapshot (the `candidate` body forbids extra keys). The 422 for multi-child is the job's outcome, not this route's synchronous answer (l.1664 returns only asset ref and validation state). No Modal call is added.
- **T2B-D8 Response (l.1664).** 202 `ParentRunAssetAcceptedV1 {request_id, story_run_id, asset_ref, asset_kind "DRAWING", asset_state "READY", input_revision, run_revision, run_state, analysis_state QUEUED|RUNNING|SUCCEEDED|FAILED|AWAITING_RECONCILIATION}` plus `Content-Location: /v1/story-runs/{id}`. **No `job` field**: l.1664 does not ask for one; the client follows the VLM step through `GET /v1/story-runs/{id}` (`job_state`, `error_code`; l.780, l.1811). `job_state` after attach is `QUEUED` (the legacy `attach_artwork` writes `RUNNING`; the runner sets `RUNNING` when it starts).
- **T2B-D9 Legacy route stays (P-06b).** Android has not moved (`ParentApi.ts:374`); nothing is removed in v3, P-06b stays open.
- **T2B-D10 Envelope (R1 B3; shared with T-2c and T-2d).** In `app.py`, the story-envelope handler: (a) `current_version` is emitted for any `/v1/story-runs*` 409 with code `STALE_REVISION` and an int `current_version` (cancel case kept); (b) `field_errors` is passed through from `detail` when it is a list of `{field, code}` items (as the profile handler does); (c) messages for `IMAGE_DIMENSIONS_EXCEEDED`, `UPLOAD_INCOMPLETE`, `UPLOAD_CHECKSUM_MISMATCH`, `UPLOAD_CONTENT_MISMATCH`, `MEDIA_TOO_LARGE`, `STORAGE_UNAVAILABLE`. Tests in `test_http_error_envelope.py` and the contract test.
