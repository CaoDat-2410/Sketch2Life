## 2. Decisions (SRS-cited)

- **T3D-D1 Create route (l.1659, l.775, FR-T-08).** `POST /v1/lesson-occurrences/{occurrence_id}/plan-revisions`. Request (`extra=forbid`, no `str_strip_whitespace` on free text): `expected_head_revision_no` (int >= 0; 0 when no plan revision exists), optional `document_revision_ref {document_id, revision_no}`, `objectives` (1-12 strings, 1-500 chars each), `teacher_direction` (1-2000, the "hướng truyện"), optional `safety_notes` (<= 2000), `activities` (0-10, ordered). **No lesson pin field**: the plan copies the occurrence's pin (`source_lesson_version_*`) so it can never differ or retarget (REG l.355, §31.2); no `latest`. Zero activities is allowed (FR-T-10 pins an activity only "nếu có preset"); 10 is a technical cap (OQ-2). Always creates `DRAFT`, immutable content, `revision_no = head + 1`.
- **T3D-D2 Activities (FR-T-08, FR-T-09 l.548, REG l.356).** `{ "kind": "LESSON", "lesson_activity_id" }` copies the library activity of the occurrence's pinned version (must belong to that version, else 400 `INVALID_REQUEST`; with no pin, `LESSON` is refused) into `activity_snapshot` and stores its hash; `{ "kind": "CUSTOM", "title" 1-200, "description" 1-4000 }` is Teacher-written and exists only in this occurrence. `CATALOG` is refused (400) until TD-16 defines the catalog read. Order is request order (`activity_order` 1..n).
- **T3D-D3 Plan hash (l.1660 "expected plan hash", l.1699).** `content_hash = sha256(canonical_json({occurrence_id, document: {document_revision_id, text_hash}|null, objectives, teacher_direction, safety_notes, lesson_ref: {lesson_id, version_id, version_no, content_hash}|null, activities: [{order, kind, catalog_activity_ref, activity_version, title, description, snapshot_hash}]}))`, same canonical JSON algorithm as the library hash (unit test pins equality with `canonical_content_hash`). Excluded: ids of the revision, `revision_no`, timestamps, state, checklist results (the hash names the content that gets approved).
- **T3D-D4 Head fence and serialisation (l.1659 `STALE_REVISION`, l.1699).** Lock the occurrence row `FOR UPDATE`; `head = max(revision_no)`; `expected_head_revision_no != head`: 409 `STALE_REVISION` (`current_version = head`, `ETag` of the head). The document ref must be a revision of a non-deleted document of this occurrence (else 404); the occurrence must be writable (else 409 `INVALID_STATE_TRANSITION`). Validation failures are 400 `INVALID_REQUEST` with `field_errors` (C-D3), never 422.
- **T3D-D5 Confirm route (l.1660, l.548, l.775, UC-04).** `POST .../plan-revisions/{revision_no}/confirm`, body `{ "expected_plan_hash": 64 lowercase hex, "checklist": [ {activity_order, checklist_version, items:[{item_id, checked}]} ] }`, key required. Order of checks under the occurrence lock: scope and write rule (T3A-D3); receipt replay; plan row exists (404); state: `APPROVED` with the same hash returns 200 unchanged (no write), `SUPERSEDED` 409 `INVALID_STATE_TRANSITION`; **hash mismatch 409 `STALE_REVISION`** (`current_version = head revision_no`); **checklist gate (400 `INVALID_REQUEST`)**: every `CUSTOM` activity needs an entry whose `checklist_version` is the current version and whose required items are all `checked: true`; each missing or unchecked item is a `field_errors` entry (`field` `checklist[<order>].items.<item_id>`, code `REQUIRED`); entries for non-custom activities or unknown orders are `UNKNOWN_FIELD`. Nothing is written when the gate fails. Confirming an older DRAFT while a newer draft exists is allowed (the path names the revision, the hash fences it); the newer draft stays DRAFT.
- **T3D-D6 What confirm writes (one transaction).** (1) checklist columns of each CUSTOM activity (`safety_checklist_version`, `checklist_result`, `confirmed_by`, `confirmed_at`); (2) the previous `APPROVED` plan of the occurrence becomes `SUPERSEDED` with `superseded_at` **before** (3) this plan becomes `APPROVED` with `approved_by/at` (the partial unique index would otherwise fire; the DDL-A trigger also refuses approval while a CUSTOM activity is unconfirmed, the DB backstop for l.548); (4) the referenced document revision gets the one-way review stamp `CONFIRMED` (`reviewed_by`, `reviewed_at`) if still `NEEDS_REVIEW` (T3C-D5); (5) the occurrence gets `approved_plan_revision_id`, `state PLAN_APPROVED`, `revision + 1`; (6) audit entry `lesson.plan.confirm` and the receipt. The supersession here only marks the old plan (WP-3 rule, §31.8.2); cancelling runs, jobs and decks is WP-4, and no `LESSON_PLAN_NOT_APPROVED` is returned by T-3 routes (l.871 is for later steps that need an approved plan).
- **T3D-D7 Safety checklist definition (FR-T-09; OPEN).** The SRS requires a "safety checklist" per Teacher-written activity (l.548, l.1660, l.1708, l.2189) and gives no item list, wording or version. The code holds the definition as a versioned frozen constant in `domain/lesson_occurrences/safety_checklist.py` (`version`, ordered `item_id` and Vietnamese text); **its content is a product and safety decision and is not invented here**. Without a supplied definition T-3d implements and tests the gate with a test-only definition and ships with an empty registry, so a plan with a CUSTOM activity cannot be confirmed (400 `INVALID_REQUEST`, `field_errors` naming the checklist version) until the owner provides it. See §7, BLOCKED_OPEN question.
- **T3D-D8 Keys (l.1697).** Both commands keyed; receipts in `be1_command_receipts` (scopes `POST /v1/lesson-occurrences/{id}/plan-revisions` and `.../{n}/confirm`), fingerprints over the canonical request; the receipt stores references (revision id and number) and replay returns the current stored row after re-authorisation; another payload is 400 `INVALID_IDEMPOTENCY_KEY`.
- **T3D-D9 Deny rule.** As T3A-D3: out of scope or unknown 404; guide/observer 403; unassigned in-scope Teacher 404 on existing occurrences (the 409 `TEACHER_ASSIGNMENT_REQUIRED` applies only to create, T3A-D2); Manager and Parent 404.

**ETag** of a plan revision is `"<content_hash>.<state>"` (state changes at confirm while content is immutable, so the hash alone would not be a valid validator). The occurrence read (T-3a) shows the approved plan's `revision_no` and `plan_hash`; there is no `latest` alias; the head is the first list item. The SRS gives no read shapes (l.798): these are the TD-05 choices.

## 6. FE impact (not done), rollback, risks

- **FE:** Teacher web plan form (objectives, story direction, activities, document revision picker), checklist dialog that blocks approval (l.1708), 409 reload on stale hash, revision history. Android: none.
- **Rollback:** revert the commit; written rows stay valid; no DDL. A confirmed plan cannot be edited or deleted (trigger); correction is a new revision.
- **Risks:** R1 the checklist definition is missing (BLOCKED_OPEN below); R2 the plan hash excludes the checklist, so two confirmations of one hash with different checklist answers are possible only on the first confirm (second is a no-op); R3 trigger-level checks add failure modes that surface as `DBAPIError` (service pre-checks first and maps them); R4 later tasks (WP-4 run creation, WP-5) must read `approved_plan_revision_id` and pins from this schema; supersession handling of runs is theirs.
