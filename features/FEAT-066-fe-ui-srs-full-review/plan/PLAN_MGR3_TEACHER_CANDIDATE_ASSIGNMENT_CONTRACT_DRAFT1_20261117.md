### 2.1 Assignment handler and persistence facts

- The assignment handler locks the active classroom row with `FOR UPDATE`, derives the organization from that row, checks the caller's current `school_admin` assignment, and counts active Teacher assignments for the class. If one exists, it returns 409 `CLASS_TEACHER_EXISTS`.
- It then looks up `payload.subject`. If no `AdultIdentityModel` exists, it creates one with the caller's issuer and active state. If one exists, it checks issuer equality only. The handler does not establish that the selected subject is a verified Teacher, an active Teacher account, or a current member of the same organization before creating the class assignment. The body-supplied subject is therefore not a safe candidate reference under D-066-62.
- The successful response returns that subject. The target candidate/assignment contract must not expose or accept provider UID, raw subject, email, or other personal data without an approved basis. A server-issued, organization-scoped opaque candidate reference is one **PROPOSAL**, not a selected field or existing contract.
- `AdultIdentityModel` has `state`, `account_role`, and `role_revision`. `OrganizationAssignmentModel` has organization, subject, optional class, role, active, and created time, but no assignment revision or pending-transfer state. Its unique constraint is `(organization_id, subject, class_id, role)`; it does not enforce at most one active Teacher per class. The class-row lock/count is handler-level behavior for this route, not a global invariant across all assignment-affecting writes.
- The current endpoint behaves as an initial assignment command: it rejects a class that already has an active Teacher. No Teacher reassignment or offboarding command is declared in the audited BE1 router. Platform Admin role changes can separately deactivate assignment rows; that path does not implement the SRS transfer saga.
- `GET /organizations/{organization_id}/me` filters assignments by the authenticated caller's subject and active rows. It cannot be treated as a substitute for a scoped candidate-read API.

### 2.2 Provisioning and mutation paths that constrain a candidate source

- The Platform Admin account-create schema allows role `teacher` without an organization ID. The create handler provisions the identity and stores the Teacher account role, but its organization-assignment branch is only for `school_manager`. This does not establish same-organization Teacher membership for candidate discovery.
- The public registration handler creates Parent identities. The BE1 bootstrap utility creates an organization and its initial School Manager identity/assignment. Neither is a Teacher candidate source.
- In the inspected BE source, the Manager class-assignment route is the only direct creation of `OrganizationAssignmentModel(role="teacher")`. Platform Admin account role-change logic can deactivate assignments. No separate Teacher invitation, organization-membership provisioning, candidate-read, or Teacher-assignment revoke route was found in the audited surfaces.
- Consequently, a reviewed contract needs an owner-approved source for verified, organization-bound Teacher candidates. This plan does not add Teacher invitation/provisioning or assume that account creation is equivalent to organization membership.

### 4.2 Assignment command

At command time, revalidate the authenticated Manager's current organization/class authority, the active class, and the selected candidate's verified identity, Teacher role/state, same-organization eligibility, and current assignment facts. A list result may be stale and cannot authorize the write by itself. Do not accept a guessed/raw principal subject from the client.

The Rev60 target is `POST /v1/classes/{class_id}/assignments` with HTTP 200 and an assignment revision. The existing BE route is a source path only; exact gateway/prefix mapping stays OPEN. A request field such as `candidate_ref` and a response with an opaque assignment reference plus revision are **PROPOSALS**; names, representation, required preconditions, and public error mapping are OPEN. Do not expose the source `subject` field without an approved basis.

Require the SRS idempotency behavior: same principal/operation/target key and same payload replays the original result; different payload under the same key returns HTTP 400 `INVALID_IDEMPOTENCY_KEY`. The literal header, format/length, missing-key response mapping, fingerprinting, receipt persistence, and retention are OPEN. `X-Request-ID` remains correlation only.

Enforce exactly one active responsible Teacher per class across every writer. A future implementation must prove a transaction/locking or database invariant that covers Manager assignment, account role/state changes that affect assignments, and any approved lifecycle path. Current `FOR UPDATE` plus count and a test-file assertion are source evidence, not proof of an invariant across all writers or runtime environments. A database constraint or table is not selected by this plan.

Return the SRS assignment revision on success. Do not treat `AdultIdentityModel.role_revision` as an assignment revision.

### 4.3 Errors and privacy

**SRS REQUIREMENT — Rev60 §9.8:** every API error uses the stable safe envelope `code`, `message`, `correlation_id`, and `retryable`, with optional `retry_after_seconds` and `field_errors` when applicable. Return HTTP 403 `ACTION_NOT_ALLOWED` only after confirming the resource is in scope and the actor lacks permission for that action. Return HTTP 404 `RESOURCE_NOT_FOUND` with the same shape for nonexistent and out-of-scope class/candidate resources; do not disclose membership, assignment, or existence across scope.

**Current source gaps:** a missing/inactive class currently returns `403 SCOPE_DENIED`; missing account/assignment scope can return `403 ACCOUNT_SCOPE_UNAVAILABLE`; the BE1 envelope serializes `request_id` and does not match the Rev60 envelope. These are source observations, not target policy. The assignment-specific occupied-class conflict mapping (including whether to retain or replace source code `CLASS_TEACHER_EXISTS`) remains OPEN because Rev60 does not define that operation-specific mapping. Do not disclose candidate identity in such a conflict.

The current BE1 error envelope uses `request_id`; Rev60 specifies `correlation_id`, `retryable`, and optional `retry_after_seconds`/`field_errors`. The final assignment envelope and correlation mapping need an explicit OpenAPI contract. Generated schema and runtime output remain NOT VERIFIED.
