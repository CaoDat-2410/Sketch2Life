## 1. Changes to Draft 1

- **Request size guard (R1 F-01, P2).** Draft 1 §6 R1 becomes a requirement. The route is bounded to 13 MiB (a 2 MiB text of control characters is 6 bytes per character once JSON-escaped, about 12 MiB, plus the envelope). The guard is an ASGI branch of the existing bounded-upload middleware: it refuses a `Content-Length` over the cap and counts streamed bytes, answers 413 `MEDIA_TOO_LARGE` in the CONV-1 envelope, and runs before FastAPI reads, parses or validates the body and before any authorisation or database access. FastAPI converts an error raised while it reads the body into its own 400, so the streamed case records the breach, drops the application's answer and sends the 413 itself. Tests: oversize with and without a length, exactly at the cap (not a 413), a valid 2 MiB control-character text under the cap, other routes untouched, 413 before authentication and without any database write.
- **Text hazards (R1 F-02, P2).** The text is encoded strictly: a lone surrogate or a NUL is 400 `INVALID_REQUEST` with `field_errors [{extracted_text, INVALID_FORMAT}]`; the limit is 2,097,152 UTF-8 bytes (`TOO_LONG`), blank after trimming is `EMPTY`. Pydantic `max_length` stays a coarse character bound (a character is at least one byte); the byte check is the real limit. The rules run before authorisation and before any database access.
- **Replay snapshot (R1 F-03).** The receipt stores `status_code`, `document_revision_id`, `revision_no` and the `review_state` the revision had when it was created (no text). A replay reads the immutable row and answers with that review state and ETag, so it equals the first response even after the revision is confirmed. Test added.
- **No-op receipts (R1 F-04).** A no-op writes the receipt only (status 200, the head revision id of that moment), no revision and no audit entry; its replay returns that head, not the current one. Exact bytes are compared (no normalisation): another line ending is a real edit. Stated in the OpenAPI description.
- **Cap (R1 F-05).** 50 revisions per document counted including the extraction revision, under the document lock; the 51st edit is 409 `RESOURCE_CONFLICT`. The cap is checked after the stale fence and the no-op check, so a no-op at 50 still answers 200. The OpenAPI text says that reloading does not help. A total-text-size cap instead of a count stays an option for the owner.
- **Locks and tests (R1 F-06).** Lock order: occurrence `FOR SHARE`, then the source document `FOR UPDATE` (the order T-3d uses). The occurrence state is read under that share lock. `ARCHIVED` and `DELETED` are set by SQL in the tests (no v3 route sets them). Added tests: the 409 body carries `current_version` as an integer and the head `ETag`; missing key is 400 `REQUIRED`; unknown body field is `UNKNOWN_FIELD`; a Teacher of another organization, a Manager and an unknown document answer one 404 body; guide and observer 403; no row lock or open transaction survives any outcome.
- **Approval (R1 F-07).** Unchanged: an edit never confirms itself; a DRAFT plan may pin a `NEEDS_REVIEW` revision and the Teacher may edit again after pinning. OQ-1 stays open for the owner.
- **Write scope (T-3b review F-02 ruling).** The write path is the responsible Teacher only (guide, observer and a second Teacher row of the class are 403).
