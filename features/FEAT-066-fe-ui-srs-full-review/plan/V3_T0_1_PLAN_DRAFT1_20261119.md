## 3. Exact changes per route

### 3.1 Four story routes (`routers/parent_story_runs.py`)
- Keep the declaration `Header(alias="Idempotency-Key", min_length=1, max_length=128)` (required in the published OpenAPI, so the catalog `header \`Idempotency-Key*\`` rows stay valid; `maxLength` becomes 128).
- After `_require_parent(db, principal)` add `key = parse_idempotency_key(request)` (needs `request: Request` on the three confirmation routes; `create` has it) and pass `key` to the service instead of the raw header value (same order as cancel/delete, `:389-392`). This catches space, control characters and two headers that header validation does not.
- `app.py` validation handler, `/v1/story-runs` paths only: an issue at `header/Idempotency-Key` yields **400 `INVALID_REQUEST`**, message "Yêu cầu không khớp với hợp đồng API.", and is **not** added to `field_errors` (null when nothing else is wrong; other field issues keep today's `INVALID_FIELD` items). For `/api/parent/v1/ai/...` paths keep the flag and `INVALID_IDEMPOTENCY_KEY` unchanged (T-2d).
- Order of checks on a keyless request becomes: body/header validation 400 first, then auth, role, key parse. A missing key therefore hides a 403/404 behind 400, which discloses nothing.

### 3.2 `POST /api/be1/v1/organizations/{organization_id}/classes` (`be1_registry.py:465`)
1. Signature: add `request: Request`, `response: Response` and `idempotency_key: Annotated[str, Header(alias="Idempotency-Key", min_length=1, max_length=128)]` (same as `:308`). Missing key then answers 400 `INVALID_REQUEST` with `field_errors [{Idempotency-Key, REQUIRED}]` (conv1 handler, `app.py:675-688`).
2. After `_require_m2_assignment(... roles={"school_admin"})`: `parse_idempotency_key(request)` (1-128 visible ASCII; adds the rule C6 lacks).
3. `scope = f"POST /organizations/{organization_id}/classes"` (tenant in scope; at most 156 of 256 chars). `fingerprint = sha256(canonical JSON {"display_name": payload.display_name})`, helper style of `be1_registry.py:335-341`.
4. `receipt = db.get(Be1CommandReceiptModel, (principal.subject, scope, key))`. Found with another fingerprint: 400 `INVALID_IDEMPOTENCY_KEY` (`failure(...)`, as `:343-349`). Found with same fingerprint: rebuild the body from the stored `class_id` and `state`, plus `display_name` read from the class row, `db.rollback()`, answer 201 again. (Display name is not stored in `response_json`, per the model docstring `be1_models.py:68-74`.)
5. Else create the class as today, then `db.add(Be1CommandReceiptModel(principal_ref, operation_scope, idempotency_key, organization_id, request_fingerprint, response_json={"class_id", "state"}))` in the same transaction as the class, audit and event rows.
6. Commit with local handling (not `be1_common.commit`): on `IntegrityError` roll back, re-read the receipt; same fingerprint: replay; another fingerprint: 400 `INVALID_IDEMPOTENCY_KEY`; none: 409 `RESOURCE_CONFLICT`. This makes two concurrent same-key requests create **one** class (the loser rolls back with its audit/event rows; no orphan). Pattern: `platform_admin_accounts.py:549-572`.
7. Body: `{"contract": "Be1ClassV1", "class_id", "display_name", "state": "active", "assignment_revision": 1}` (`class_assignment_revision(0)` = 1, same value as the list item at `:455`). `ClassroomModel.state` default is `"active"` (`be1_models.py:138`); use `record.state` after `flush`. `assignment_revision` is a response field only, no `If-Match` and no ETag (l.1649, l.1699 need no expected revision here). Column meaning: it is the assignment revision the next assignment call must send; the class revision of T-7c profile create is a different concept (OQ-1).

No model, no migration, no new route. `be1_command_receipts` exists (`be1_models.py:68`, migration `20261119_ar_0002`): PK `(principal_ref, operation_scope, idempotency_key)`; key column 128 chars matches the rule.
