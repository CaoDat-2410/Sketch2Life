## Montessori/profile implementation

- Added versioned `ChildLearningProfileContextV1` and `P1ContextOptionsRequestV1`; the profile
  contains bounded catalog IDs and adult-confirmed progress, not child identity or free text.
- The existing GET route is preserved. A POST on the same context-options path validates actor,
  session and expected version, computes the same no-profile baseline plus deterministic
  personalized options, and does not mutate the session or call Qwen again.
- Parent/Guide profile settings and initial child selection can edit interests/dislikes,
  adult-confirmed progress, readiness, available material options, supervision and explicit
  non-clinical supports. The active flow locks profile edits. React state is volatile; no
  AsyncStorage, backend history write or analytics write was added.
- Profile request metadata records which adult role declared it and when; each progress item keeps
  its own confirming adult and date. Recommendation explanations expose that provenance when that
  progress evidence affected the selected activity.
- Regression audit found that V2 could select a versioned golden activity while the recommendation
  card adapter only understood curated expansion variants, yielding an empty card list. The adapter
  now reads only the exact activity version, displays its authored title/purpose/material/safety
  metadata, and marks preparation blocked with a clear warning if no matching preparation profile
  exists; it does not silently reuse stale preparation metadata from another version.
- Safety/supervision, prerequisites, dislikes, readiness and all required material groups are hard
  gates. Interests, adult-confirmed objectives and explicit support may only adjust ranking after
  hard gates. No-profile behavior retains its pre-existing path.
- Material-group regression: MVP activity `ACT-0002` has two separate required groups. A profile
  with an option from only one group is now rejected; one compatible option from each group passes.
